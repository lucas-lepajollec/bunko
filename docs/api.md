# HTTP API contract

All endpoints are same-origin. Unless marked public, send `Authorization: Bearer <access-token>` or the `bunko_session` cookie from `/api/auth`. Never put keys in query strings. POST/PATCH/DELETE JSON requests require `Content-Type: application/json`; maximum body size is 1 MiB. A supplied Origin must match the application host. Responses are uncached except private, bounded image caching.

Types below refer to **the complete browser-safe definitions in `src/types/shared.ts`**. Responses are the named value directly, not an extra `{data: ...}` envelope. Failures use `ApiError`: `{ "error": { "code": "...", "message": "..." } }`. Do not display raw HTML from upstream synopses.

Enqueue only the chosen variant of each chapter.

The URL-based chapter lookup resolves an already discovered Suwayomi manga by exact source ID and source-relative manga URL. If unknown it returns `MANGA_NOT_INDEXED` (404); perform a deep search first. There is no universal arbitrary-URL scraper. ## Administrator account and browser sessions

`GET /api/auth` is public and **always returns 200 for normal authentication state**, replacing the old signed-out 401. Before setup it returns `{authenticated:false,setupRequired:true,username:null}`. After setup, signed-out, expired and invalid-cookie requests return `{authenticated:false,setupRequired:false,username:null}`; a valid session returns `{authenticated:true,setupRequired:false,username:"<saved username>"}`. Other protected routes still return 401 `UNAUTHORIZED` without valid cookie/Bearer authentication. Responses are `Cache-Control: no-store`.

On the first visit, `POST /api/auth/setup` takes `Credentials`: `{username,password}`. The username is 3–40 ASCII letters/digits/`.`/`_`/`-`; the password is 10–200 characters, with no trimming. Successful setup creates the single administrator and signs in the browser. Creation is enforced atomically by SQLite: concurrent and later valid setup calls return 409 `ALREADY_SET_UP`. No default account or password is seeded. Existing installations migrate to this same setup flow; their settings, media and API token are preserved, and old token-login browser cookies must be replaced by account sign-in.

`POST /api/auth` takes the same credentials. Username matching is case-insensitive; the saved spelling is returned. Before setup it returns 409 `SETUP_REQUIRED`; a wrong username or password returns 401 `INVALID_CREDENTIALS` with the same generic message. Unknown usernames perform a dummy scrypt derivation with the same parameters and constant-time digest comparison. Validation failures return 400 `VALIDATION_ERROR`. Login and password verification share a process-wide budget of 20 attempts per minute and 10 per normalized username per minute, returning 429 `RATE_LIMITED` before hashing after exhaustion. Successful attempts count too; the fixed window resets after 60 seconds. No forwarded IP is trusted.

`POST /api/auth/password` takes `{currentPassword,newPassword}` (`PasswordChange`, each 10–200 characters) while authenticated. The current password must verify; a wrong current password returns 401 `INVALID_CREDENTIALS`. The new hash and a fresh random session epoch replace the previous values atomically. All previously issued browser cookies become invalid immediately, and the current browser receives a replacement cookie. Concurrent changes cannot overwrite a newer password using stale verification. `DELETE /api/auth` expires the current browser cookie with 204, as before. Cookies use `HttpOnly; SameSite=Strict; Path=/`, last seven days, and include `Secure` for HTTPS request URLs. A supplied Origin must match the incoming Host on setup, login, password changes and sign-out; cross-site requests return 403 `FORBIDDEN`.

API automation continues to send `Authorization: Bearer <contents of data/access.token>` to protected endpoints, including before account setup. The token cannot be submitted to the browser login endpoint. Account/password resets preserve this token. Cookie signing still uses that existing secret; rotating it also invalidates browser cookies.

For account recovery, start/recreate the container with `BUNKO_RESET_ACCOUNT=true`. Startup deletes only the administrator account, immediately invalidating its browser sessions, and emits one clear line announcing the reset without secrets. The next visit shows first-start setup again. Settings, media and the API token are preserved. **Remove the flag after this recovery start**: leaving it enabled resets the account again on every server/container restart. Reset runs even with `BUNKO_WORKER=false` and only once per process/volume across Next route module instances. Restrict access while setup is open; the first successful setup request becomes the administrator.

## Settings

`Settings` is the write shape, `PublicSettings` the read shape. The read response contains `secretsConfigured` booleans for `suwayomiPassword`, `kavitaApiKey`, `sonarrApiKey`, `prowlarrApiKey`, with **no corresponding secret fields**. A frontend must send only edited fields; it must never send a displayed mask as a key. Empty strings explicitly clear optional keys/URLs; `suwayomiUrl` remains a required HTTP(S) base URL. URL credentials, query strings and fragments are rejected; put credentials in the separate key fields.

`kavitaLibraryPath` is an optional absolute POSIX manual mapping prefix inside Kavita, default `/library`. The default requires no configuration: for `/medias/Mangas`, Bunko tries `/library/medias/Mangas` and `/library/Mangas`, preferring a unique candidate confirmed by indexed series folders. A library mounted directly at `/library` is recognized only when its indexed series folders exist there. Multiple confirmed candidates (or multiple unconfirmed existing suffix candidates) are ambiguous and unreachable. A nondefault prefix is used only if it matches the Kavita path and a reachable local directory, with series confirmation when available. The mount root comes from `BUNKO_LIBRARY_DIR` (default `/library`), never the client.

`libraryTargets`, default `{}`, maps `MANGA`, `MANHWA`, `MANHUA`, `NOVEL` to `{libraryId:positiveInteger,folder:absoluteKavitaPath}` or `null` (explicitly disabled). ONE_SHOT uses MANGA; LIGHT_NOVEL/WEB_NOVEL use NOVEL. Targets use the same resolver as folder reporting and imports. Changed targets/prefixes must resolve inside the mount and, when library information is indexed, belong to the selected library. Traversal, backslashes, NULs and symlink escapes are rejected. Each kind uses its saved target; null refuses the kind, while an omitted kind can use the unique reachable suggested library folder. Names containing manhwa/manwha/webtoon, manhua, novel/light novel/LN/books, or manga suggest the corresponding kind; Book/LightNovel types also suggest NOVEL. MANHWA and MANHUA require their own matching name/type or an explicit target; a Manga library does not receive them implicitly. No effective writable target, or multiple suggestions, returns **409 `TARGET_NOT_CONFIGURED` before enqueue persists jobs**. The mounted root is never an implicit fallback; it can only be a confirmed mapping of an actual library. `KavitaLibrary.suggestedFor` exposes these kind suggestions.

`autoImportKavita` is a boolean, default `true`. Each successful index sync follows unlinked Kavita series automatically. Disabling it leaves existing tracking untouched. `favoriteSourceIds` remains a legacy setting: its current value migrates once, on first source-preferences read, to `SourcePreferences.enabledSourceIds`. Later edits to that legacy field do not override saved preferences. `updateIntervalMinutes` is an integer from 5 to 1440, default 15, exposed unchanged in `PublicSettings`. `extensionRepos:[]` means no extension repositories. Repository changes are persisted locally before Suwayomi applies them; if the upstream fails the request reports failure but the saved value remains, and resending the same PATCH retries application.

## Search and streams

`UnifiedMedia` contains stable provider-prefixed IDs, media type, explicit nullable metadata, authors, tags, aliases, provider identifiers, actual source matches and tracked/Kavita linkage. Metadata providers can fail independently; read `providers[].status`. No-type searches include both AniList manga/novels and a separate anime request, so two AniList outcomes can appear. Explicit `MANGA` normally has four outcomes; `NOVEL` two; `ANIME` one. No fabricated results are inserted when a provider is unavailable.

`UnifiedMedia.startDate` is a nullable partial ISO publication date: `"YYYY"`, `"YYYY-MM"` or `"YYYY-MM-DD"`. AniList supplies the available year/month/day; MangaDex and MangaUpdates supply a year; Suwayomi-only results return `null`. Search deduplication retains the most precise available date. Older submitted media payloads may omit this field; validation defaults it to `null`.

## Discovery

`GET /api/discover` returns `{items:UnifiedMedia[],page,hasNextPage}` from AniList's reading catalog (manga and novels, excluding adult entries). Optional query parameters:

| Parameter | Accepted values                                                                               | Default    |
| --------- | --------------------------------------------------------------------------------------------- | ---------- |
| `kind`    | `all`, `manga` (JP), `manhwa` (KR), `manhua` (CN), `novel`                                    | `all`      |
| `sort`    | `trending`, `popular`, `score`, `new`                                                         | `trending` |
| `genre`   | Genre string, maximum 60 characters                                                           | Omitted    |
| `status`  | `RELEASING`, `FINISHED`                                                                       | Omitted    |
| `year`    | Integer 1900–2100                                                                             | Omitted    |
| `season`  | `WINTER` (Jan–Mar), `SPRING` (Apr–Jun), `SUMMER` (Jul–Sep), `FALL` (Oct–Dec); requires `year` | Omitted    |
| `page`    | Integer 1–200                                                                                 | `1`        |
| `perPage` | Integer 1–50                                                                                  | `24`       |

For example, `/api/discover?kind=manga&year=2026&season=SPRING&sort=popular` selects titles whose publication began in April–June 2026. Year alone selects the entire publication year, including year-only dates. Season filtering requires a known month. Invalid parameters, including season without year, return HTTP 400 `VALIDATION_ERROR`.

Date filters use AniList's exclusive `startDate_greater` / `startDate_lesser` FuzzyDateInt bounds, including partial dates within the requested period and excluding the next period. `sort=new` orders by publication start descending, then popularity, requires popularity **greater than 300**, and restricts dates to before tomorrow in UTC while excluding entirely unknown dates. Its upper bound is intersected with the requested year/season, so future periods return no titles. Partial dates retain their provider precision. Unset GraphQL variables are omitted. The bounded ten-minute discovery cache includes all effective variables, including the date bounds; the `new` cache key changes at UTC midnight.

## Search stream behavior

Each network metadata request has a 2500 ms deadline, rather than a guaranteed sub-200 ms end-to-end response. Repeated searches use a persistent SQLite cache per provider with a 30-second freshness TTL. Stale results return immediately while one background refresh runs; a provider failure retains its last successful results. Local FTS and tracked/Kavita presence are recomputed on every response. The UI should debounce, cancel stale searches and cache locally. Deep search runs a query per enabled source in preferred languages, with a 20-second deadline per active source call. Search, matching, browse and popular sync share a FIFO limit of six active source calls; queued time does not consume the upstream deadline. Matching can try up to three titles successively, each with that deadline. Both deep search and `/api/media/sources` start requests in preference priority order and stream results in completion order. Disconnect cancels source requests. Events:

```text
event: sources
data: {"sources":[...]}

event: source_result
data: {"source":{...},"results":[...],"titles":[...],"hasNextPage":false,"durationMs":120}

event: source_error
data: {"source":{...},"code":"SOURCE_HTTP_ERROR","detail":"HTTP error 503 [url]"}

event: done
data: {"completed":3}
```

`source_result.results[i]` corresponds to `titles[i]`. `done.completed` counts sources attempted, including failures; sync can emit multiple pages for each source. No sources is a legitimate empty sources event followed by `done` with zero. A setup/stream-wide failure emits `error` with `{code,message}`. Comment heartbeats occur every 15 seconds. `EventSource` automatically reconnects: **close it on done and on component cleanup**. Deep search is a finite operation; download status is continuous. For the POST sync stream use fetch + a real SSE parser; a chunk is not necessarily a full event.

Downloads emit `snapshot` with a `DownloadsSnapshot` and `error` with `{code,message}`. The local engine returns `status.state` STARTED or STOPPED, queue item states QUEUED, DOWNLOADING or ERROR, and `progress = pagesDone/pagesTotal` (0–1). No speed or ETA is fabricated. A queue error is not completion. Batches distinguish enqueuing/downloading/importing/scanning/completed/error. Worker imports/scans continue after the stream is closed.

Use `thumbnailUrl` and extension `iconUrl` exactly as returned: these are application-relative authenticated image-proxy URLs. A native image element or an unoptimized Next image carries the same-origin cookie; an unauthenticated server-side image optimizer cannot retrieve them. The proxy only permits `/api/v1/manga/<numeric-id>/thumbnail` and `/api/v1/extension/icon/<package>`, limits bytes and rejects active SVG/HTML. Unfollowed metadata covers/banners use provider URLs. Followed covers switch to the stable authenticated `/api/covers/<id>?v=<hash>` URL after storage.

## Arr interactive search

- Sonarr: `?provider=sonarr&seriesId=123&seasonNumber=1&episodeNumber=2`. `seriesId` required; season/episode optional. If provider is omitted, the presence of seriesId selects Sonarr.
- Prowlarr: `?provider=prowlarr&query=Title`. Query required. Without provider or seriesId, Prowlarr is selected.
- POST the selected release's own `{provider,guid,indexerId}`. Sonarr receives `/api/v3/release`; Prowlarr receives `/api/v1/search`. GUIDs are opaque and provider-specific. Search again if the upstream cache expires.
- Tags are parsed from the actual title; missing resolution/codec/seeders stay null. `sizeGb` uses GiB (1024³ bytes), rounded to two decimals; label it GiB. Missing seeders must never be presented as zero. Display rejection reasons and require a deliberate user selection before grabbing.

## Tracking and imports

`TrackRequest` accepts optional `status` (default `READING`), `autoDownload`, `kavitaSeriesId` and ordered `sources`. `TrackPatch` requires `id`, accepts the same state fields, and optionally accepts a validated `media:UnifiedMedia` to replace the catalog identity. Replacement updates title, type, cover and catalog metadata/IDs while preserving reading status, ordered sources, download preference, import/update history, progress and Kavita linkage. Conflicting media/AniList/MangaDex identities return 409 `ALREADY_TRACKED` without mutation. Status is one of `PLANNING`, `READING`, `PAUSED`, `COMPLETED`, `DROPPED`; caught-up is derived by the frontend. `autoDownload=true` requires selected manga/novel sources and is rejected for anime. Source order is preserved and the first available variant is preferred during automatic MANGA checks.

Each `TrackedMedia` returns `status`, `progress`, `newChapters`, `lastReadAt`, `identity`, `sourceStatus` and `coverChoice`. `progress.owned` counts the union of distinct imported numeric chapter numbers and matched Kavita chapter numbers, including fractional numbers; duplicate source variants count once. `read` is null until a successful Kavita progress fetch, then the highest completely read numeric chapter (0 if none). A partially read chapter does not advance `read`. `unread` counts owned numbers above `read`, or all owned numbers when `read` is null. `released` is the maximum of catalog chapter count, every linked source’s latest numbered chapter, historical source observations, and the highest owned/indexed Kavita chapter number. Source statuses refresh in the worker, so plain `GET /api/tracked` includes current released counts without opening a title page. `newChapters` counts distinct observed numeric chapters absent from both the imported ledger and matched Kavita series. Unnumbered specials retain their upstream identity for download/detection but do not affect numeric counts. Imported archives are linked by media ID, AniList ID or MangaDex ID, including imports made before tracking.

Kavita progress refreshes on the worker update cycle and on `GET /api/tracked?refresh=progress`. The on-demand endpoint starts at most one refresh per two minutes, sharing an attempt timestamp in SQLite across route instances/restarts. Concurrent requests share the same run, bounded to 15 seconds with up to four entries in flight. Later requests inside the two-minute window return the stored array immediately, including after a failed attempt. Failure preserves the last successful progress. `readSource` is `kavita` after a successful fetch, otherwise `none`; `lastReadAt` comes from Kavita's reading timestamps. A saved `kavitaSeriesId` is used directly. Otherwise the local Kavita index matches normalized title/aliases against series name, localized name, original name and sort name. If the index has no match, reading-progress refresh retains the legacy bounded folder/title lookup as a fallback. The resolved ID is saved. Supplying `kavitaSeriesId` in PATCH is a sticky manual choice: a positive indexed ID links that series, `null` explicitly marks the entry as absent from Kavita. Automatic title matching, progress fallback, chapter presence and ownership honor that choice on every later sync. Changing/clearing the link clears cached read progress until refreshed; replacing only `media` keeps it. API-key and JWT authentication modes use the configured Kavita user.

Enqueue requires a full `UnifiedMedia` so metadata survives a restart. Enqueue, tracking and identity-patch schemas accept HTTP(S) resource URLs without credentials, plus an exact allowlist of root-relative Bunko image routes: `/api/suwayomi/image?path=<approved encoded thumbnail/icon path>`, `/api/kavita/image?seriesId=<positive id>` and `/api/covers/<trackedId>?v=<16 lowercase hex chars>`. Local routes reject extra/duplicate parameters, traversal, fragments, backslashes and other origins; an arbitrary local path never qualifies. Media returned by detail, tracked, catalog/discovery and search can be sent back unchanged. Repeated tracking uses the existing row. Enqueue and same-identity media patches use the server's followed artwork; submitted cover/banner fields cannot replace it. Select a cover using `cover`, and use a different catalog identity to replace a wrong match. A slow patch rebases its state fields on the latest row; an intervening identity change returns 409 `CONCURRENT_EDIT`. The local worker calls Suwayomi `fetchChapterPages(input:{chapterId})`, downloads its authenticated proxy pages, and constructs an ordered CBZ with embedded `ComicInfo.xml`. It never enqueues Suwayomi downloads or changes Suwayomi download settings. One chapter transfers at a time, with three pages in parallel; each page has a 20-second deadline, a 20 MiB cap, supported raster image content types, and up to three attempts with 250/500 ms backoff. Chapters are capped at 2000 pages and 256 MiB total page bytes. Temporary file + fsync + rename precedes the imported-chapters ledger write. Page caches persist in the application state volume for retries/restarts and are removed after successful import.

New folders are sanitized series titles without hash suffixes. Filenames are `Series Title Ch. 0012.cbz`, `Series Title Ch. 0012.5.cbz`, `Series Title Vol. 03 Ch. 0012.cbz`, or `Series Title SP - chapter name.cbz`. A volume is taken from chapter metadata when supplied internally, or an explicit volume marker in the chapter name. Specials embed `<Format>Special</Format>` to force Kavita's special handling. If a matched Kavita series already has a folder inside the selected target/library, that exact folder is reused. Nothing moves old hash-suffixed folders or files. Scan-folder receives the actual series folder mapped back into Kavita's namespace.

Enqueue requires an effective library target. A previously configured target can still resolve while Kavita is offline; a scan failure leaves the batch retryable after Kavita returns. Retry reconciles the ledger and skips completed chapter imports, retaining partial page caches. The successful CBZ write plus ledger entry determines chapter completion, independently of Suwayomi `isDownloaded`.

## Sources and browsing

`GET /api/sources` returns every installed source matching `SourcePreferences.languages`, including disabled sources. `enabledSourceIds` is an ordered list of positive signed 64-bit **strings**. An empty list enables all matching sources in Suwayomi order. Disabled sources have `priority:null`; enabled priorities follow preference positions. `iconUrl` uses the existing authenticated image proxy and `extensionId` is the providing package when available. `GET /api/sources/preferences` reads preferences and `PUT` replaces both fields, for example:

```json
{ "enabledSourceIds": ["9223372036854775806", "9007199254740993"], "languages": ["fr", "en"] }
```

Search, automatic media matching, and catalog sync use enabled sources; browsing a disabled source remains possible. Source health persists the latest search/browse latency, checked timestamp, safe error code and optional sanitized `detail`: `slow` above 4000 ms, `ok` otherwise, `error` on failure and `unknown` before a call. GraphQL extension messages classify Cloudflare/challenge/CF 403 as `CLOUDFLARE`, HTTP/status errors as `SOURCE_HTTP_ERROR`, and login/authentication requirements as `SOURCE_LOGIN_REQUIRED`; other messages retain `SUWAYOMI_GRAPHQL_ERROR`. HTTP `cf-mitigated: challenge` is also recognized. SSE `source_error` and `SourceHealth.detail` expose only a sanitized first line of at most 140 characters; URLs, query strings, credentials/tokens and emails are removed. Upstream messages are never logged raw.

`GET /api/sources/[id]/filters` maps the pinned Suwayomi filter union to header, separator, select, text, checkbox, tristate, sort and group. Group children have positions relative to their group. Filters preserve defaults, including false, empty text and null sort selection. Nesting is bounded to eight group levels. The source must be installed in the selected languages; it need not be enabled.

`POST /api/sources/[id]/browse` takes an explicit positive page, mode `POPULAR`, `LATEST` or `SEARCH`, optional query (up to 200 chars) and optional filters. Each filter change has `position` and exactly one state field. A group change wraps its child, for example:

```json
{
  "mode": "SEARCH",
  "query": "Title",
  "page": 1,
  "filters": [{ "position": 7, "groupChange": { "position": 0, "triState": "INCLUDE" } }]
}
```

The backend sends `fetchSourceManga` with `source`, `type`, `query`, `page` and `filters`, indexes results in FTS, and returns `{source,items,page,hasNextPage}`. Items include `trackedId` when the Suwayomi manga is selected by a tracked entry. Suwayomi applies filters to SEARCH; POPULAR/LATEST follow the upstream source's own listing behavior. Browse uses the same 20-second active-call deadline and six-call queue. Unsupported latest or extension failures use structured upstream errors.

## Updates and download controls

The durable worker refreshes **all tracked entries with selected sources**, including manual titles, using `updateIntervalMinutes`. First check treats currently discovered, unimported chapters as new. Observations prevent repeated entries on later checks/restarts. Detection groups prefer the first selected source for duplicate numbers, group by tracked series/source/check, and keep each detection group whole while splitting automatic batches at 500 chapters. Manual groups are `pending`; automatic groups persist a batch and become `queued`. The feed derives `downloading` from downloading/importing/scanning, `downloaded` only when every linked batch completes, and `error` on batch failure. Retrying a batch updates the feed too. Partial manual enqueues leave remaining chapters pending after the selected chapters complete. Observations and automatic batch creation share a transaction.

`GET /api/updates` returns `{entries,lastCheckAt,nextCheckAt,checking,autoCount,trackedCount}`. Times are ISO strings or null before a first check; counts refer to MANGA entries with sources, and `autoCount` is their automatic subset. `checking` follows a live worker lease. `lastCheckAt` is the most recent check start; next time is that timestamp plus the configured interval. Per-source failures preserve partial results and retry on the next cycle. A check has a separate 45-second background matching budget, a two-minute linked-source deadline, a 15-second progress budget and a 60-second cover budget; oldest source checks run first. Incomplete source work keeps the check requested; unfinished work requests another cycle. `POST /api/updates/check` persists a request and returns 202 immediately; repeated requests during an active check do not start duplicate work. Restart retries an interrupted check after acquiring the worker lease. Processing existing batches may delay a requested or scheduled check.

For a pending entry, find its `TrackedMedia` using `trackedId`, POST its ordered selections as `{sources:[...]}` to `/api/manga/chapters`, choose variants whose numbers appear in `entry.chapters`, then POST `{chapterIds,media:tracked.media}` to `/api/downloads/enqueue`. Existing update groups link to manual batches (including alternate source variants with the same observed number). No extra enqueue endpoint is required. Unnumbered specials are available through the chapter table; the feed's numeric `chapters` array omits them.

`POST /api/downloads/control` takes `{"action":"pause"}`, `{"action":"resume"}` or `{"action":"clear"}` and returns the local `DownloadStatus`. Pause interrupts active transfers and persists STOPPED across restart; resume allows the worker to continue. Clear interrupts transfers, empties the local queue and marks unfinished/failed transfer batches `error` with `CANCELLED`; written CBZs, ledger entries and partial page caches remain available for explicit retry. It preserves the paused/running preference. A persisted cancellation generation coordinates distinct Next module instances. Failed batches use the existing retry endpoint. EPUB conversion and AniList login remain outside this API.

## Error behavior

| HTTP | Typical codes                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------ |
| 400  | VALIDATION_ERROR, INVALID_STATE payload validation                                               |
| 401  | UNAUTHORIZED, INVALID_CREDENTIALS                                                                |
| 403  | FORBIDDEN (origin)                                                                               |
| 404  | NOT_FOUND, MANGA_NOT_INDEXED                                                                     |
| 409  | SERVICE_NOT_CONFIGURED, INVALID_STATE, SETUP_REQUIRED, ALREADY_SET_UP                            |
| 413  | PAYLOAD_TOO_LARGE                                                                                |
| 415  | CONTENT_TYPE                                                                                     |
| 429  | RATE_LIMITED (login)                                                                             |
| 502  | UPSTREAM_TIMEOUT, UPSTREAM_HTTP_ERROR, SUWAYOMI_GRAPHQL_ERROR, ARR_GRAB_ERROR, KAVITA_SCAN_ERROR |
| 500  | INTERNAL_ERROR without credential/upstream body exposure                                         |

Stream HTTP status is already committed after opening; later errors are named SSE events. Per-provider failures are reported inside successful search responses. Batch errors persist as safe codes and require explicit retry. Never assume HTTP 200 means every external service succeeded.

## Kavita index and catalog presence

The worker refreshes an index of all accessible Kavita libraries and series each update cycle, using paginated `Series/all-v2`, `Series/metadata` and `Series/volumes`. `POST /api/kavita/sync` requests the same work without waiting. Failed refreshes preserve the previous complete snapshot, set status `error`, and back off requested retries for 60 seconds. `syncedAt` is the last successful refresh; `unconfigured` means URL/key are absent. An accepted folder scan is asynchronous inside Kavita, so newly scanned content can appear on a later index refresh.

`GET /api/kavita/libraries` uses Kavita's folders, reports their mapped `localPath` or null, and probes writeability with an exclusive temporary file immediately removed. Unmounted or inaccessible folders are not writable; no directories are created by this probe.

`UnifiedMedia.kavita` is null or `{seriesId,libraryId,libraryName,chapters,url}`. Its chapter count is the distinct numeric chapter count; specials and volume-only sentinel entries do not invent chapter numbers. Numeric ranges expand to distinct numbers (bounded to 2000 increments). A saved tracked `kavitaSeriesId` wins; otherwise only a single normalized-title/alias match qualifies. Search (including cached results), discovery, media detail, relations, recommendations and tracked media use the local index. `url` is `${kavitaUrl}/library/${libraryId}/series/${seriesId}`. Submitted media accepts omitted or nullable `kavita`, default null; client presence does not override authoritative tracked linkage.

`GET /api/kavita/series?q=name` searches indexed names/aliases (case/diacritic insensitive, maximum 200 characters); it can combine with `unmatched=1` to omit series linked explicitly or unambiguously by title to a tracked entry. Covers always use `/api/kavita/image?seriesId=...`; authentication stays server-side (the upstream URL includes `apiKey` as required by stable v0.9.x, along with the configured API-key/JWT headers; develop also accepts this URL), redirects and active content types are refused, and transfer time/size are bounded.

`POST /api/kavita/track` searches the catalog using up to four indexed names, excludes anime, and requires a best match scoring at least 0.85 with a margin of at least 0.10 over the next identity. It creates or links the catalog entry with `kavitaSeriesId` set. New entries default to READING, or COMPLETED when every Kavita chapter has positive pages and is completely read; existing user status is preserved. Repeating an explicit link returns it. No match, ambiguous identity or an existing conflicting link returns 409 `NO_MATCH` without tracking changes; an unknown index ID returns 404.

After each successful sync, `autoImportKavita=true` runs the same unique catalog matching for unlinked series. Without an unambiguous catalog match, or when that identity has a conflicting/manual link, it follows a `kavita:<seriesId>` media (`providers:["kavita"]`), using the indexed title/aliases, summary, genres, library-derived format and `/api/kavita/image?seriesId=...` cover. `GET /api/media?id=kavita:<id>` returns `MediaDetail` with empty tags/relations/recommendations; unknown indexed IDs return 404. These identities are accepted for tracking, chapters and source matching, which uses their titles. Imports are idempotent and preserve existing user status, sources and manual links. DELETE tracking remembers a linked series dismissal durably, preventing automatic re-import; explicit track-from-Kavita can add it again.

For catalog-linked entries with a reachable writable series folder and no `cover.*`/`folder.*` raster image (case insensitive), Bunko downloads the catalog cover from its restricted HTTPS provider allowlist (15 MiB / 15 seconds, redirects refused). It atomically writes an exclusive `cover.jpg`, preserving existing covers. **Kavita does not use a series-folder sidecar as its custom series cover**: Bunko also calls `POST /api/Upload/series` with `{id,url:"data:image/...;base64,...",lockCover:true}`, then requests `Library/scan-folder` using the original Kavita series path. Pending upload/scan state survives retries; an edited sidecar cancels the pending upload. This initial missing-cover bootstrap preserves existing files; subsequent tracked cover synchronization follows the selected/automatic cover as described below. See [Kavita's cover selection explanation](https://github.com/Kareadita/Kavita/discussions/2717) and [UploadController](https://github.com/Kareadita/Kavita/blob/develop/Kavita.Server/Controllers/UploadController.cs).

## Off-catalog identities, background sources and cover selection

Every `TrackedMedia` includes `backdrop: "auto" | "hidden"`, persisted per tracked entry. Existing entries migrate to `"auto"`, and newly tracked entries default to it. `PATCH /api/tracked {id,backdrop:"hidden"}` hides the catalog banner; `backdrop:"auto"` restores automatic display. Other values (including null) return 400 `VALIDATION_ERROR` without mutation. Unrelated patches preserve the saved choice. A successful `media` or `offCatalog:true` patch resets it to `"auto"`, even if the same request supplies `backdrop:"hidden"`, so a replacement work can show its banner. Off-catalog banners remain hidden by the interface regardless of this preference.

`PATCH /api/tracked {id,offCatalog:true}` removes the catalog identifiers and metadata. With a linked indexed Kavita series it becomes `kavita:<seriesId>` using that series’s title, aliases, summary, genres and cover. Otherwise it becomes `suwayomi:<first linked mangaId>` using the source’s title, metadata and proxied thumbnail. Without either identity it returns 409 `NO_IDENTITY` without mutation. The row, reading state, history and sources stay attached. `identity` is `catalog` or `off-catalog`; a detachment is persistent and automatic Kavita import/matching retains it. An explicit later `media` patch can select a catalog work again. `media` and `offCatalog` cannot be combined.

The worker wakes immediately on local enqueue, retry/resume, update/index requests, tracking and identity edits. Otherwise it sleeps for `BUNKO_WORKER_IDLE_MS` (default 30000, clamped 1000–300000). One scheduler per process/volume serves all route bundles; other processes observe durable requests on their next idle wake. Active work renews its 90-second SQLite lease every ten seconds; idle work has no heartbeat timer. The worker continuously drains a queue of source-less MANGA entries independently of the update interval, one entry at a time with a 250 ms pause between entries. Never-searched entries come first, then the oldest search. A search without a confident result is retried after seven days; PATCH changes to media, off-catalog identity or Kavita linkage requeue it immediately. Enabled sources are searched in parallel through the same shared six-call gate as interactive searches, with selection in preference order and the interactive title scorer. Cancellation or loss of the worker lease discards unfinished matching results and leaves them retryable. Sources in error back off for six hours. Only candidates scoring at least 0.9 qualify; the best eligible candidate per source is selected, up to three sources per entry. Automatically linked statuses have `auto:true`. `PATCH {id,sources:[...]}` makes retained/new links manual (`auto:false`) and persists every removed source+manga pair as dismissed. Automatic matching never restores those pairs; a user can explicitly select them again. Concurrent user source/identity edits take precedence over an in-flight match.

`sourceMatch` is `linked` when sources exist, `searching` for the entry currently being processed under a live worker lease, `queued` when due, and `not-found` after a search without confident matches. `GET /api/library/activity` is authenticated and uses SQLite/settings only, with no upstream requests. It returns `{matching:{queued,current},refresh:{running,done,total,lastAt,nextAt}}`. `queued` excludes the current entry; `current` is its title or null. Refresh counts cover linked entries attempted in the current/latest update cycle; `lastAt` is that cycle's start and `nextAt` adds the configured interval. `running` and current matching require a live worker lease, so a crashed worker does not remain visibly active.

`sourceStatus` follows the order of `sources`, with `sourceId`, `suwayomiMangaId`, source title, proxied `thumbnailUrl`, `latestChapter`, `chapterCount`, `checkedAt`, `auto` and safe `error` code. The update cycle refreshes chapter and manga metadata for linked entries regardless of automatic downloads. Failures keep the last successful values with an error code; behind sources remain linked and never lower the released maximum. Initial statuses are persisted on tracking/manual selection, before the first background check. An automatic source link immediately refreshes chapter numbers, source titles and thumbnails, without waiting for an update cycle.

`GET /api/tracked/covers?id=<trackedId>` lists the matched catalog cover, up to 20 MangaDex volume covers when a MangaDex ID is known (cached for 24 hours), linked source thumbnails via `/api/suwayomi/image`, and the linked Kavita cover via `/api/kavita/image`. Options carry `{origin,id,label,url}`; stable IDs are catalog media IDs, `mangadex:<coverId>`, `<sourceId>:<mangaId>` or the Kavita series ID. A MangaDex failure keeps local options and cached volume options usable. Unknown tracked IDs return 404.

`PATCH {id,cover:"auto"}` tries catalog cover, then linked source thumbnails in order, then Kavita. A successful candidate is downloaded and retained by Bunko, independently of later upstream failures. `PATCH {id,cover:{origin,id}}` selects one returned option. A source choice may name any live Suwayomi manga, including an unlinked scan result: `{origin:"source",id:"<sourceId>:<mangaId>"}`. The server verifies that the manga belongs to the source. Unknown manga/wrong source returns 404 `NOT_FOUND`; unavailable catalog/Kavita choices return 400 `INVALID_COVER`. PATCH returns the complete updated `TrackedMedia`. Apply identity replacement before selecting a cover in a separate patch. Explicit cover selection (including selecting the same option again) fetches replacement bytes. Identity/link context changes resolve again; ordinary source metadata refreshes keep stored bytes. Matching search/discover/detail results reuse the followed cover through exact catalog IDs or a unique linked source/Kavita identity.

The first successfully fetched cover is atomically stored as `<data>/covers/<trackedId>-<16-char SHA-256>.<ext>` (JPEG/PNG/WebP/GIF/AVIF, maximum 15 MiB). Both `TrackedMedia.coverUrl` and its `media.coverUrl` become `/api/covers/<trackedId>?v=<hash>`; home, detail, search and discovery use the same URL. `coverFallbacks` is empty after storage and for manual choices; before storage it lists remaining automatic candidates. A failed full resolution returns `coverUrl:null` and retries later. Background backfill processes one entry at a time within the 60-second cover budget; idle backfill retries missing covers at most every five minutes. Explicit choices bypass that backoff. Replacement publishes a complete new file/pointer, deletes the previous file and changes `v` when bytes change. Untracking removes the stored file. Stored covers are independent of the bounded/evictable upstream proxy cache.

`GET /api/covers/<id>?v=<hash>` requires normal authentication, returns raster bytes with `Cache-Control: private, max-age=31536000, immutable`, an ETag derived from the stored hash, and bodyless 304 for matching `If-None-Match`. Unknown IDs/versions return 404. Omitting `v` resolves the current file with `private, max-age=0, must-revalidate`. Hits stream from disk without contacting upstream or re-hashing the image. The worker synchronizes these same stored bytes to Kavita using `Upload/series` and `lockCover:true`, even without a local library mount. A durable hash suppresses unchanged uploads; a failed upload retries from local bytes. Kavita-origin bytes are never uploaded back to the same reader. Mounted writable series folders receive an atomic `cover.jpg`. Source/Kavita credentials remain server-side, transfers are bounded and reject redirects, and catalog hosts remain allowlisted.

`libraryTargets` distinguishes omitted kinds (one unambiguous matching suggestion may be used), `{libraryId,folder}` (explicit selection), and `null` (explicitly no target). Null disables suggestions and fallback for that kind; downloads return 409 `TARGET_NOT_CONFIGURED` before jobs are persisted. A missing MANHWA/MANHUA target never uses a Manga library. Stored older broad suggestions are reclassified from the library name/type before target selection.

## Persistent server caches

Both `/api/kavita/image` and `/api/suwayomi/image` (including extension icons) persist complete raster bytes and content type under `<data>/cache/images/`. Keys incorporate the configured upstream/authentication identity and are SHA-256 filenames; the client cannot supply a disk path. The cache is limited to 500 MiB with least-recent-access eviction. Writes use an exclusive temporary file, fsync and atomic rename. Kavita covers retain the 15 MiB transfer cap, Suwayomi thumbnails/icons 10 MiB; both have a 15-second deadline and reject redirects/active content.

Images return a strong SHA-256 `ETag`, `Cache-Control: private, max-age=86400, stale-while-revalidate=604800` and bodyless 304 for a matching `If-None-Match`. Disk hits stream the image payload without re-hashing it; the strong hash is saved on publication. Legacy cache entries compute that hash once per process until refreshed. Disk hits require no upstream request. After one day, the cached bytes return immediately and a coalesced background fetch attempts revalidation, at most daily even on failure. Failed fetches keep the old copy beyond its freshness period. Successful Bunko cover uploads invalidate the matching Kavita proxy entry, including obsolete in-flight writes; unchanged byte hashes do not upload again.

Catalog metadata, discovery pages, genres, MangaDex volume options and per-provider search results share a bounded SQLite cache (1,000 values / 64 MiB, maximum 8 MiB per value; oldest refreshed values pruned). Freshness TTLs are 30 seconds for search, ten minutes for discovery, 30 minutes for details and 24 hours for genres/volume options. Stored values return immediately after expiry while one background refresh runs. Failed refreshes retain them, with a 30-second retry floor (or TTL when shorter); only a cold lookup needs a successful upstream response. These server caches do not change JSON responses' `Cache-Control: no-store`.

`GET /api/media?id=...` for a followed catalog, linked-source or Kavita identity returns the persisted tracked media immediately, with cached detail extras when available and empty extras otherwise. Background catalog/detail refreshes update `tracked_media` without blocking the request or overwriting an intervening identity edit. Reading state, source links and validated cover resolution remain attached. Suwayomi detail keys are scoped to the configured upstream credentials. No Kitsu integration currently exists.
