# HTTP API contract

All endpoints are same-origin. Unless marked public, send `Authorization: Bearer <access-token>` or the `bunko_session` cookie from `/api/auth`. Never put keys in query strings. POST/PUT/PATCH/DELETE JSON requests require `Content-Type: application/json`; maximum body size is 1 MiB. A supplied Origin must match the application host. Responses are uncached except private, bounded image caching.

Types below refer to **the complete browser-safe definitions in `src/types/shared.ts`**. Responses are the named value directly, not an extra `{data: ...}` envelope. Failures use `ApiError`: `{ "error": { "code": "...", "message": "..." } }`. Do not display raw HTML from upstream synopses.

## Accounts, sessions and authorization

Every user is a separate Bunko instance with their own settings, Suwayomi/Kavita connections, libraries, sources/extensions, matches, covers, downloads, files, updates and content filter. Admins additionally manage accounts; all other API capabilities are equal for both roles. Every protected handler runs inside its authenticated tenant context. Missing authentication returns 401 `UNAUTHORIZED`; account-management routes return 403 `FORBIDDEN` for members.

`GET /api/auth` is public and returns 200 `AuthState`: `{authenticated,setupRequired,username,userId,role}`. Signed-out identities have `username`, `userId` and `role` set to null. The response resolves the current username, numeric user ID and `admin` or `member` role from the accounts store on every request. Before first setup (or during administrator password recovery), `setupRequired` is true. Responses use `Cache-Control: no-store`.

`POST /api/auth/setup` takes `Credentials` (`{username,password}`). Usernames contain 3–40 ASCII letters/digits/`.`/`_`/`-`; passwords contain 10–200 characters without trimming. Setup creates the first admin atomically under a SQLite immediate transaction; concurrent/later setup returns 409 `ALREADY_SET_UP`. No default credentials are seeded. Existing administrators migrate to user 1, with their password hash, library dates, status, progress and content filter preference preserved. Existing signed v2 cookies retain their IDs, session epochs and signing key and remain valid.

`POST /api/auth` accepts the same credentials, matches usernames case-insensitively and returns the saved spelling. Before setup it returns 409 `SETUP_REQUIRED`; unknown usernames and wrong passwords both return 401 `INVALID_CREDENTIALS`. Unknown users perform the same scrypt derivation and constant-time comparison. Login/password verification retains the 20/minute process-wide and 10/minute normalized-username budgets; successful attempts count, exhaustion returns 429 `RATE_LIMITED`, and no forwarded IP is trusted.

`POST /api/auth/password` changes only the signed-in user's password using `{currentPassword,newPassword}`. Hash and session epoch rotate atomically; that user's earlier cookies become invalid, other users' sessions remain valid, and the caller receives a new cookie. Stale concurrent verification cannot overwrite a newer password. `DELETE /api/auth` expires the current browser cookie with 204. Signed v2 cookies include the user ID, expiry and random session epoch and use `HttpOnly; SameSite=Strict; Path=/`, seven-day expiry and `Secure` for HTTPS. Origin checks apply to mutations. Roles are read from SQLite on each request, so promotions/demotions apply to existing sessions immediately.

The Bearer access token belongs to its original user (the first admin by default) and always acts inside that tenant, including after role changes. Deleting its owner revokes it. Before setup, protected tenant calls return 409 `SETUP_REQUIRED`. It cannot sign in browsers. Password resets preserve the token; rotating it invalidates all cookies.

| Route               | Authorization and behavior                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/users`    | Admin: `UserAccount[]`, sorted by ID; no hashes, epochs or keys                                                                |
| `POST /api/users`   | Admin: `UserCreate {username,password,role}` → 201 `UserAccount`; duplicate username (case-insensitive) → 409 `USERNAME_TAKEN` |
| `PATCH /api/users`  | Admin: `UserPatch {id,username?,role?,password?}` → `UserAccount`; resetting a password invalidates that user's sessions       |
| `DELETE /api/users` | Admin: `{id,confirmDeleteData:true}` → `{ok:true}`; revokes sessions and deletes the tenant data directory                     |
| `GET /api/me`       | Signed-in user: `MyAccount {id,username,role,adultContent}`                                                                    |
| `PATCH /api/me`     | Signed-in user: `MyAccountPatch {username?,adultContent?}` → `MyAccount`                                                       |

Deleting or demoting the last admin returns 409 `LAST_ADMIN`, transactionally. Unknown users return 404 `NOT_FOUND`. Account deletion requires an explicit `confirmDeleteData:true` flag; absent/false confirmation returns 400 `VALIDATION_ERROR` without deletion. Mounted Kavita library media is retained. Creation and password resets use the setup password/username rules. `UserAccount.kavitaLinked` means that tenant has both a Kavita URL and a configured key; keys are never returned. Kavita credentials belong to `/api/settings`, and `/api/me` accepts only the username and content filter preference.

`PATCH /api/users` lets an admin rename any account, including themselves; `PATCH /api/me` lets either role rename only their own account. Both return the updated account, including its new username, and reuse setup’s 3–40 character ASCII username validation without trimming. Invalid names return 400 `VALIDATION_ERROR`; a username already held by another account, regardless of case, returns 409 `USERNAME_TAKEN`. Case-only changes and resubmitting the same name are allowed. Admin username/role/password edits commit together; a rejected rename changes none of them. A rename alone preserves the user ID, password hash and session epoch: existing cookies and the owner’s Bearer token remain valid, and `GET /api/auth` immediately returns the new spelling. Login accepts only the new name (case-insensitively). An accompanying password reset still invalidates that account’s browser sessions. The tenant directory remains `<data>/users/<id>/`; no data or media files move.

Admins and members can use every personal-instance route, including settings, service status, Arr, source preferences, catalog sync, extensions, Kavita targets/index sync, update checks and queue controls. `/api/users`, changes to shared optional catalog fields and `/api/settings/test-provider` require admin. All work IDs, batches, observations, caches and files resolve from the caller's tenant; an unknown work in that tenant returns 404, irrespective of another tenant's IDs. There are no shared-work membership permissions.

Recovery with `BUNKO_RESET_ACCOUNT=true` clears only the first admin's password and rotates that admin's session epoch at startup. It preserves the user ID, username, role, tenant preferences/library, other users/sessions, settings, works, files and token. `/api/auth/setup` then sets a replacement password on that same admin (the submitted username does not rename the retained account). Reset runs once per process/volume, including with `BUNKO_WORKER=false`. Remove the flag after recovery; each fresh process otherwise resets again. Restrict access while recovery setup is open.

## Settings

`Settings` is the write shape and `PublicSettings` the read shape for every signed-in user. GET/PATCH use that user's own instance except for the shared optional catalog fields described below. The deprecated `adultContent` field aliases the same preference exposed by `/api/me`. The read response contains `secretsConfigured` booleans for all `SecretSetting` keys, with **no corresponding secret fields**. `catalogs:{canManage:boolean,configured:{googlebooks:boolean,metron:boolean,rakuten:boolean,hardcover:boolean}}` supplies shared availability and the caller's write/probe permission. Availability means configured, not a successful live credential check. A frontend must send only edited fields; it must never send a displayed mask as a key. Empty strings explicitly clear optional keys/URLs; `suwayomiUrl` remains a required HTTP(S) base URL. URL credentials, query strings and fragments are rejected; put credentials in the separate key fields.

`kavitaLibraryPath` is an optional absolute POSIX manual mapping prefix inside Kavita, default `/library`. It is independent of the local tenant media root. For `/medias/Mangas`, Bunko tries `<mediaRoot>/medias/Mangas` and `<mediaRoot>/Mangas`, preferring a unique candidate confirmed by indexed series folders. A library mounted directly at the resolved root requires indexed series-folder evidence. Multiple confirmed candidates (or multiple unconfirmed existing suffix candidates) are ambiguous and unreachable. A nondefault prefix is used only if it matches the Kavita path and a reachable local directory, with series confirmation when available.

`Settings.mediaRoot: string | null` is an explicit choice of `/library` (or `BUNKO_LIBRARY_DIR`) or one of its direct real subdirectories. Names are arbitrary and independent of usernames/account IDs. `PATCH /api/settings {"mediaRoot":"/library/lucas-special"}` reserves that folder; `{"mediaRoot":null}` clears it. Unknown, relative, nested, noncanonical, traversal, symlink or non-directory paths return 400. An exact or ancestor/descendant overlap with another account's reservation returns **409 `MEDIA_ROOT_TAKEN`**. Sibling directories can be chosen by different accounts. Validation and reservation share an immediate accounts-store transaction, including concurrent PATCH requests; target validation failures roll back the reservation. Clearing never moves/deletes files and never triggers automatic reassignment.

`GET /api/kavita/status` returns `{state,series,syncedAt,mediaRoot,mediaRootOptions}`. Its `mediaRoot` is the reachable chosen root, otherwise null. Settings retain the chosen path even when its directory is temporarily missing. `mediaRootOptions: {path:string,usedBy:string|null,available:boolean}[]` includes the mount and its direct real subdirectories only. `usedBy` is the exact owner's current username or null; `available` is false for an overlap with another owner, including when the option itself has no owner. A user's own reservation remains available. Missing reserved roots continue blocking overlap until cleared. Roots/ancestors that are symlinks are refused. Null makes Kavita folders unreachable and downloads fail with `TARGET_NOT_CONFIGURED`.

Upgrade snapshots the existing working roots once: exact current username directories, numeric directories, then user 1's legacy mount if no dedicated/explicit root conflicts. Unsafe/missing/ambiguous resolutions remain null. A stale rename/isolation marker does not suppress user 1's legacy mount when another account has only an abandoned old-name folder. An explicit subfolder owner does suppress it. After migration, names and directory appearances never choose another root; renaming changes only the owner label in options. No media moves, and Kavita-side paths/format targets stay unchanged. See [Docker volume layouts](architecture.md#docker-volumes-and-library-mounts).

`libraryTargets`, default `{}`, maps `MANGA`, `MANHWA`, `MANHUA`, `COMIC`, `LIGHT_NOVEL`, `WEB_NOVEL`, `NOVEL`, `BOOK` to `{libraryId:positiveInteger,folder:absoluteKavitaPath}` or `null` (explicitly disabled). ONE_SHOT uses MANGA; all four text formats have separate targets. Schema v11 copies an old NOVEL target (including null) to LIGHT_NOVEL and WEB_NOVEL, retaining NOVEL and any already separate targets; BOOK remains unset. The migration runs once per tenant. Targets use the same resolver as folder reporting and imports. Changed targets/prefixes must resolve inside the mount and, when library information is indexed, belong to the selected library. Traversal, backslashes, NULs and symlink escapes are rejected. Each kind uses its saved target; null refuses the kind, while an omitted kind can use the unique reachable suggested library folder. Names containing manhwa/manwha/webtoon, manhua, light novel/LN, web novel/WN, novels/romans/books, non-fiction/essays, or manga suggest the corresponding kind; generic Book libraries default to NOVEL and LightNovel types to LIGHT_NOVEL; Comic/ComicVine types and names containing comics, BD or bande dessinée suggest COMIC. COMIC never falls back to a Manga target. MANHWA and MANHUA require their own matching name/type or an explicit target; a Manga library does not receive them implicitly. No effective writable target, or multiple suggestions, returns **409 `TARGET_NOT_CONFIGURED` before enqueue persists jobs**. The mounted root is never an implicit fallback; it can only be a confirmed mapping of an actual library. `KavitaLibrary.suggestedFor` exposes these kind suggestions.

`autoImportKavita` is a boolean, default `true`. Each successful index sync follows Kavita series in that tenant's library, for either role. Disabling it leaves existing tracking untouched. `favoriteSourceIds` remains a legacy setting: its current value migrates once, on first source-preferences read, to `SourcePreferences.enabledSourceIds`. Later edits to that legacy field do not override saved preferences. `updateIntervalMinutes` is an integer from 5 to 1440, default 15, exposed unchanged in `PublicSettings`. `extensionRepos:[]` means no extension repositories. Repository changes are persisted locally before Suwayomi applies them; if the upstream fails the request reports failure but the saved value remains, and resending the same PATCH retries application.

## Search and streams

`UnifiedMedia` contains stable provider-prefixed IDs, media type, explicit nullable metadata, authors, tags, aliases, provider identifiers, actual source matches and tracked/Kavita linkage. Metadata providers can fail independently; read `providers[].status`. No-type searches include AniList manga/light novels, MangaDex, MangaUpdates, Open Library and local entries. `type=NOVEL` includes LN, WN, fiction and non-fiction books; `MANGA` excludes text and `ANIME` uses AniList only. Open Library is represented under the existing `local` provider enum; provider outcomes are grouped once per enum value, reporting error if any member failed while retaining successful results. Open Library identities always use `openlibrary:OL…W` and its own work URL. No fabricated results are inserted when a provider is unavailable.

`UnifiedMedia.startDate` is a nullable partial ISO publication date: `"YYYY"`, `"YYYY-MM"` or `"YYYY-MM-DD"`. AniList supplies the available year/month/day; MangaDex and MangaUpdates supply a year; Suwayomi-only results return `null`. Search deduplication retains the most precise available date. Older submitted media payloads may omit this field; validation defaults it to `null`.

`fast=1` returns `partial:true` from tenant FTS, tracked works, indexed Kavita series and any persistent provider results already present, including stale results. It makes no upstream request or revalidation attempt. The normal call remains complete and omits `partial`; failures remain in provider outcomes. Both paths use identical provider order, deduplication, relevance ranking, tracking enrichment and content filter. The intended fast-path budget is approximately 300 ms on a local catalog; it is not an upstream deadline. Fetch the normal URL to complete the result.

## Discovery

`GET /api/discover` returns `{items:UnifiedMedia[],page,hasNextPage,pending?,warnings?}` from AniList, MangaUpdates, Open Library or configured optional catalogs (the per-user content filter applies to every provider). Optional query parameters:

| Parameter | Accepted values                                                                                       | Default    |
| --------- | ----------------------------------------------------------------------------------------------------- | ---------- |
| `kind`    | `all`, `manga` (JP), `manhwa` (KR), `manhua` (CN), `comic`, `lightnovel`, `webnovel`, `novel`, `book` | `all`      |
| `sort`    | `trending`, `popular`, `score`, `new`                                                                 | `trending` |
| `genre`   | Genre string, maximum 60 characters                                                                   | Omitted    |
| `status`  | `RELEASING`, `FINISHED`                                                                               | Omitted    |
| `year`    | Integer 1900–2100                                                                                     | Omitted    |
| `season`  | `WINTER` (Jan–Mar), `SPRING` (Apr–Jun), `SUMMER` (Jul–Sep), `FALL` (Oct–Dec); requires `year`         | Omitted    |
| `page`    | Integer 1–200                                                                                         | `1`        |
| `perPage` | Integer 1–50                                                                                          | `24`       |

For example, `/api/discover?kind=manga&year=2026&season=SPRING&sort=popular` selects titles whose publication began in April–June 2026. Year alone selects the entire publication year, including year-only dates. Season filtering requires a known month. Invalid parameters, including season without year, return HTTP 400 `VALIDATION_ERROR`.

Date filters use AniList's exclusive `startDate_greater` / `startDate_lesser` FuzzyDateInt bounds, including partial dates within the requested period and excluding the next period. `sort=new` orders by publication start descending, then popularity, requires popularity **greater than 300**, and restricts dates to before tomorrow in UTC while excluding entirely unknown dates. Its upper bound is intersected with the requested year/season, so future periods return no titles. Partial dates retain their provider precision. Unset GraphQL variables are omitted. The bounded ten-minute discovery cache includes all effective variables, including the date bounds; the `new` cache key changes at UTC midnight.

`kind=comic` uses Metron when the shared catalog is configured, and otherwise returns `{items:[],page,hasNextPage:false}` with HTTP 200 and no upstream catalog request. Comics/BD also appear through local/source search, matching and the Kavita index; `UnifiedMedia.type` remains MANGA and its `format` is COMIC. See [optional catalogs](#optional-catalogs).

With `kind=all` (including an omitted kind), AniList, fiction/nonfiction Open Library pages, MangaUpdates WN and configured Hardcover/Metron results are combined. A cold aggregate waits at most 300 ms for the first useful lane, then returns `pending:true` while the rest load. Revalidate the same query until false. Results use round-robin provider order, without a shared popularity score; `page`/`perPage` apply to each provider lane, so aggregate item counts can exceed `perPage`. No extra slice discards provider items. `hasNextPage` is true while any returned lane has another page. Partial failures retain available results with `warnings:[{provider,code:"METADATA_UNAVAILABLE"}]`; total failure becomes 502 once loading finishes. Degraded aggregates retry after thirty seconds; healthy ones cache ten minutes. The UI requests eight items per lane in All and polls pending pages every 1.5 seconds.

### Text catalogs

`lightnovel` uses AniList `format:NOVEL` (all origins map to LIGHT_NOVEL); MangaDex entries explicitly tagged Novel/Light Novel map to the same format. `webnovel` uses MangaUpdates Novel search pages plus cached full series sheets. MU's single Novel type is classified WEB_NOVEL only with positive evidence in genres, categories, publication names, publishers or serialization/status fields: Web Novel/web serial/online serialization or platforms such as Shousetsuka ni Narou/Syosetu, Kakuyomu, Qidian, JJWXC, Munpia, Royal Road, Wattpad, Naver, Kakao or Novelpia. Otherwise it defaults to LIGHT_NOVEL. Summary search results start a coalesced tenant-local background hydration because MU omits these fields in summaries. The response uses available positive evidence immediately and sets `pending:true` while detail classification runs. Detail sheets run one at a time with a thirty-second job budget and a five-minute per-record retry cooldown; later requests resume unfinished records. Failed classification without any confirmed WN returns METADATA_UNAVAILABLE instead of a misleading final empty success. Offline/missing evidence retains the LN fallback in general search. WN discovery maps trending/popular/score/new to MU week_pos/list_reading/rating/year. Pages may be sparse after classification; hasNextPage follows provider pagination. Unsupported seasons return an empty page.

Open Library discovery errors (HTTP, timeout, invalid JSON/shape) return HTTP 200 with `{items:[],page,hasNextPage:false,warnings:[{provider:"openlibrary",code:"METADATA_UNAVAILABLE"}]}`. A stale good page stays available during failures; after a failed background refresh, subsequent responses retain its items and expose the same non-fatal warning. Successful refresh clears the warning. Failed empty fallbacks are never persisted as successful pages.

`novel` means fiction books (romans), `book` means non-fiction. Both use the keyless [Open Library Search API](https://openlibrary.org/dev/docs/api/search): fiction versus non-fiction/history/science/biography subject facets, with trending/readinglog/rating/new sorting. Explicit non-fiction, essays, biography, memoir, manual or textbook subjects imply BOOK; otherwise fiction/novel/story/fantasy/romance/mystery subjects imply NOVEL (so History, Fiction remains fiction); other factual subjects imply BOOK, and unknown subjects default to NOVEL. This is a metadata heuristic. `new` excludes undated/future years. Genre/year filters apply; unsupported status/season filters return empty pages.

`GET /api/media?id=openlibrary:OL27448W` uses work JSON, the editions listing (`limit=1` and total `size`), author records and a work-key search for the first publication year. It returns authors, synopsis, subjects as genres/tags, the cover, `year`/`startDate`, and additive `editionCount:number|null`. `volumes` is not an edition count. Work and edition IDs remain distinct; only work IDs may be tracked. Covers use covers.openlibrary.org/b/id. Provider metadata is persistently cached in each tenant's SQLite store: search/discovery 30 minutes, work/edition/author detail seven days, bounded by the existing cache budget. A process-wide serial gate paces Open Library at one request per second with a Bunko User-Agent, 15-second request bounds and Retry-After cooldown on 429/503, following its [rate guidance](https://openlibrary.org/developers/api). No keys or account are needed.

LN/WN chapter and volume releases from MangaUpdates/MangaDex keep their separate kinds in releases, planning and home. Google Books and BnF add fiction/non-fiction editions and comics to the release feed. `HomeFeed.latest` always has manga, manhwa, manhua, comic, lightnovel, webnovel, novel and book keys; each shelf is populated when dated provider releases are available. Text downloads are not supported: all four formats return **409 UNSUPPORTED_FORMAT** before target resolution or batch persistence.

## Chapter releases, weekly planning and home

`GET /api/releases` returns `ReleasesPage` with the newest chapter releases first. Filters are `kind=all|manga|manhwa|manhua|comic|lightnovel|webnovel|novel|book`, case-insensitive exact `genre` (maximum 60 characters), and `library=1` for followed works. Each page has at most 50 `ChapterRelease` values and an opaque `nextCursor`, null at the end. Send the cursor with the same filters; malformed or mismatched cursors return 400 `VALIDATION_ERROR`. Equal timestamps use stable IDs for pagination. A concurrent earlier publication correction can move a deduplicated item; cursors do not freeze a historical snapshot.

Releases answer from SQLite immediately, including on first use (an empty feed is valid). Authenticated use of releases/planning/home triggers a coalesced background refresh at most every twenty minutes, with the attempt time persisted before HTTP. Provider outages keep existing data. Cached MangaUpdates series are saved as soon as the daily listing arrives; each newly resolved series is saved separately, so a slow or failed later lookup cannot delay completed releases. A failed refresh emits one sanitized `[releases] refresh incomplete` warning containing only provider names, allowlisted error codes, numeric HTTP statuses and failure counts. Attempt and completion state persist in `worker_state` (`release_refresh`, `release_refresh_result`); an incomplete refresh retains the twenty-minute attempt throttle. The public feed covers approximately thirty days; six weeks of history (at most 30,000 provider records) support planning. MangaUpdates supplies the public daily listing and series metadata, MangaDex complements it with readable chapters in the configured source languages, and `provider:"source"` represents observed chapters of followed titles. Source releases use only Suwayomi chapter `uploadDate` (epoch milliseconds, normalized to UTC). First observation and `fetchedAt` never become publication dates. Missing, zero, invalid, future, or older-than-thirty-day upload dates produce no source feed/planning item. The first successful check of each linked source/manga establishes a baseline without creating library updates or automatic batches; later unseen chapters need a usable recent upload date. Failed checks do not establish a baseline. All observations still advance available chapter counts. Schema v8 clears old source release/detection rows with observation-only provenance; observations, imports and durable download batches remain intact. Existing titles establish their baselines at the next successful check.

MangaUpdates attribution is retained through `provider`, series `webUrl` and group names. Integration verified against the official [MangaUpdates OpenAPI](https://api.mangaupdates.com/openapi.yaml), OpenAPI **3.0.0**, API **1.0.0**, retrieved **2026-10-16**. Bunko uses public `GET /releases/days?include_metadata=true&page=…` and `GET /series/{id}`. The specification marks `POST /releases/search` as bearer-authenticated, so feed ingestion uses the daily route without keys. Daily responses contain `{results:[{record,metadata:{series}}]}`; null series identities are skipped. `release_date` is a day. For the chapter feed, `record.time_added.as_rfc3339` supplies `releasedAt` (normalized to UTC) and `hasTime:true` when the calendar date written in that timestamp, in its own offset, is within one calendar day of `release_date`. This represents when the release appeared on MangaUpdates. Missing/invalid timestamps and older bulk imports retain `release_date` with `hasTime:false`. Feeds sort on that timestamp and planning derives its local `time` from it. Series sheets persist for seven days; stale releases are saved immediately, then ingestion awaits/coalesces revalidation so failures are reported. Other metadata callers retain stale-while-revalidate. Calls share a process-wide serialized gate, a Bunko User-Agent, minimum one-second spacing, and at most three attempts with Retry-After/exponential backoff. Long Retry-After values remain honored; waits beyond the ninety-second request budget fail safely without an early retry.

MangaDex integration uses the official [OpenAPI](https://api.mangadex.org/docs/static/api.yaml), OpenAPI **3.0.3**, API **5.13.1**, retrieved **2026-10-16**: `GET /chapter?order[readableAt]=desc&includes[]=manga&includes[]=scanlation_group&translatedLanguage[]=…`, with a batched manga/cover lookup. Ingestion fetches at most 100 chapters per refresh. MangaUpdates fetches the latest two-day listing plus one rotating historical page (pages 2–21), reading at most 1,000 rows from each. The current page drains all its distinct series progressively (at most 1,000 lookups); the historical page keeps a forty-sheet budget. Missing sheets precede stale revalidation, and cached series anywhere in a page are saved before any sheet lookups. The first current-page fill can take several minutes at one request per second, while releases become readable after each sheet; it does not wait for the full page to finish. This avoids starving less frequent kinds such as novels below the first forty series. This is best-effort coverage, not an exhaustive release archive.

Numbered chapters are deduplicated by resolved series/chapter across providers and groups, retaining the earliest publication and merging group names. Ranges and specials retain their published labels. Cheap resolution uses provider IDs (including MangaDex's AniList link) and unique exact title/alias matches in the followed/catalog metadata cache; conflicting provider identities are preserved. Unresolved MangaUpdates works use `mangaupdates:<series_id>`, directly supported by `/api/media`. `trackedId` is recomputed from current tracking. No remote identity search runs per feed request.

`GET /api/planning` accepts any valid ISO date in `week`, default today, and returns seven dated days starting Monday in the server's time zone (`TZ`). Invalid dates return 400. Past days show actual releases; today shows published releases and estimates for series without an actual release today. Future days show estimates. Estimation needs at least three distinct release dates within the last six weeks, with at least three and 60% on one weekday. Bulk chapter releases on a single date count once. A local hour is estimated only when at least three and 60% of those weekday releases share it; the median minute is used. Missing times remain null. Expected chapter numbers remain null. Date-only records retain their stated day; timestamps use server-local time, including DST. Items sort by known time, then title; unknown times follow known times. `kind` and `library=1` use the same feed rules, without excluding estimable followed works by popularity.

`GET /api/home` returns up to eight recent releases with artwork from distinct series as `hero`, up to ten AniList trending reading works across manga/manhwa/manhua/light-novel formats as `top`, and at most twelve chapter releases per kind in `latest`. Top metadata has a five-minute persistent SWR cache over the existing ten-minute discover cache. A cold top shelf is empty while its background lookup runs. Only nonempty successes are persisted; empty/failed refreshes retain the last good list, including across restarts and generic metadata-cache eviction. An empty cold unfiltered discovery response returns `502 METADATA_UNAVAILABLE`, is never cached as success, and is retried on the next request; legitimately empty filtered/later pages stay valid but uncached. Hero candidates without banners receive at most twelve cached AniList lookups, three concurrently with four-second deadlines, in the background. Matching requires an AniList ID or an unambiguous exact title/alias and compatible type/origin. Banner-bearing releases are preferred; cover-only heroes are used when none have a banner. Resolved artwork persists for a day; warm reads never wait for these lookups. Feed shelves and library artwork/visibility recompute from the current local snapshot. `sort=latest` is not added to discovery; chapter chronology belongs to `/api/releases`.

### Volumes, book editions and followed serials

Volume ownership counts explicitly indexed complete-volume archives: their basename identifies the volume and contains no chapter number. A volume grouping, a missing filename or an imported chapter with a volume label does not establish complete-volume ownership; unknown/partial volumes remain unowned in volume mode. Released is the maximum of catalog `volumes`, observed source/edition volume numbers and owned volumes. Read comes from completed Kavita volumes when available, otherwise completed read chapters mapped to an explicitly owned complete volume; unread and `newChapters` use the same unit. Switching units preserves chapter progress. Source update checks skip chapter variants covered by an explicitly owned complete-volume archive, including in chapter mode; individual chapter imports never suppress the rest of a volume; existing manual selections remain explicit. Update group numbers also follow the work's unit.

Google Books uses the [public volumes API](https://developers.google.com/books/docs/v1/using) without a key: `orderBy=newest`, `printType=books`, subjects fiction/nonfiction/comics, `langRestrict=fr|en`, twenty records per lane, six requests at most per six hours per tenant. Categories classify novel/book/comic; explicit light-novel categories and publisher hints identify LIGHT_NOVEL. [BnF SRU](https://api.bnf.fr/fr/api-sru-catalogue-general) queries recent French printed/digital monographs by creation-date range and publication year, maximum fifty notices per twelve hours, requesting UNIMARC. Both namespace-qualified Dublin Core and UNIMARC parse title, author, date, ISBN and series/tome. BnF IDs (`bnf:cb…`) open through `/api/media`, retaining the catalogue ARK for attribution. **Only an explicit valid publication day enters the chronology**: annual/month-only dates are skipped rather than replaced by their catalogue creation date. This makes BnF sparse, sometimes empty. A private `edition-scan:bnf` cache diagnostic records notices read and notices with a publication day.

All new public calls identify Bunko, serialize per provider with at least 1.2 seconds between request starts, have a fifteen-second deadline and four-megabyte response limit, and reject redirects. Successful metadata and failed-attempt cooldowns persist separately in tenant storage; stale successes survive outages. HTTP status diagnostics contain only provider/status/time. XML parsing rejects DTDs/entities and bounds depth/size. No account, key, chapter text or HTML scraping is required.

Edition deduplication uses validated ISBN-13 (including ISBN-10 conversion), then resolved work/unit/volume identity. Chapter and volume releases remain distinct. MangaUpdates/MangaDex volume-only records also emit `unit:"volume"`. All release/home/planning output uses the existing content filter and current tenant's following state. Future editions stay stored (up to two years ahead) for planning as `expected` on the announced day with no invented time; released feeds contain only dates that have arrived, including exclusion beyond today+7. Edition dates never generate a recurring weekly prediction. `HomeFeed.latest.novel`, `.book` and `.comic` now use these records.

Followed novels with Royal Road fiction URLs/IDs in catalog metadata, source links or exact matching cached catalog titles poll only `https://www.royalroad.com/fiction/syndication/<id>`. AniList detail retains Royal Road external links server-side; linked source URLs can come from the tenant's source catalog. At most five works rotate per pass, with thirty-minute RSS caching and polite shared pacing. RSS items emit `provider:"royalroad",unit:"chapter"`, UTC publication timestamps and chapter numbers when parseable. They appear in releases, planning and informational library updates; RSS items never become Suwayomi download jobs. Unknown chapter numbers retain their titles. A work without a known Royal Road identity requires a catalog/source link: no Royal Road search/page scraping is performed under the RSS-only policy.

## Content filter

`PATCH /api/media/adult` accepts `{id:string,adult:boolean|null}` and returns `200 {id,adult:boolean,adultOverride:boolean|null}`. `true` marks a work 18+, `false` clears a provider false positive, and `null` removes the manual decision and restores automatic classification. IDs also accept `googlebooks:<id>`, `bnf:cb…` and `openlibrary:OL…W`. Other IDs use `anilist:<positive int32>`, `mangadex:<UUID>`, `mangaupdates:<positive decimal, up to 20 digits>`, `suwayomi:<positive int32>` or `kavita:<positive int32>`. Malformed IDs, missing fields and nonboolean/non-null decisions return `400 VALIDATION_ERROR`; normal authentication and same-origin mutation protection apply. Unknown works retain the detail endpoint's not-found/upstream errors and do not create a decision.

Decisions persist independently of provider metadata, across every known exact identity: the media ID, AniList/MangaDex/MangaUpdates IDs, linked Suwayomi/Kavita identities and the tracked row. Newly learned exact aliases inherit the decision; resetting through any alias clears it for the connected work. Titles alone never connect overrides. If separately marked works later acquire a shared identity, the most recent decision wins. Both directions take precedence over all automatic/provider/Kavita evidence. SQLite write versions invalidate library and feed snapshots in the same transaction, so the next request reflects mark, unmark or reset on discovery, full/quick search, releases, planning, home, recommendations/relations, `/api/tracked`, `hiddenAdult` and details, including warm metadata caches. Provider queries include explicit results when a manual false-positive correction needs them; list visibility still follows the effective classification and current user’s preference. The original provider flags and tracked metadata are retained for reset. Editing an untracked title does not follow it.

`MyAccount.adultContent` defaults to **false** per new user and accepts only a boolean in `PATCH /api/me`. The deprecated `Settings.adultContent` alias reads/writes the current user’s preference; it is not a server-wide filter. Migration copies the legacy global value to user 1 only. Per-work overrides belong to the current tenant, including for untracked catalog works. `UnifiedMedia.adult` is computed from AniList’s classification flag, MangaDex’s restricted content ratings, MangaUpdates’ restricted-content genres (Mature alone does not qualify), indexed Kavita `ageRating >= X18Plus` (numeric 14). Source NSFW warnings never classify a title, including titles followed exclusively through those sources. Suwayomi extension flags are exposed as `Source.nsfw` for information only. They never hide a source. Missing provider classification is not proof of adulthood.

With the content filter enabled (`adultContent:false`), discovery, catalog/search (also used by quick search), release feeds, planning, home hero/top/latest, relations and recommendations filter classified adult works. Direct media details always return the work, including adult works, with effective `adult` and `adultOverride` filled. `/api/tracked` hides adult entries and `/api/updates` hides their detection entries and followed/automatic counts. Indexed adult Kavita entries are hidden from lists. Sources remain accessible in global search, popular catalog sync, browse, matching, chapters, reader and downloads regardless of extension flags. Source browse/search results hide only works classified by local catalog metadata or manual overrides; unknown works stay visible and no extra upstream lookup is made. The next request after a setting PATCH uses the new visibility in either direction, including warm caches. `GET /api/library/activity.hiddenAdult` counts followed titles hidden by the current setting (zero when enabled), so the interface can disclose them. Enabling the setting restores visibility; upstream search/discover caches are separated by the mode, while cached details and related lists are enriched at read time. Tracking rows, chapter observations, imports and automatic-download choices remain stored; worker updates and downloads continue for hidden titles.

## Search stream behavior

Initial AniList/MangaDex/MangaUpdates search requests have a 2500 ms deadline. Full MU novel-sheet hydration and Open Library calls use their separately documented bounds; a cold text search can therefore take longer. Repeated searches use a persistent SQLite cache per provider with a 30-second freshness TTL. Stale results return immediately while one background refresh runs; a provider failure retains its last successful results. Local FTS and tracked/Kavita presence are recomputed on every response. The UI should debounce, cancel stale searches and cache locally. Deep search runs a query per enabled source in preferred languages, with a 20-second deadline per active source call. Search, matching, browse and popular sync share a FIFO limit of six active source calls; queued time does not consume the upstream deadline. Matching can try up to three titles successively, each with that deadline. Both deep search and `/api/media/sources` start requests in preference priority order and stream results in completion order. Disconnect cancels source requests. Events:

```text
event: sources
data: {"sources":[...]}

event: source_result
data: {"source":{...},"results":[...],"titles":[...],"hasNextPage":false,"durationMs":120}

event: source_error
data: {"source":{...},"code":"SOURCE_HTTP_ERROR","detail":"HTTP error 503 [url]"}

event: done
data: {"completed":3}
```

`source_result.results[i]` corresponds to `titles[i]`. `done.completed` counts sources attempted, including failures; sync can emit multiple pages for each source. No sources is a legitimate empty sources event followed by `done` with zero. A setup/stream-wide failure emits `error` with `{code,message}`. Comment heartbeats occur every 15 seconds. `EventSource` automatically reconnects: **close it on done and on component cleanup**. Deep search is a finite operation; download status is continuous. For the POST sync stream use fetch + a real SSE parser; a chunk is not necessarily a full event.

Downloads emit `snapshot` with a `DownloadsSnapshot` and `error` with `{code,message}`. The local engine returns `status.state` STARTED or STOPPED, queue item states QUEUED, DOWNLOADING or ERROR, and `progress = pagesDone/pagesTotal` (0–1). No speed or ETA is fabricated. A queue error is not completion. Batches distinguish enqueuing/downloading/importing/scanning/completed/error. Both snapshots (including SSE) and `/api/downloads/batches` return the same persisted `chapters` and `scan` fields. `chapters` has at most 500 entries in queue order: `{id,number,name,sourceName,state,progress,error}`. Names come from Suwayomi, retained from chapter selection and refreshed before transfer; legacy/arbitrary IDs have empty labels and null numbers until metadata resolves. Chapter states are `queued`, `downloading`, `importing`, `done`, `error`; progress is 0–1 only during downloading, otherwise null. Errors are safe codes. A failed chapter does not stop later chapters. A batch is `error` only if no chapter could be imported; otherwise it is `completed`, with individual failed chapters retained. `scan` is null before an attempt, then `{state:"done"|"failed",error,at}`. A scan failure preserves successful imports and `completed` state. Worker imports/scans continue after the stream is closed.

Use `thumbnailUrl` and extension `iconUrl` exactly as returned: these are application-relative authenticated image-proxy URLs. A native image element or an unoptimized Next image carries the same-origin cookie; an unauthenticated server-side image optimizer cannot retrieve them. The proxy only permits `/api/v1/manga/<numeric-id>/thumbnail` and `/api/v1/extension/icon/<package>`, limits bytes and rejects active SVG/HTML. Unfollowed metadata covers/banners use provider URLs. Followed covers switch to the stable authenticated `/api/covers/<id>?v=<hash>` URL after storage.

## Tracking and imports

`GET /api/tracked` lists the signed-in tenant's library. `POST /api/tracked` creates a work in that private database with the requested status (default READING); repeated tracking retains its state and choices. `DELETE /api/tracked` removes that work, its stored cover and its local related state; files and batches remain. A linked Kavita dismissal prevents automatic re-import until an explicit follow. Another tenant's library is independent even when both follow the same provider identity.

Library classification follows the matched indexed Kavita series' library ID. If exactly one non-null `libraryTargets` entry targets that ID, `TrackedMedia.media.format` becomes that kind (MANGA, MANHWA, MANHUA, COMIC, LIGHT_NOVEL, WEB_NOVEL, NOVEL or BOOK), and both `media.type` and the tracked `type` become MANGA or NOVEL accordingly. Shared targets preserve the stored/provider classification. With no target for that ID, the indexed import mapping supplies the fallback (library name/type, EPUB/PDF and genre evidence); older index records without a kind retain the stored format. An unknown series or explicit unlink retains the stored/provider classification. This applies to Kavita-only and catalog-linked works, library filters and tracked items enriched into home/feed kinds. Catalog detail `/api/media` retains the provider format/type. The tenant's memoized snapshot recomputes after target settings, link or index changes without Kavita calls or rewriting provider metadata; newly auto-imported series follow the same rule.

`TrackRequest` accepts optional `status` (default `READING`), `autoDownload`, `kavitaSeriesId` and ordered `sources`. `TrackPatch` requires `id`, accepts the same state fields, and optionally accepts a validated `media:UnifiedMedia` to replace the catalog identity. Replacement clears sticky off-catalog state, adopts the submitted catalog title/cover/metadata/IDs and locks the retained Kavita link as a manual choice. It preserves reading status, ordered sources, download preference, import/update history, progress and Kavita linkage. Conflicting media/AniList/MangaDex identities return 409 `ALREADY_TRACKED` without mutation. Status is one of `PLANNING`, `READING`, `PAUSED`, `COMPLETED`, `DROPPED`; caught-up is derived by the frontend. `autoDownload=true` requires selected manga/novel sources and is rejected for anime. Source order is preserved and the first available variant is preferred during automatic MANGA checks.

`PATCH {id,displayTitle:string|null}` trims and validates 1–300 characters; null restores the catalog/Kavita title. The choice is tenant-local and survives metadata/index refresh and identity changes. `TrackedMedia.title` and `media.title` use it; `customTitle` is true while set. `titleOptions` deduplicates the catalog title, aliases and indexed Kavita names (including localized/original names). Catalog metadata retains its original title for matching. Library presence, media detail/search, home, releases/planning items with trackedId and newly created download batches use the display title. Existing Kavita folders (or folders proven by imported archive history) are reused exactly; changing a name never renames a folder.

Each `TrackedMedia` belongs entirely to the current tenant: dates, status/progress, identity, sources, matches, covers/backdrop, Kavita link, auto-download, chapter ownership/observations and releases. All `trackedId` / library flags, `library=1` filters, updates/counts, hidden-content activity and home state refer to that tenant's database.

Each `TrackedMedia` returns `status`, `progress`, `newChapters`, `lastReadAt`, `identity`, `sourceStatus` and `coverChoice`. `progress.owned` counts the union of distinct imported numeric chapter numbers and matched Kavita chapter numbers, including fractional numbers; duplicate source variants count once. `read` is null until a successful Kavita progress fetch, then the highest completely read numeric chapter (0 if none). A partially read chapter does not advance `read`. `unread` counts owned numbers above `read`, or all owned numbers when `read` is null. `released` is the maximum of catalog chapter count, every linked source’s latest numbered chapter, historical source observations, and the highest owned/indexed Kavita chapter number. Source statuses refresh in the worker, so plain `GET /api/tracked` includes current released counts without opening a title page. `newChapters` counts distinct observed numeric chapters absent from both the imported ledger and matched Kavita series. Unnumbered specials retain their upstream identity for download/detection but do not affect numeric counts. Imported archives are linked by media ID, AniList ID or MangaDex ID, including imports made before tracking.

Kavita progress refreshes on the worker update cycle and on `GET /api/tracked?refresh=progress`. The on-demand endpoint starts at most one refresh per user per two minutes, sharing a user-scoped attempt timestamp in SQLite across route instances/restarts. Concurrent requests share the same run, bounded to 15 seconds with up to four entries in flight. Later requests inside the two-minute window return the stored array immediately, including after a failed attempt. Failure preserves the last successful progress. `readSource` is `kavita` after a successful fetch, otherwise `none`; `lastReadAt` comes from the latest Kavita or built-in reader activity; refresh never lowers stored numeric read progress. A saved `kavitaSeriesId` is used directly. Otherwise the local Kavita index matches normalized title/aliases against series name, localized name, original name and sort name. If the index has no match, reading-progress refresh retains the legacy bounded folder/title lookup as a fallback. The resolved ID is saved. Supplying `kavitaSeriesId` in PATCH is a sticky manual choice: a positive indexed ID links that series, `null` explicitly marks the entry as absent from Kavita. Automatic title matching, progress fallback, chapter presence and ownership honor that choice on every later sync. Changing/clearing the link clears cached read progress until refreshed; replacing only `media` keeps it. API-key and JWT authentication modes use the tenant's Kavita key from settings for progress, indexing, scans and covers. Replacing the key clears saved progress and its refresh throttle; late results from a replaced key/URL are discarded. Worker and on-demand refresh affect only that tenant.

Enqueue requires a full `UnifiedMedia` so metadata survives a restart. Enqueue, tracking and identity-patch schemas accept HTTP(S) resource URLs without credentials, plus an exact allowlist of root-relative Bunko image routes: `/api/suwayomi/image?path=<approved encoded thumbnail/icon path>`, `/api/kavita/image?seriesId=<positive id>` and `/api/covers/<trackedId>?v=<16 lowercase hex chars>`. Local routes reject extra/duplicate parameters, traversal, fragments, backslashes and other origins; an arbitrary local path never qualifies. Media returned by detail, tracked, catalog/discovery and search can be sent back unchanged. Repeated tracking uses the existing row. Enqueue and same-identity media patches use the server's followed artwork; submitted cover/banner fields cannot replace it. Select a cover using `cover`, and use a different catalog identity to replace a wrong match. A slow patch rebases its state fields on the latest row; an intervening identity change returns 409 `CONCURRENT_EDIT`. The local worker calls Suwayomi `fetchChapterPages(input:{chapterId})`, downloads its authenticated proxy pages, and constructs an ordered CBZ with embedded `ComicInfo.xml`. It never enqueues Suwayomi downloads or changes Suwayomi download settings. One chapter transfers at a time, with three pages in parallel; each page has a 20-second deadline, a 20 MiB cap, supported raster image content types, and up to three attempts with 250/500 ms backoff. Chapters are capped at 2000 pages and 256 MiB total page bytes. An exclusive temporary file + fsync + exclusive hard-link publication precedes the transactional archive-pointer/import-ledger acknowledgement. An existing destination is preserved: only an identical embedded Bunko work/connection/chapter fingerprint allows crash recovery; otherwise the chapter reports `IMPORT_CONFLICT`. Page bytes share the bounded per-tenant image cache with the reader and persist across retries/restarts until LRU eviction; successful imports remove only obsolete legacy chapter-cache folders.

New folders are sanitized series titles with a stable `[bunko-<12 hex>]` work suffix and a SQLite ownership reservation. Work UUIDs survive identity/title changes and never reuse a deleted tracked row ID. A folder already reserved for another work returns `IMPORT_CONFLICT`, including a conflicting manual Kavita link. Filenames are `Series Title Ch. 0012.cbz`, `Series Title Ch. 0012.5.cbz`, `Series Title Vol. 03 Ch. 0012.cbz`, or `Series Title SP - chapter name.cbz`. A volume is taken from chapter metadata when supplied internally, or an explicit volume marker in the chapter name. Specials embed `<Format>Special</Format>` to force Kavita's special handling. If a matched Kavita series already has a folder inside the selected target/library, that exact folder is reused. Nothing moves old hash-suffixed folders or files. Scan-folder receives `{apiKey,folderPath}` in its JSON body, with the actual series folder mapped back into Kavita's namespace. Kavita authenticates this anonymous endpoint from the body, independently of headers. The key never enters batch JSON or logs. Non-admin denials map to `KAVITA_NOT_ADMIN`; other scan failures map to `KAVITA_SCAN_ERROR`.

Comic enqueue requires an effective library target; text enqueue returns 409 UNSUPPORTED_FORMAT. A previously configured target can still resolve while Kavita is offline; a scan failure leaves the batch retryable after Kavita returns. Retry reconciles the ledger and skips completed chapter imports, retaining partial page caches. The successful CBZ write plus ledger entry determines chapter completion, independently of Suwayomi `isDownloaded`.

## Sources and browsing

`GET /api/sources` returns every installed source matching `SourcePreferences.languages`, plus multilingual (`all`) sources, including disabled global-search favourites. `enabledSourceIds` is an ordered list of positive signed 64-bit **strings**. An empty list enables all matching sources in Suwayomi order. Disabled sources have `priority:null`; enabled priorities follow preference positions. `iconUrl` uses the existing authenticated image proxy and `extensionId` is the providing package when available. `GET /api/sources/preferences` reads preferences and `PUT` replaces both fields, for example:

```json
{ "enabledSourceIds": ["9223372036854775806", "9007199254740993"], "languages": ["fr", "en"] }
```

Global search and catalog sync use enabled sources; automatic matching uses every installed healthy source in the selected languages plus multilingual sources; browsing a disabled source remains possible. Source health persists the latest search/browse latency, checked timestamp, safe error code and optional sanitized `detail`: `slow` above 4000 ms, `ok` otherwise, `error` on failure and `unknown` before a call. GraphQL extension messages classify Cloudflare/challenge/CF 403 as `CLOUDFLARE`, HTTP/status errors as `SOURCE_HTTP_ERROR`, and login/authentication requirements as `SOURCE_LOGIN_REQUIRED`; other messages retain `SUWAYOMI_GRAPHQL_ERROR`. HTTP `cf-mitigated: challenge` is also recognized. SSE `source_error` and `SourceHealth.detail` expose the complete sanitized extension message without a server-side character cutoff; URLs, query strings, credentials/tokens and emails are removed. Upstream messages are never logged raw.

`GET /api/sources/[id]/filters` maps the pinned Suwayomi filter union to header, separator, select, text, checkbox, tristate, sort and group. Group children have positions relative to their group. Filters preserve defaults, including false, empty text and null sort selection. Nesting is bounded to eight group levels. The source must be installed in the selected languages; it need not be enabled.

`POST /api/sources/[id]/browse` takes an explicit positive page, mode `POPULAR`, `LATEST` or `SEARCH`, optional query (up to 200 chars) and optional filters. Each filter change has `position` and exactly one state field. A group change wraps its child, for example:

```json
{
  "mode": "SEARCH",
  "query": "Title",
  "page": 1,
  "filters": [{ "position": 7, "groupChange": { "position": 0, "triState": "INCLUDE" } }]
}
```

The backend sends `fetchSourceManga` with `source`, `type`, `page` and, in SEARCH mode only, `query`/`filters`, indexes results in FTS, and returns `{source,items,page,hasNextPage}`. Items include `trackedId` when the Suwayomi manga is selected by a tracked entry. Suwayomi applies filters to SEARCH; POPULAR/LATEST follow the upstream source's own listing behavior. Browse uses the same 20-second active-call deadline and six-call queue. Unsupported latest or extension failures use structured upstream errors.

## Updates and download controls

The durable worker refreshes **all tracked entries with selected sources**, including manual titles, using `updateIntervalMinutes`. First check treats currently discovered, unimported chapters as new. Observations prevent repeated entries on later checks/restarts. Detection groups prefer the first selected source for duplicate numbers, group by tracked series/source/check, and keep each detection group whole while splitting automatic batches at 500 chapters. Manual groups are `pending`; automatic groups persist a batch and become `queued`. The feed derives `downloading` from downloading/importing/scanning, `downloaded` only when every linked chapter succeeds, and `error` on any linked chapter failure (including partial batches). Retrying a batch updates the feed too. Partial manual enqueues leave remaining chapters pending after the selected chapters complete. Observations and automatic batch creation share a transaction.

`GET /api/updates` returns `{entries,lastCheckAt,nextCheckAt,checking,autoCount,trackedCount}`. Times are ISO strings or null before a first check; counts refer to MANGA entries with sources, and `autoCount` is their automatic subset. `checking` follows a live worker lease. `lastCheckAt` is the most recent check start; next time is that timestamp plus the configured interval. Per-source failures preserve partial results and retry on the next cycle. A check has a separate 45-second background matching budget, a two-minute linked-source deadline, a 15-second progress budget and a 60-second cover budget; oldest source checks run first. Incomplete source work keeps the check requested; unfinished work requests another cycle. `POST /api/updates/check` persists a request and returns 202 immediately; repeated requests during an active check do not start duplicate work. Restart retries an interrupted check after acquiring the worker lease. Processing existing batches may delay a requested or scheduled check.

For a pending entry, find its `TrackedMedia` using `trackedId`, POST its ordered selections as `{sources:[...]}` to `/api/manga/chapters`, choose variants whose numbers appear in `entry.chapters`, then POST `{chapterIds,media:tracked.media}` to `/api/downloads/enqueue`. Existing update groups link to manual batches (including alternate source variants with the same observed number). No extra enqueue endpoint is required. Unnumbered specials are available through the chapter table; the feed's numeric `chapters` array omits them.

`POST /api/downloads/control` returns the local `DownloadStatus` and accepts:

- `{"action":"pause"}` / `{"action":"resume"}`: interrupt active transfers and persist STOPPED, or continue from cached pages.
- `{"action":"clear"}`: interrupt transfers and empty the local queue. Remaining chapters receive `error:"CANCELLED"`; batches with imported chapters remain `completed`, otherwise `error`. The paused/running preference is preserved.
- `{"action":"retry_failed","batchId":"<uuid>"}`: requeue only failed chapters of a batch. Omit `batchId` to retry failures across all batches. During an active transfer, the selected failed IDs are persisted and requeued after its current work finishes; later failures require another retry. Successful chapters and their archives are retained; no failed chapters is a no-op.
- `{"action":"remove","batchId":"<uuid>"}`: drop a finished batch from history, or cancel an active batch's remaining chapters. Written archives, imported ledger rows and cached pages are retained. Other batches continue.

A batch belongs to the Suwayomi connection on which it was created. Internal connection fingerprints are never returned in batch JSON. A server/credential change prevents its execution/retry on the replacement connection (`SOURCE_CHANGED`). Changing the Suwayomi URL detaches previous numeric source selections and clears their local catalog/health so they can be matched again; followed works, files and import history remain. Enqueue recognizes imported chapters by connection and work identity, rather than by chapter ID alone. A same-connection chapter ID already imported for a different work fails with `SOURCE_CHANGED` before transfer; its previous history is preserved. Historical files remain available through the owned-number local reader.

Unknown batch IDs return 404. Malformed IDs/actions return 400. Durable global and per-batch cancellation generations coordinate distinct Next module instances. `POST /api/downloads/batches {id,action:"retry"}` also supports a completed batch with failed chapters or a failed scan; a scan-only retry makes no chapter requests. EPUB conversion and AniList login remain outside this API.

## Kavita index and catalog presence

The worker checks the Kavita index approximately every fifteen minutes, using paginated `Series/all-v2`. A lightweight listing detects new/removed series and compares returned update fields (lastModified/lastModifiedUtc/updatedAt, lastChapterAdded/lastChapterAddedUtc and lastFolderScanned), identity, library and reading fields. Only changed/new series reload `Series/metadata` and `Series/volumes`, at two series in flight. Missing update fields fall back to reloading that series. Once a day, or after connection changes, all series reload. The complete successful listing commits additions, changes and deletions atomically. `POST /api/kavita/sync` records a durable request and directly awaits the refresh (or the current tenant's in-flight refresh), independently of the worker lease, update interval and retry throttle. It still reuses unchanged series metadata. The existing Settings button's status revalidation therefore runs after completion, with the completed `syncedAt` and count; failures return 502 and the refreshed status shows `error`. Failed refreshes preserve the previous complete snapshot and back off background retries for 60 seconds; a new manual request retries immediately. `syncedAt` is the last successful refresh; `unconfigured` means URL/key are absent. An accepted folder scan is asynchronous inside Kavita, so newly scanned content can appear on a later index refresh.

`GET /api/kavita/libraries` uses Kavita's folders, reports their mapped `localPath` or null, and probes writeability with an exclusive temporary file immediately removed. Unmounted or inaccessible folders are not writable; no directories are created by this probe.

`UnifiedMedia.kavita` is null or `{seriesId,libraryId,libraryName,chapters,url}`. Its chapter count is the distinct numeric chapter count; specials and volume-only sentinel entries do not invent chapter numbers. Numeric ranges expand to distinct numbers (bounded to 2000 increments). A saved tracked `kavitaSeriesId` wins; otherwise only a single normalized-title/alias match qualifies. Search (including cached results), discovery, media detail, relations, recommendations and tracked media use the local index. `url` is `${kavitaUrl}/library/${libraryId}/series/${seriesId}`. Submitted media accepts omitted or nullable `kavita`, default null; client presence does not override authoritative tracked linkage.

`GET /api/kavita/series?q=name` searches indexed names/aliases (case/diacritic insensitive, maximum 200 characters); it can combine with `unmatched=1` to omit series linked explicitly or unambiguously by title to a tracked entry. Covers always use `/api/kavita/image?seriesId=...`; authentication stays server-side (the upstream URL includes `apiKey` as required by stable v0.9.x, along with the configured API-key/JWT headers; develop also accepts this URL), redirects and active content types are refused, and transfer time/size are bounded.

`POST /api/kavita/track` directly follows COMIC-library series as `kavita:<id>` with format COMIC, since no public comics catalog is available. For other kinds it searches the catalog using up to four indexed names, excludes anime, and requires a best match scoring at least 0.85 with a margin of at least 0.10 over the next identity. It creates or links the catalog entry with `kavitaSeriesId` set. An explicit follow initializes READING and preserves an existing status. Automatic import initializes COMPLETED when all indexed chapters are read in that tenant’s Kavita, otherwise READING. Repeating an explicit link returns it. No match, ambiguous identity or an existing conflicting link returns 409 `NO_MATCH` without tracking changes; an unknown index ID returns 404.

After each successful sync, `autoImportKavita=true` runs the same unique catalog matching for unlinked series. Without an unambiguous catalog match, or when that identity has a conflicting/manual link, it follows a `kavita:<seriesId>` media (`providers:["kavita"]`), using the indexed title/aliases, summary, genres, library-derived format and `/api/kavita/image?seriesId=...` cover. `GET /api/media?id=kavita:<id>` returns `MediaDetail` with empty tags/relations/recommendations; unknown indexed IDs return 404. These identities are accepted for tracking, chapters and source matching, which uses their titles. Imports are idempotent and preserve existing user status, sources and manual links. DELETE tracking remembers a linked series dismissal durably, preventing automatic re-import; explicit track-from-Kavita can add it again.

For catalog-linked entries with a reachable writable series folder and no `cover.*`/`folder.*` raster image (case insensitive), Bunko downloads the catalog cover from its restricted HTTPS provider allowlist (15 MiB / 15 seconds, redirects refused). It atomically writes an exclusive `cover.jpg`, preserving existing covers. **Kavita does not use a series-folder sidecar as its custom series cover**: Bunko also calls `POST /api/Upload/series` with `{id,url:"data:image/...;base64,...",lockCover:true}`, then requests `Library/scan-folder` using the original Kavita series path. Pending upload/scan state survives retries; an edited sidecar cancels the pending upload. This initial missing-cover bootstrap preserves existing files; subsequent tracked cover synchronization follows the selected/automatic cover as described below. See [Kavita's cover selection explanation](https://github.com/Kareadita/Kavita/discussions/2717) and [UploadController](https://github.com/Kareadita/Kavita/blob/develop/Kavita.Server/Controllers/UploadController.cs).

## Off-catalog identities, background sources and cover selection

Every `TrackedMedia` includes `backdrop: "auto" | "hidden"`, persisted per tracked entry. Existing entries migrate to `"auto"`, and newly tracked entries default to it. `PATCH /api/tracked {id,backdrop:"hidden"}` hides the catalog banner; `backdrop:"auto"` restores automatic display. Other values (including null) return 400 `VALIDATION_ERROR` without mutation. Unrelated patches preserve the saved choice. A successful `media` or `offCatalog:true` patch resets it to `"auto"`, even if the same request supplies `backdrop:"hidden"`, so a replacement work can show its banner. Off-catalog banners remain hidden by the interface regardless of this preference.

`PATCH /api/tracked {id,offCatalog:true}` removes the catalog identifiers and metadata. With a linked indexed Kavita series it becomes `kavita:<seriesId>` using that series’s title, aliases, summary, genres and cover. Otherwise it becomes `suwayomi:<first linked mangaId>` using the source’s title, metadata and proxied thumbnail. Without either identity it returns 409 `NO_IDENTITY` without mutation. The row, reading state, history and sources stay attached. `identity` is `catalog` or `off-catalog`; a detachment is persistent and automatic Kavita import/matching retains it. An explicit later `media` patch can select a catalog work again. `media` and `offCatalog` cannot be combined.

The worker wakes immediately on local enqueue, retry/resume, update/index requests, tracking and identity edits. Otherwise it sleeps for `BUNKO_WORKER_IDLE_MS` (default 30000, clamped 1000–300000). One scheduler per process/volume serves all route bundles and iterates tenants with at most two ticks active; every tick, lease, transfer control and wake is tenant-scoped, and empty unconfigured tenants skip integration work; other processes observe durable requests on their next idle wake. Active work renews its 90-second SQLite lease every ten seconds; idle work has no heartbeat timer. The worker continuously drains a queue of source-less MANGA entries independently of the update interval, one entry at a time with a 250 ms pause, yielding after two entries per tenant tick. Never-searched entries come first, then the oldest search. A search without a confident result is retried after seven days; PATCH changes to media, off-catalog identity or Kavita linkage requeue it immediately. All installed healthy sources in the tenant’s selected source languages, plus `all` (multilingual) sources (independent of global-search favourites) are searched in parallel through the same shared six-call gate as interactive searches, using the interactive title scorer. Both background selection and `/api/media/sources` SSE rank by descending score, then descending `chapterCount`, then source preference for equal values. Only confident candidates (score ≥ 0.9) trigger a minimal `fetchChapters { chapters { id } }` count probe behind the common six-call source gate. Counts are cached for ten minutes in the bounded metadata cache; failed/unknown counts are null and sort after known counts. SSE returns at most three candidates per source; automatic matching links at most three sources. Both paths deduplicate source ID + manga ID and identical normalized titles across language variants of the same extension, keeping the first selected language even when another variant is faster or has more chapters. Distinct extensions and distinct titles remain separate. There is one SSE lane per eligible unique source ID; duplicate-title lanes complete with no candidates. Sibling variants resolve in language preference order while independent extensions continue streaming. Cancellation or loss of the worker lease discards unfinished matching results and leaves them retryable. Background sources in error back off for one minute; interactive requests always re-test. Only candidates scoring at least 0.9 qualify; the best eligible candidate per source is selected, up to three sources per entry. Automatically linked statuses have `auto:true`. `PATCH {id,sources:[...]}` makes retained/new links manual (`auto:false`) and persists every removed source+manga pair as dismissed. Automatic matching never restores those pairs; a user can explicitly select them again. Concurrent user source/identity edits take precedence over an in-flight match.

`sourceMatch` is `linked` when sources exist, `searching` for the entry currently being processed under a live worker lease, `queued` when due, and `not-found` after a search without confident matches. `GET /api/library/activity` is authenticated and uses SQLite/settings only, with no upstream requests. It returns `{matching:{queued,current},refresh:{running,done,total,lastAt,nextAt}}`. `queued` excludes the current entry; `current` is its title or null. Refresh counts cover linked entries attempted in the current/latest update cycle; `lastAt` is that cycle's start and `nextAt` adds the configured interval. `running` and current matching require a live worker lease, so a crashed worker does not remain visibly active.

`sourceStatus` follows the order of `sources`, with `sourceId`, `suwayomiMangaId`, source title, proxied `thumbnailUrl`, `latestChapter`, `chapterCount`, `checkedAt`, `auto` and safe `error` code. The update cycle refreshes chapter and manga metadata for linked entries regardless of automatic downloads. Failures keep the last successful values with an error code; behind sources remain linked and never lower the released maximum. Initial statuses are persisted on tracking/manual selection, before the first background check. An automatic source link immediately refreshes chapter numbers, source titles and thumbnails, without waiting for an update cycle.

`GET /api/tracked/covers?id=<trackedId>` lists the matched catalog cover, up to 20 MangaDex volume covers when a MangaDex ID is known (cached for 24 hours), linked source thumbnails via `/api/suwayomi/image`, and the linked Kavita cover via `/api/kavita/image`. Options carry `{origin,id,label,url}`; stable IDs are catalog media IDs, `mangadex:<coverId>`, `<sourceId>:<mangaId>` or the Kavita series ID. A MangaDex failure keeps local options and cached volume options usable. Unknown tracked IDs return 404.

`PATCH {id,cover:"auto"}` tries catalog cover, then linked source thumbnails in order, then Kavita. A successful candidate is downloaded and retained by Bunko, independently of later upstream failures. `PATCH {id,cover:{origin,id}}` selects one returned option. A source choice may name any live Suwayomi manga, including an unlinked scan result: `{origin:"source",id:"<sourceId>:<mangaId>"}`. The server verifies that the manga belongs to the source. Unknown manga/wrong source returns 404 `NOT_FOUND`; unavailable catalog/Kavita choices return 400 `INVALID_COVER`. PATCH returns the complete updated `TrackedMedia`. Apply identity replacement before selecting a cover in a separate patch. Explicit cover selection (including selecting the same option again) fetches replacement bytes. Identity/link context changes resolve again; ordinary source metadata refreshes keep stored bytes. Matching search/discover/detail results reuse the followed cover through exact catalog IDs or a unique linked source/Kavita identity.

The first successfully fetched cover is atomically stored as `<data>/users/<id>/covers/<trackedId>-<16-char SHA-256>.<ext>` (JPEG/PNG/WebP/GIF/AVIF, maximum 15 MiB). Both `TrackedMedia.coverUrl` and its `media.coverUrl` become `/api/covers/<trackedId>?v=<hash>`; home, detail, search and discovery use the same URL. `coverFallbacks` is empty after storage and for manual choices; before storage it lists remaining automatic candidates. A failed full resolution returns `coverUrl:null` and retries later. Background backfill processes one entry at a time within the 60-second cover budget; idle backfill retries missing covers at most every five minutes. Explicit choices bypass that backoff. Replacement publishes a complete new file/pointer, deletes the previous file and changes `v` when bytes change. Untracking removes the stored file. Stored covers are independent of the bounded/evictable upstream proxy cache.

`GET /api/covers/<id>?v=<hash>` requires normal authentication, returns raster bytes with `Cache-Control: private, max-age=31536000, immutable`, an ETag derived from the stored hash, and bodyless 304 for matching `If-None-Match`. Unknown IDs/versions return 404. Omitting `v` resolves the current file with `private, max-age=0, must-revalidate`. Hits stream from disk without contacting upstream or re-hashing the image. Each entry exposes persisted `kavitaCover:{state,error}`. It is `none` without a matched Kavita series or usable cover, `pending` for a queued/current replacement, `synced` after its stored hash has been synchronized and the folder scan accepted, or `failed` with a safe code. A new choice/hash/link resets it to pending. Explicit cover patches wake the worker and attempt synchronization immediately; a retained local cover does not suppress failed push retries. The state is scoped to entry, cover context/hash and series and survives restarts. Scan failure retries use the already uploaded hash without sending the bytes again.

The worker synchronizes these same stored bytes to Kavita using `Upload/series` and `lockCover:true`, even without a local library mount. A durable hash suppresses unchanged uploads; a failed upload retries from local bytes. Kavita-origin bytes are never uploaded back to the same reader. Mounted writable series folders receive an atomic `cover.jpg`. Successful uploads are followed by a folder scan in Kavita’s original namespace when the indexed folder is known. Source/Kavita credentials remain server-side, transfers are bounded and reject redirects, and catalog hosts remain allowlisted.

`libraryTargets` distinguishes omitted kinds (one unambiguous matching suggestion may be used), `{libraryId,folder}` (explicit selection), and `null` (explicitly no target). Null disables suggestions and fallback for that kind; downloads return 409 `TARGET_NOT_CONFIGURED` before jobs are persisted. A missing MANHWA/MANHUA target never uses a Manga library. Stored older broad suggestions are reclassified from the library name/type before target selection.

## Persistent server caches

Derived library, releases and planning snapshots are keyed by tenant ID and that database’s durable write versions; progress coalescing/throttling also includes the tenant directory. Settings, key and library writes affect only that tenant. Provider metadata, release ingestion and private images are conservatively stored per tenant too; library flags are enriched at response time. Transaction-local snapshots are never retained after rollback.

Private image and retained-cover responses vary on `Cookie` and `Authorization`, including 304 responses. A browser changing accounts cannot reuse one tenant’s cached private image for another tenant at the same proxy URL.

Both `/api/kavita/image` and `/api/suwayomi/image` (including extension icons) persist complete raster bytes and content type under `<data>/users/<id>/cache/images/`. Keys incorporate the configured upstream/authentication identity and are SHA-256 filenames; the client cannot supply a disk path. The cache is limited to 500 MiB with least-recent-access eviction. Writes use an exclusive temporary file, fsync and atomic rename. Kavita covers retain the 15 MiB transfer cap, Suwayomi thumbnails/icons 10 MiB; both have a 15-second deadline and reject redirects/active content.

Images return a strong SHA-256 `ETag`, `Cache-Control: private, max-age=86400, stale-while-revalidate=604800` and bodyless 304 for a matching `If-None-Match`. Disk hits stream the image payload without re-hashing it; the strong hash is saved on publication. Legacy cache entries compute that hash once per process until refreshed. Disk hits require no upstream request. After one day, the cached bytes return immediately and a coalesced background fetch attempts revalidation, at most daily even on failure. Failed fetches keep the old copy beyond its freshness period. Successful Bunko cover uploads invalidate the matching Kavita proxy entry, including obsolete in-flight writes; unchanged byte hashes do not upload again.

Catalog metadata, discovery pages, genres, MangaDex volume options and per-provider search results share a bounded SQLite cache (1,000 values / 64 MiB, maximum 8 MiB per value; oldest refreshed values pruned). Freshness TTLs are 30 seconds for search, ten minutes for discovery, 30 minutes for details and 24 hours for genres/volume options. Stored values return immediately after expiry while one background refresh runs. Failed refreshes retain them, with a 30-second retry floor (or TTL when shorter); only a cold lookup needs a successful upstream response. These server caches do not change JSON responses' `Cache-Control: no-store`.

`GET /api/media?id=...` for a followed catalog, linked-source or Kavita identity returns the persisted tracked media immediately, with cached detail extras when available and empty extras otherwise. Background catalog/detail refreshes update `tracked_media` without blocking the request or overwriting an intervening identity edit. Reading state, source links and validated cover resolution remain attached. Suwayomi detail keys are scoped to the configured upstream credentials. No Kitsu integration currently exists.

`GET /api/status` includes `kavita:{state,admin}`. `admin` is true/false only when roles in a plugin-authentication JWT returned by the configured Kavita server establish the key's role; it is null when configuration/authentication/roles are unknown. The boolean result is cached for about ten minutes, scoped by a hash of URL/key; changing either forces a new probe. Tokens and keys are never exposed or persisted in that cache. A known non-admin key gates `Upload/series` before upload with `KAVITA_NOT_ADMIN`; an upstream 403 maps to the same code. Unknown roles allow the authenticated upstream request to decide. Other cover upload failures use `KAVITA_COVER_ERROR` or a safe transport code.

### Opt-in live release verification

Normal tests use isolated storage and local fixtures. After building an image, run `scripts/container-releases-live.sh bunko:your-image` to exercise the real public APIs in a fresh read-only container with disposable tmpfs storage (default deadline 1,000 seconds; override `LIVE_TIMEOUT`). The script reports first response/first MangaUpdates persistence/completion latency, raw SQLite counts and fully paged API counts by provider and kind, content filter behavior, timestamps, novel/home availability and planning. A `refreshFailed:true` result and the sanitized warning disclose partial upstream failures while the script still verifies the successfully persisted feed. It removes the container on exit and never prints the generated token. This is separate from the fixture-only suite and `scripts/container-smoke.sh`.

### NAS regression and performance checks

`scripts/container-l3-regression.sh <image>` seeds disposable NSFW-source/followed fixtures and verifies HTTP PATCH/GET visibility off → on → off → on for tracked, discovery, full/quick search (the same `/api/search` used by the header), releases, home, planning, updates and `hiddenAdult`. It also verifies source upload-date provenance against a warmed feed/planning. The optional second argument `before` reports old-image behavior without asserting corrected counts.

`scripts/container-feed-profile.sh <image>` measures complete local HTTP/JSON round trips against 30,000 stored releases, 100 followed titles and 5,000 observations, with twelve warm samples per route and cursor page. No external metadata or existing user data is used. `scripts/container-home-live.sh <image>` separately calls real public AniList: top ten, unfiltered discovery, and a banner-less provider-only hero resolved by its exact catalog title. Both scripts use throwaway read-only containers/tmpfs and remove them on exit. Unit performance coverage also guards against reparsing the entire release store after a library-only write.

## Built-in reader and volumes

All three reader routes require authentication and use the signed-in tenant's Suwayomi connection, import ledger, media root, cache and progress. `GET /api/reader/chapter?id=10&media=anilist:123` resolves Suwayomi metadata and `fetchChapterPages`, without downloading images. Pages are application URLs `/api/reader/page?chapter=10&index=0`; source credentials and raw upstream page URLs never reach the browser. Numeric neighbours come from the same source manga, exclude equal-number variants and specials, and are null at the ends. Locally imported chapters use the retained source chapter inventory (up to 20,000 entries) and known local imports, so offline local reading remains available.

Direction is `vertical` for MANHWA/MANHUA or webtoon genres, `rtl` for MANGA/ONE_SHOT and `ltr` for COMIC. Supplying `media` uses that work's format; a tracked linked work or known source vocabulary supplies the fallback. `resumePage` is the saved zero-based page for that specific work/chapter, clamped to the current length; `TrackedMedia.readerPosition` is its most recently saved chapter position.

The page endpoint fetches only the requested image through Suwayomi's authenticated proxy. A Bunko-imported CBZ takes priority over the network, including older ledger-only imports with unambiguous Kavita filenames. Local reads stay inside the tenant's resolved mount and reject symlink escapes. ZIP central-directory and requested-entry reads use async IO; only that page is inflated, with a 20 MiB page limit. Page index beyond the chapter returns 404. Reader/download page transfers share three slots per tenant and a 20-second active-transfer deadline. Cache files are private 0600 files, shared with cover proxies under a 500 MiB per-tenant LRU budget; crossing the threshold schedules batched asynchronous pruning to 450 MiB. Eviction may briefly lag active writes. Hits stream from disk with `Vary: Cookie, Authorization`, strong SHA-256 ETag/304 and `Cache-Control: private, max-age=86400, stale-while-revalidate=604800`.

`PUT /api/reader/progress` accepts `{mediaId,chapterId,number,page,pageCount}`. Unfollowed works can retain a position without being auto-tracked. A source work's `suwayomi:<mangaId>` must match the chapter; an existing followed entry must be linked to that source manga (or have its own matching source identity). Known provider aliases resolve to the followed work's canonical ID. The server verifies the chapter number and actual page count; malformed/out-of-range input returns 400, an unrelated source/linked entry 404. First writes persist immediately, intermediate updates coalesce for at most one second, and the last page flushes immediately. Repeated identical updates within the interval do not write again. A pending intermediate position can be lost on abrupt process termination. Finishing a numbered chapter raises `progress.read` only when higher; neither finishing an earlier chapter nor refreshing Kavita can lower existing progress. Specials retain their position without advancing numeric progress. The contract's `readSource` remains `kavita|none`; reader-only progress uses `none`.

`ChapterVariant.volume` uses a finite nonnegative source field when available, otherwise names matching Vol./Volume/Tome/巻; pinned Suwayomi currently supplies volumes through names. `MergedChapter.volume` takes the first known variant volume. Imports use the same parser for `<Volume>` and `Series Vol. 03 Ch. 0012.cbz`; chapter-only and special filenames remain compatible. COMIC archives write `<Manga>No</Manga>`.

### Matching source coverage

`GET /api/media/sources` and background matching use every installed source exposed by the tenant's Suwayomi connection in the selected source languages, plus multilingual (`all`) sources once, independently of global-search enabled IDs/favourites. The content filter applies to matched works, never to source flags; interactive matching always re-tests sources on demand, including slow/error sources; only background matching skips an error measured within the last minute. Slow/error states expire to unknown after one minute. Selected language order comes first, then favourite priority and upstream installation order; the stream announces the whole eligible list and emits a lane result/error for each, with done.completed equal to that list's size. A process-wide gate per normalized Suwayomi base URL allows six calls total, at most four from background tasks, reserves capacity and queue priority for interactive calls, and rotates background tenant lanes. Cancellation removes queued calls; queue wait is excluded from health latency and upstream deadlines. Searches have a 20-second active-call timeout. Normal matching returns at most three candidates per source; background linking retains at most three best sources. Global search/stream/popular sync keep using preferences/favourites. Global-search `enabled` is a search preference, not an extension installation switch. Identical source ID + manga ID candidates appear once; identical normalized titles across language variants of an extension retain the first selected language. When no source preference exists, the first preference access initializes it from the first supported `Accept-Language` language plus English (English once), or English without a request/browser hint. This fallback matches automatic browser UI detection; a manual UI-language override is currently browser-local and is not sent to the backend. Saved source preferences always win.

Kavita import honors explicit library kinds/names (LightNovel → LIGHT_NOVEL, WN/web novel → WEB_NOVEL, Book → NOVEL by default). EPUB/PDF series in generic Manga libraries are treated as NOVEL; factual/non-fiction genres on a generic Book/NOVEL series select BOOK. Manual catalog matches and explicit Kavita links/unlinks take precedence over later automatic imports, progress lookup and index sync.

Persisted metadata/response cache records are schema-versioned; incompatible records are cold misses. Older home feeds are normalized when read: `hero` and `top` are always arrays, and `latest` always contains arrays for manga, manhwa, manhua, comic, lightnovel, webnovel, novel and book. Local CBZ reader pages validate the chosen root before serving even warm cached bytes; page identities include archive path, device/inode and size/mtime.

For a bounded live sample without waiting for the existing full MangaUpdates backfill, run `LIVE_SAMPLE_SECONDS=30 scripts/container-releases-live.sh <image>`. Counts are a sample and `refreshComplete:false` explicitly marks the continuing refresh; status diagnostics still report Google Books/BnF/Royal Road independently. The default waits for refresh completion.

## Optional catalogs

Administrators manage the instance-wide optional catalog configuration through `PATCH /api/settings`: `googleBooksApiKey`, `metronApiToken`, `metronUsername`, `metronPassword`, `rakutenApplicationId`, `rakutenAccessKey`, `hardcoverToken`. These fields live in `accounts.db`; service connections, preferences and results caches remain tenant-local. Members receive 403 `FORBIDDEN` for any catalog field, including an empty-string clear or a patch mixed with personal fields, before any settings change. Secrets use AES-256-GCM like existing integration credentials. Responses omit secret values, expose `secretsConfigured` and `catalogs` availability, and return an empty `metronUsername` for members. Admins may read the non-secret Metron username. Empty strings disable a credential. Unknown fields, control characters, oversized values and malformed field types are rejected.

Upgrade copies only the oldest current administrator's catalog rows, retaining encrypted bytes and legacy private rows. An immediate accounts transaction serializes migration and existing shared entries win. No member or second-admin configuration is merged. The migration marker prevents later reads/restarts/clears from reviving old account keys. Shared writes advance a durable revision, invalidating warm settings across accounts/route bundles/processes. Each account refreshes publication feeds on its next request after a revision change, without waiting for the normal twenty-minute interval. Provider results remain private and credential-fingerprinted; removing keys does not erase previously cached public metadata or personal works.

`POST /api/settings/test-provider {provider}` accepts `googlebooks|metron|rakuten|hardcover`, requires admin plus the normal authentication/origin checks, and returns `{ok:true,provider}`. Members receive 403 before any upstream call. It makes at most one small cached query with the saved credentials; save edited fields before testing. Errors use the normal `{error:{code,message}}` envelope and never include upstream bodies or credentials: `PROVIDER_UNCONFIGURED` (409), `PROVIDER_AUTH_FAILED`, `PROVIDER_UNAVAILABLE`, `PROVIDER_INVALID_RESPONSE`, `PROVIDER_QUERY_FAILED`, or `RATE_LIMITED` (502). An incomplete Rakuten configuration returns `PROVIDER_ACCESS_KEY_REQUIRED` (409).

- Google Books: a configured key is attached server-side to the existing six edition lanes and detail requests. Keyed lanes request up to forty volumes, refresh hourly and use a 250 ms pacing interval; keyless lanes retain their six-hour cache and slower pacing. Cache identifiers never include the key.
- Metron: [documented Bearer token or Basic authentication](https://github.com/Metron-Project/metron/blob/master/api/README.md#authentication). `metronApiToken` works alone and takes priority over a complete legacy username/password pair. Rejected tokens never fall back silently; clear the token explicitly to use Basic. Request/search/probe cache fingerprints use the active mode and credentials, so replacing a token cannot reuse the previous token's probe. `GET /api/discover?kind=comic` lists series, `sort=new` restricts to series launched this year (or the requested year); other sorts retain provider catalog order because no popularity ranking is documented. Search uses `q` across primary and alternative series names. Series responses have no cover field: cards use `/api/metron/cover?seriesId=...`, resolving a matching issue image on demand from the first issue page. The protected route redirects only to HTTPS Metron artwork hosts, never forwards credentials, and shares the seven-day, credential-scoped issue cache with details. At most two cover lookups enter the paced provider queue; offscreen cards retain lazy loading. Previously cached/tracked series with null artwork are repaired when projected to catalog/search results. `GET /api/media?id=metron:<series-id>` adds description, years, issue count, first available issue cover and publisher/year tags. Weekly issue ingestion uses `store_date_range_after/before` from seven days ago to seven days ahead, up to ten pages. Store dates populate `/api/releases`, home `latest.comic` and planning; future store dates appear as expected. Single issues use `unit:chapter` and `#<number>`; collected editions use `unit:volume`. No release day is inferred from cover dates.
- Hardcover: [backend-only GraphQL access](https://docs.hardcover.app/api/getting-started/) with Bearer authorization; public books only, read operations only. Novel/book discovery supplements Open Library; search uses the documented full-text search operation. `hardcover:<book-id>` details include series positions and edition release dates as tags. Genre-based fiction/nonfiction classification is best effort. Pattern operators disabled by Hardcover are never used. The documentation limits access to 60 requests/minute and requires keeping tokens server-side; policy pages currently render no readable terms body, so this is not a claim of broader commercial permission.
- Rakuten: [current Books API](https://webservice.rakuten.co.jp/documentation/books-book-search) requires `rakutenAccessKey` **in addition** to `rakutenApplicationId`; both are configurable shared secrets. The adapter/fixtures support the current endpoint, Books genres `001017` (LN) and `001001` (manga), `sort=-releaseDate`, volume releases and Japanese `salesDate` precision. Approximate dates remain metadata only; only exact valid days enter planning/releases. Releases are marked `Japon / Japan` with the publisher. Ingestion requires both credentials; no obsolete application-ID-only endpoint is attempted.

All optional provider requests are serialized per provider across route bundles/accounts, use bounded responses and deadlines, tenant-local credential-fingerprinted caches, durable failed-attempt cooldowns and shared Retry-After/rate-limit budgets. Tests use documented response fixtures exclusively. Live verification covers keyless paths only.

### Local ownership, scan refresh and source diagnostics

- A successful download scan immediately polls/upserts its Kavita series, by known ID or an exact scanned-folder match for a newly created series. Polling has six attempts and a ten-second total deadline. Imported chapter/volume numbers bound success; delayed indexing schedules a durable retry. `/api/tracked`, media presence and chapter ownership read the new snapshot immediately; manual Kavita links/unlinks win over automatic linkage.
- `POST /api/manga/chapters {sources,mediaId}` accepts an empty `sources` list when `mediaId` is supplied. `inKavita` contains the owned numeric union of the Kavita index and imported ledger. Numbers absent from source responses appear as `{key,number,volume,localOnly:true,variants:[]}`. `volume` is null when unknown.
- `GET /api/reader/chapter?local=2.5&media=anilist:123` reads an owned CBZ for the work. Followed works, indexed `kavita:<id>` identities and imported ledger identities work offline; reading an unfollowed work does not follow it. Local and source selectors are mutually exclusive. It returns `local`, `prevLocal`/`nextLocal` (all neighbouring owned numbers), null source neighbours, and a stable negative `chapterId`. Send that returned ID unchanged in `PUT /api/reader/progress`; page URLs already address its tenant-local archive. `GET /api/reader/chapter?id=<negative ID>&media=...` can resume the same saved local identity. Source IDs remain positive. Missing/unrelated work, unavailable/ambiguous archive or unsafe path returns 404. Current root validation precedes warm page-cache access. No source access is needed for local reading/progress.
- `GET /api/media/sources?id=<mediaId>&q=<query>` uses only the given query on every matching installed source (selected languages), including sources with slow/error health. `q` is trimmed and must contain 1–200 characters without control characters. Candidates retain scores against the work's original/alternate titles and include all returned hits, even zero-score hits, ordered by score and chapter count within each source lane. Omit `q` for normal title matching and thresholds.
- `PATCH /api/tracked {id,kavitaCoverSync:false}` disables cover uploads/sidecar writes for that series and returns `kavitaCover.state:none`. Existing/new entries default to true. Switching back to true promptly pushes the current cover and retries failures through the worker. Bunko's own cover selection/cache remains usable while pushes are disabled.
- Source browse follows Suwayomi-WebUI's `FetchSourceMangaInput`: one-based `page`, string `source`, explicit `POPULAR`/`LATEST` without search fields, or `SEARCH` with `query` and a filter-change array. Nested filters use `groupChange`, preserving the extension's positional indices. Both clients use GraphQL, so the server's existing extension preferences/cookies apply; Bunko does not replace those preferences, add undocumented query flags or fall back to REST. Comparison: [official RequestManager](https://github.com/Suwayomi/Suwayomi-WebUI/blob/master/src/lib/requests/RequestManager.ts), [filter mapping](https://github.com/Suwayomi/Suwayomi-WebUI/blob/master/src/features/source/browse/screens/SourceMangas.tsx).
- `SourceHealth.detail`, source SSE errors and HTTP `{error:{code,message,detail}}` expose complete sanitized extension messages, without a server-side character cutoff. Credentials, URLs, email addresses, query strings and token-like material are removed; sensitive assignments conservatively redact their remaining text. Details are never logged. Fixtures also include two unmodified error payloads captured from a disposable Suwayomi v2.4.2366 instance (missing source and invalid filter input), plus the real Cloudflare-disabled message from [Suwayomi-Server #2181](https://github.com/Suwayomi/Suwayomi-Server/issues/2181) in a reconstructed graphql-java envelope. This is protocol/diagnostic coverage, not a claim that every third-party extension works: the reported private extension failure still needs acceptance against its actual full message.
