# Architecture

Bunko is a long-running Node 22 Next.js App Router service. All route handlers run in the Node runtime, dynamically, with private JSON responses marked no-store and a persistent private image cache. The root page renders a French React interface with a server layout, locally bundled Geist font, Tailwind CSS and Radix dialogs/tabs. `src/lib/client/api.ts` is the browser adapter over the shared contract; server integrations never enter the client bundle. Authentication gates the views, signed HttpOnly cookies authenticate SSE, and logout/expiry resets interface state.

## Data and execution

- `src/types/shared.ts` is the browser-safe contract. `src/lib/validation.ts` validates untrusted request payloads; UI imports only shared types.
- SQLite WAL and FTS5 are initialized lazily in `db.ts`, with schema version 7. A transactional, idempotent migration adds tracked reading status (default `READING`), numeric read/released values, reading timestamps and a progress-provenance marker. It preserves v1/v2/v3 data and never downgrades a newer user_version. The v3 migration adds `kavita_series` snapshots and durable `download_jobs`; existing files and ledger rows are preserved. The v7 migration adds a per-entry `backdrop` choice constrained to `auto`/`hidden`, defaulting existing and new entries to `auto`; catalog identity patches reset it to `auto`. The v6 migration adds sticky `off_catalog`, `cover_choice_json`, matching timestamps and per-entry `source_links`/`source_dismissals` tables with cascade deletion. The v5 migration adds sticky `kavita_manual` linkage, durable `kavita_dismissals` and a unique JSON media identity index, preserving earlier rows. The v4 migration adds the singleton `administrator` table (`id=1`, username, versioned password hash, random session epoch); no account is seeded and existing settings/library data stay intact. Alongside `settings`, `tracked_media`, `catalog_fts`, `catalog_keys`, `download_batches` and `worker_lock`, `imported_chapters`, `observed_chapters`, `source_health`, `update_entries`, `update_chapters` and `worker_state` persist the library, source observations and update scheduling. Stable FTS row IDs avoid scanning the entire catalog on every upsert. No sample catalog or media data is seeded.
- SQLite uses WAL, `synchronous=NORMAL`, a 16 MiB page cache (`cache_size=-16384`), `temp_store=MEMORY` and a five-second busy timeout. WAL/NORMAL preserves transaction atomicity and consistency after a crash; a host power loss can lose the latest committed transactions before a WAL sync/checkpoint. Application files still publish through fsync/atomic rename. Run one replica per volume.
- Auxiliary `stored_covers`, `kavita_cover_status`, `chapter_labels` and `write_versions` tables are created idempotently alongside the v7 schema. SQL triggers advance durable library, linkage, index, settings and batch versions in the same transaction as each write, including writes from other route connections. Rollback rolls the counters back; uncommitted snapshots are never retained. `listTracked` groups imported/observed numbers by tracked ID in set queries and loads source/cover rows in bulk, then memoizes the result until the library version changes. `getTracked(id)` reuses a fresh snapshot or loads just that entry. Prepared statements, indexed Kavita names/IDs, settings, batch JSON and bounded parsed metadata are reused; catalog presence builds identity/source maps once per list. Reading/matching states remain current without invalidating large payloads on every worker heartbeat.
- AES-256-GCM encrypts API credentials in SQLite using a generated 0600 settings key, separate from the database. Filesystem/volume access controls remain the operator's responsibility. The app's 0600 access token is independent of that key and remains the Bearer automation credential. Browser login uses the single administrator's case-insensitive username and password; first-start setup is atomic through the singleton SQLite primary key. Passwords use Node async `crypto.scrypt`, a random 16-byte salt, a 64-byte derived key, explicit N=32768/r=8/p=1/maxmem=64 MiB parameters and `timingSafeEqual`. The stored `scrypt$v1$32768$8$1$<salt hex>$<key hex>` format is versioned; hashes/passwords never enter logs or responses. Unknown usernames take the same derivation/comparison path using a dummy hash. Login and password-verification attempts share a process-wide 20/minute and per-normalized-username 10/minute budget across route bundles, including successful attempts, without trusting forwarded IPs. Signed browser cookies expire after seven days and contain a random account session epoch: password changes replace the hash and epoch together using a conditional update, reject stale concurrent changes and reissue only the current session. Reset/recreation generates a new epoch, so old cookies cannot revive. Cookie signing still uses `access.token`; rotating that token invalidates cookies too. Raw token browser sign-in is removed.
- `instrumentation.ts` starts the durable worker in the Node server. Its initializer opens the database and handles `BUNKO_RESET_ACCOUNT=true` before scheduling background work, even if the worker is disabled. Recovery deletes only the administrator, invalidates all browser sessions, and logs one line without secrets. A process-global volume guard prevents Next module reloads/route bundles from repeatedly resetting a newly created account. Remove the flag after recovery; each fresh server process otherwise resets again. The access token, settings and library data are preserved. Authenticated routes also ensure it starts. A SQLite lease prevents normal Next module instances/processes from duplicating work. Active work renews its lease every ten seconds with a 90-second expiry; restart recovery may wait for that expiry. A process-global scheduler wakes on enqueue/retry/control, tracking/identity edits and update/index requests. It otherwise sleeps 30 seconds (`BUNKO_WORKER_IDLE_MS`, clamped 1–300 seconds), with no idle heartbeat. Cross-process requests remain durable and are observed at the next wake. Deploy one application replica per SQLite volume.
- Batches persist before local transfers. The worker fetches chapter metadata and Suwayomi page proxy URLs, transfers pages itself, builds CBZs atomically, records each imported chapter in SQLite, writes metadata and scans Kavita. No Suwayomi enqueue/status/download-storage or download-setting mutation participates. A completed import is a written CBZ plus ledger entry. Retry/restart reconciles the ledger even if a crash occurred before updating the batch's imported IDs; interrupted unrecorded writes are safe to repeat.
- The local engine serializes chapters and fetches at most three pages concurrently. It persists jobs/progress, cached pages, pause preference and cancellation generation. Pause/clear abort HTTP transfers; a persisted generation and short polling also propagate controls across Next module instances. Clear marks remaining chapters CANCELLED and empties jobs, retaining imported files and partial pages for explicit retry. Remove cancels only one active batch or deletes a finished history row; per-batch cancellation generations prevent active writers from reviving it. Failed page transfers get up to three attempts with 250/500 ms backoff. Snapshots/SSE read the local queue independently of Suwayomi availability.
- Tracking refreshes all entries with selected sources at `updateIntervalMinutes` (5–1440, default 15). It chooses one variant per normalized chapter number in selection priority order. Observations, detection groups and automatic batch creation share a SQLite transaction; manual titles produce pending groups. Repeated checks do not duplicate observations, and unfinished check requests survive restart. The Kavita index refresh runs each cycle. In parallel, a lease-owned matching queue drains source-less comics continuously, one entry at a time with a 250 ms pause, independently of the update interval and download processing. Never-searched entries precede seven-day retries; identity/title or manual Kavita-link patches clear the last-search timestamp. Source searches run concurrently behind the shared six-call gate, and the best confident hit per source (maximum three, descending relevance then chapter count, with preference order breaking equal scores/counts) is linked transactionally only if identity and manual sources still agree. Each new link immediately refreshes chapters, title and thumbnail. Abort or lease loss discards unfinished results. The worker keeps servicing downloads and scheduled/requested checks while matching drains. Linked entries are checked oldest first, with up to three titles concurrently under a shared two-minute bound and the common six-call upstream gate; reading progress has a separate 15-second bound and cover synchronization a 60-second bound. Existing batches are processed before checks.
- Update groups are persisted by series/source/detection cycle (groups remain whole; maximum 500 chapters per batch). Each chapter links to an automatic or subsequent manual batch. The feed derives queued/downloading/downloaded/error from durable batches; a completed subset of a manual group does not mark its remaining chapters complete. The latest 200 groups and scheduling state are returned to the UI. `checking` is meaningful only while the SQLite worker lease remains live.
- Library ownership counts the union of distinct imported numeric chapter numbers and matched indexed Kavita chapter numbers. Progress and unread counts use that union plus persisted Kavita reading progress; the maximum of source observations, metadata chapter counts and Kavita chapter numbers determines released. Unnumbered specials remain downloadable but do not advance numeric counters. Imports preceding tracking are linked when the series is added. Migration does not infer chapter numbers from pre-v2 batch ID lists or scan arbitrary existing media files; ownership is recorded on successful imports from v2 onward.
- Multi-source chapter tables retain all variants for manual fallback. Automatic substitution after a source download failure is not implemented; the user can select the alternate source explicitly. Anime downloads go through Arr, not Suwayomi. Downloader pause/resume/clear controls the local transfer engine and its durable state.

## Protocol choices

Suwayomi is pinned to release `v2.4.2366` (`40bc5da`). Source IDs use its `LongString` scalar and remain strings end to end. Chapter numbers use `chapterNumber`; extension mutations use `UpdateExtensionInput.patch`. APK/JAR upload is not necessary for repository installs: these use `updateExtension`, the supported path requested in the brief. The app never selects or installs third-party extension stores automatically.

Search fans out with `Promise.allSettled`: AniList, MangaDex, MangaUpdates and local FTS. Each public request has a 2500 ms deadline. No-type searches also query AniList anime independently. Exact normalized aliases merge within one media type; conflicting known provider IDs prevent merging sequels/remakes. This heuristic can miss unrelated-language titles without a common alias. It never promises a universal identity graph. Provider failures remain explicit in the response; partial results are usable. Per-provider successful results persist in the bounded SQLite metadata cache with a 30-second freshness TTL and stale-while-revalidate; local FTS and tracked/Kavita presence are recomputed per response. Search is query-driven, not an invented discovery feed.

Deep search resolves enabled installed sources in preferred languages and queues source calls behind a shared FIFO gate of six. An active call has a 20-second deadline, independent of its queue wait. Search, matching, browse and popular sync share the gate; streams publish each completion immediately. Disconnect cancels queued and active source requests. Actual hits are indexed in FTS. Popular sync iterates a bounded number of pages (1–50) per source and streams progress. These operations progressively index the catalog. Extensions that are unreachable or protected by unsupported challenges can fail independently. Source preferences are stored separately from legacy favorites, which migrate once on first preference access. Empty enabled IDs means all matching sources in Suwayomi order; explicit IDs determine search priority. Every source search/browse persists latency and a safe error code; successful calls above four seconds are slow. GraphQL extension messages classify Cloudflare/challenges/CF 403, HTTP errors, login requirements and other errors separately. `source_error.detail` and persisted health detail contain only a sanitized first line (140 characters maximum), with URLs/query strings, credentials/tokens and emails removed. Messages are never logged raw; Cloudflare mitigation headers are also recognized. Browsing uses the pinned filter union (all eight types), aliased defaults to avoid GraphQL field conflicts, bounded nested groups and the same FTS indexing as search.

Kavita scans need a configured library including the shared path. The persistent index enumerates `Library/libraries`, pages `Series/all-v2` by library, and retrieves `Series/volumes` with at most four series requests concurrently. It also fetches `Series/metadata` and stores series/library identity, name/localized/original/sort aliases, folder, summary, genres, guessed library kind, all-chapters-read state and distinct numeric chapter numbers in SQLite. Specials and the loose-leaf/volume-only sentinel do not invent chapter numbers; bounded numeric ranges expand into their numbers. A complete refresh replaces the snapshot transactionally; failure keeps the old index and marks it stale/error. The periodic update cycle refreshes it; POST sync is durable and nonblocking, with a 60-second retry backoff on failure. Kavita's scan acceptance itself is asynchronous. `scanKavitaFolder` sends `{apiKey,folderPath}`: Kavita's anonymous scan-folder endpoint reads the body key and requires an admin. A bounded denial-body check maps its fixed non-admin response to `KAVITA_NOT_ADMIN`; all other failures become `KAVITA_SCAN_ERROR`, never upstream text. The batch records `{state,error,at}` separately from chapter completion. Plugin-auth JWT roles establish `ServicesStatus.kavita.admin`; a URL/key-hashed ten-minute boolean cache contains no tokens or keys. Unknown roles remain null; known non-admin keys gate cover uploads, whose 403 also maps to the safe denial code.

Presence matching first honors sticky manual linkage: an explicit ID selects that series and an explicit null forbids automatic presence/progress/source fallback. Otherwise it uses a saved tracked series ID, then exact normalized title/alias equality with exactly one indexed series. Every catalog response, related/recommended item and tracked media gets presence from the local snapshot without blocking on Kavita. Cached search results recompute linkage. Chapter lookup can accept a catalog `mediaId` or resolve selected tracked/FTS source identities; ambiguous results expose no owned-number guess. Ownership and update detection union indexed numbers with the import ledger, preventing automatic downloads of existing Kavita chapters.

Reading progress uses the indexed match first, with the legacy bounded `Search/search`, `Series/{seriesId}` folder/title lookup as fallback when no index match exists. Resolved IDs persist. `pagesRead >= pages` marks a numeric chapter complete; partial reads affect the latest reading timestamp. Current `maxNumber` and legacy `number` fields are supported; specials do not advance read progress. Refresh is bounded and failures retain previous values. API-key mode uses `x-api-key`; JWT mode exchanges the stored key at Plugin/authenticate. All Kavita image fetches share `kavitaCoverEndpoint`, adding the stored `apiKey` query parameter required by stable v0.9.x while retaining API-key/JWT headers for develop compatibility. This upstream URL never enters browser responses. The image proxy keeps authentication server-side, permits raster image content types only, rejects redirects and caps cover transfer at 15 MiB / 15 seconds. Libraries report mapped folders and real exclusive-create/remove write probes; inaccessible/unmounted folders are not writable.

`libraryTargets` routes MANGA/MANHWA/MANHUA/NOVEL to a Kavita library/folder; ONE_SHOT follows MANGA and both novel formats follow NOVEL. `library-paths.ts` owns the common resolver for reporting, target validation, imports, cover writes and scan namespace conversion. It tries every Kavita folder path suffix under the mount (`/medias/Mangas` → `/library/medias/Mangas`, `/library/Mangas`) and uses indexed relative series folders as evidence. A series library mounted directly at the root needs positive series-folder evidence. One confirmed candidate wins over unconfirmed suffix candidates; multiple confirmed candidates, or multiple existing candidates without evidence, are refused. A nondefault `kavitaLibraryPath` can override only when its prefix and reachable directory match, confirmed by series folders when available. Realpath containment excludes symlink escapes. Existing suffix directories can establish a unique mapping before the first index completes; no arbitrary root fallback is used.

Library definitions and kind suggestions persist in worker state so target selection works across route instances/restarts without upstream calls. Names infer MANHWA (including the common Manwha spelling)/MANHUA/NOVEL/MANGA; book types infer novels. The name takes precedence over the generic library type. A kind is suggested only by a matching name/type; MANHWA/MANHUA never fall back to Manga. Stored v5 broad suggestions are reclassified on read. An explicit null kind target disables suggestions and fallback and refuses downloads with 409 TARGET_NOT_CONFIGURED. The saved kind target wins; otherwise exactly one reachable writable suggested folder is required. `createBatch` refuses 409 TARGET_NOT_CONFIGURED before persisting any job if there is no effective target. Each ancestor is checked again before creation/writing. New series folders use sanitized titles without hash suffixes. A matched series folder inside the target and library is reused exactly, and scan paths are derived relative to that resolved target, preserving Kavita's namespace. Old files/folders never move. Chapter filenames follow `Series Ch. 0012.5.cbz`, optional `Vol. 03`, and `Series SP - chapter name.cbz`; specials additionally embed ComicInfo Format=Special.

Successful index refreshes run automatic tracking when `autoImportKavita` (validated boolean, default true) is enabled. `kavita-track.ts` shares the explicit track-from-Kavita unique catalog scorer. An unmatched/ambiguous series, or a catalog match blocked by an existing manual/conflicting link, becomes a `kavita:<id>` identity with provider `kavita`, proxy cover, indexed summary/genres and guessed format. New status is READING, or COMPLETED only if every chapter has positive pages and all pages read. Existing choices are retained. Tracking/dismissal checks repeat transactionally after network matching so edits made during lookup win. DELETE records durable dismissed series; automatic refresh never recreates them. Kavita-only media details use the local snapshot and return empty relations/recommendations; source matching uses the normal title scorer. PATCH can replace catalog metadata and indexed identifiers without losing row identity/history/progress, translates unique conflicts to ALREADY_TRACKED, and stores sticky manual series links/unlinks independently of catalog metadata.

`kavita-cover.ts` fills absent `cover.*`/`folder.*` images only in resolved writable series folders. Catalog downloads require an allowlisted HTTPS host, no credentials/nonstandard port/redirect, raster content type and 15 MiB / 15-second limits. An exclusive temporary file, fsync and exclusive hard-link publication make `cover.jpg` complete without overwriting a user cover. Kavita's scanner does not interpret external series sidecars as custom covers, so Bunko uploads the bounded bytes using `Upload/series` (base64 data URL, lockCover true), then scans the original series folder. Durable pending state retries uploads/scans; a digest detects user replacement and cancels our upload. Kavita-only entries initially use the authenticated cover proxy, then their own retained Bunko cover.

Suwayomi v2.4.2366's `fetchChapterPages(input:{chapterId})` returns `pages:List<String>` containing `/api/v1/manga/{id}/chapter/{index}/page/{index}` proxy paths. Only those relative paths are accepted; HTTP Basic auth goes exclusively to configured Suwayomi with redirects refused. Each page has a 20 MiB / 20-second limit and a supported raster content type. A chapter is capped at 2000 pages and 256 MiB page bytes. Its ordered pages and XML are assembled in memory, so allow RAM for page buffers and ZIP creation. Exclusive temporary CBZ creation, fsync and rename happen before ledger insertion. Application-owned page caches survive partial failure and restart, then disappear after import. No Suwayomi download directories or ZIP extraction are used. Metadata writes use temporary files and rename; covers use exclusive atomic publication; optional provider covers retain the restricted HTTPS host allowlist.

Arr results retain rejection information. Sonarr grabs use `/api/v3/release`; Prowlarr grabs use `/api/v1/search`, so results are not incorrectly sent to Sonarr with foreign GUIDs. Grabs use the upstream search cache and can require searching again after expiry. Existing Sonarr series/indexers/download clients must already be configured externally. Light-novel metadata/tracking is supported; no EPUB text scraping or conversion is implemented.

## Verification and limits

`npm run check` covers ESLint, strict TypeScript, backend and SSE framing tests, including v1→v7 migration, automatic path resolution/suggestions/target refusal, automatic library import/dismissals, catalog and Kavita-only details, bounded cover writes/uploads/rescan, identity replacement/manual sticky links and released maxima, singleton/concurrent setup, credential validation, unknown-user scrypt work, rate limits, password/session epoch rotation, startup reset and Bearer/origin checks, source error sanitization/concurrency, local page/CBZ transfers, controls/retry/module restart recovery, Kavita indexing/presence/ownership/track-from-library, source preferences/filters, updates and API-key/JWT progress fixtures, followed by a Next production build when lint/typecheck pass. Tests use local protocol fixtures, deliberate failures and synthetic archives. Docker checks use an isolated stack and real pinned Suwayomi, with unconfigured external services and no extension installation. They validate service startup, native SQLite, authentication, API routing, GraphQL settings/extensions, streams and metadata response shape. Container smoke is historical coverage, not a real-service acceptance result for this new local engine.

Successful local fixture tests do not prove compatibility with every extension, private Sonarr/Prowlarr setup or Kavita instance. Real private-service scans/grabs and a complete real-media download require operator configuration and remain unverified. No hard claim of <200 ms metadata search, <5 ms FTS at arbitrary library size, or guaranteed Cloudflare bypass is made. Public search can legitimately take up to the 2500 ms provider deadline, plus local overhead; the frontend should show a loading state and cache/debounce requests.

## Browser origin check

Next standalone builds `request.url` with its internal bind hostname, so `checkOrigin` compares the browser Origin with the incoming `Host` header (falling back to the request URL for direct calls). Mismatched and `null` origins are rejected; forwarded host headers are never trusted. Reverse proxies must preserve the original Host.

## Source identities and tracked cover state

Catalog detachments are explicit tracked-row state. PATCH builds a fresh Kavita/source media identity, clears catalog IDs and retains the row/history; no alternate identity returns NO_IDENTITY. Automatic import returns an already linked row without catalog replacement. Explicit media replacement can restore a catalog identity. Exact catalog IDs or a unique linked source/Kavita identity also connect search/detail cover presence without fuzzy title reassociation.

`tracked-sources.ts` owns continuous source discovery, persistent dismissals and manual/automatic provenance. It processes one eligible source-less MANGA entry at a time, prioritizing never-searched entries, then searches older than seven days. Enabled-source searches run in parallel with the normal title scorer and shared FIFO upstream gate; recent source errors back off six hours. A score of 0.9, best eligible candidate per source and a three-source ceiling constrain automatic links. Transactional rechecks after HTTP preserve concurrent identity/source edits and dismissed pairs. Manual source replacement persists removals and resets retained links to manual.

Every linked entry’s update check persists source title/thumbnail metadata, latest numeric chapter, chapter count, timestamp and safe errors. Source/chapter metadata calls share the six-call gate with searches. Failed checks preserve prior successful values; removed links cannot be resurrected by a completing HTTP call. GET tracked derives released as the maximum of raw catalog chapters, linked statuses, historical observations and Kavita/imported numeric chapters. Oldest-status ordering prevents a slow large library from permanently starving older entries.

`tracked-covers.ts` separates raw catalog metadata from the effective cover. The persisted choice is auto or a validated origin/id with a resolved selected URL. Before validation, auto derives catalog → ordered sources → Kavita locally. A successful bounded fetch persists the selected URL and consecutive-failure count in `resolved_covers`, so GET never requires upstream traffic. Identity, cover choice and ordered source/Kavita links form its resolution context; metadata/thumbnail changes alone do not change it. Two consecutive failed checks permit a replacement; a success clears the count. Choice/identity patches or a changed link context permit immediate re-resolution. Even entries without a Kavita match can retain a validated automatic resolution. Cover options add at most twenty MangaDex volume covers with a durable 24-hour cache. Selected covers propagate to tracked/media/search/discover output without overwriting raw catalog cover metadata. Restart preserves manual choices.

Tracked cover synchronization checks oldest-attempt entries first so its 60-second budget cannot repeatedly starve the rest of a large library. It serializes writes/uploads across route bundles, downloads only allowlisted catalog images or validated authenticated proxy shapes, and caps each image at 15 MiB/15 seconds. It updates a complete sidecar via fsync/atomic rename in a resolved writable series directory; API upload can still work without a mounted folder. Upload/series uses lockCover and a durable SHA-256 byte hash: equal bytes do not upload again across origin/URL changes or restart. Failed requests leave the choice retryable. Kavita’s own cover is copied to a sidecar if available but never uploaded back, preventing a feedback loop. The initial legacy missing-sidecar bootstrap retains its exclusive-write and pending-scan behavior and shares the upload hash.

## Library activity and cover fallbacks

`source-match-state.ts` derives the matching queue from SQLite and ties the persisted current entry to its worker lease owner. `TrackedMedia.sourceMatch` exposes linked/queued/searching/not-found. `/api/library/activity` reads only local state: waiting queue size/current title, release-refresh done/total counters, running state, and last/next scheduled timestamps. Lease expiry or replacement hides stale current work; the route is authenticated and included in container smoke coverage.

Before storage, automatic covers expose the remaining deduplicated catalog → linked-source → Kavita URLs as `coverFallbacks`; explicit choices have no fallbacks. A source cover PATCH can reference an unlinked Suwayomi manga: a gated detail lookup validates existence and exact string source identity before storing the canonical Suwayomi image proxy URL. Wrong/unknown pairs return NOT_FOUND, and PATCH returns the updated tracked entry. Kavita-origin bytes bypass upload back to Kavita.

## Persistent cache boundaries

Database startup idempotently adds `metadata_cache`, `image_cache` and `resolved_covers` alongside the v7 schema, without changing existing rows or lowering `user_version`. Resolved covers reference tracked rows with cascade deletion. The legacy missing-sidecar bootstrap also records its successfully fetched automatic cover.

`metadata-cache.ts` stores JSON, UTF-8 size, last successful refresh and last attempt. At most 1,000 values / 64 MiB survive pruning by oldest successful refresh, with an 8 MiB per-value cap. A process-global, volume-scoped promise map coalesces cache misses and stale refreshes across independently loaded route bundles. Stale values return without waiting; failed refreshes retain the saved payload and back off for 30 seconds (or the TTL when shorter). Provider requests have their own deadlines and outlive browser request cancellation. Discovery retains its ten-minute TTL; detail data uses 30 minutes; genres and MangaDex volumes use 24 hours. Existing durable MangaDex volume options are adopted from worker state on first use, preserving offline upgrades. Public metadata integrations are AniList, MangaDex and MangaUpdates; there is no Kitsu client. Suwayomi detail cache keys also include a hashed configuration/authentication namespace.

Followed detail requests seed missing detail extras from `tracked_media` and immediately return that durable media. A successful background load conditionally updates its saved JSON/title using the pre-fetch identity snapshot, preserving concurrent edits, sources, reading state and resolved cover. Stored detail extras enrich the response locally. Unfollowed detail requests use the same persistent cache and only need network on a miss.

`image-cache.ts` stores a self-contained MIME/timestamp header and bounded image bytes in one 0600 file under `<data>/cache/images/<sha256(key)>`. Temporary creation, fsync and atomic rename publish a complete value. SQLite tracks byte size, last access and refresh attempts; a 500 MiB disk bound evicts by least-recent access, including orphaned complete files, and old crash partials are removed on pruning. Configuration/credential hashes isolate upstream identities without storing secrets in cache keys. Both image routes use this cache, including Suwayomi extension icons. At most one stale refresh attempt per day is claimed in SQLite, with a shared in-process promise for concurrent misses. Failed upstream refreshes keep the previous complete image. Authentication and proxy input validation still run on cache hits and 304s.

Image responses persist a strong SHA-256 ETag when bytes are published and reuse it on disk-streaming hits. Legacy cache headers compute it once per process until refreshed. Responses support `If-None-Match` lists, weak comparison and `*`. They use `private, max-age=86400, stale-while-revalidate=604800`. A successful `Upload/series` invalidates that series' Kavita cache file and detaches/invalidates any prior in-flight response so it cannot repopulate the cache. The chosen automatic bytes are passed directly to the existing cover synchronizer, keeping validation and upload consistent; its persisted byte hash suppresses redundant uploads.

`progress-refresh.ts` claims on-demand refresh attempts at most every 120 seconds using a SQLite timestamp. Independently loaded route modules share one process-global run per volume. Concurrent callers await that run; calls later in the window return saved progress immediately. Each run retains the existing four-entry concurrency and 15-second total deadline, and failure keeps the stored progress and throttle timestamp.

`tests/persistent-cache.test.ts` uses isolated temporary storage and deterministic upstream fixtures to verify disk hits/misses, module reloads, ETags/304s, stale failure/recovery, LRU eviction, upload invalidation/in-flight races, persistent metadata/SWR/pruning, immediate followed details, automatic cover stickiness/reset rules and progress throttling/coalescing.

## Retained followed covers

`stored-covers.ts` owns `<data>/covers/<trackedId>-<sha256-short>.<ext>` and a SQLite metadata pointer (context, hash, MIME, filename and origin). `tracked-covers.ts` resolves one entry at a time, writes bounded complete bytes through exclusive temporary files/fsync/rename, conditionally publishes only while the identity/choice still agrees, then synchronizes those exact bytes to Kavita. Replacement deletes the previous version; untracking deletes the file. Downloaded covers stay independent of upstream cache eviction. Explicitly selecting an option again fetches its current bytes; ordinary metadata refreshes do not refetch a stored cover. Identity/link/choice changes resolve a new context. Failed full resolution exposes null and remains retryable. Backfill starts alongside matching/transfers so a long queue cannot starve cover storage. Idle backfill handles missing covers and pending/failed Kavita pushes with a five-minute failed-attempt backoff; scheduled cycles retry uploads and complete the backfill within the 60-second budget.

The authenticated `/api/covers/[id]?v=<hash>` route streams the file with private one-year immutable caching and a stored ETag. Unversioned reads revalidate; obsolete versions return 404. `TrackedMedia.coverUrl`, its nested media, and followed detail/search/discovery/home responses share that URL; fallbacks matter only before storage. Enqueue/repeated-track/same-identity patches retain authoritative server artwork. Image validation shares the exact local route allowlist with cover fetching, rejecting extra parameters/foreign origins/traversal. ## Chapter outcomes and source completeness

Each durable batch embeds at most 500 `DownloadChapter` values and a nullable scan result. Chapter metadata uses the upstream name, normalized number and source name; progress writes carry the pages-done ratio, followed by importing/done or a safe per-chapter error. One failure does not stop subsequent chapters. Ledger reconciliation precedes transfer and cancellation, preserving imports after interruptions. A batch with any successful imports finishes as completed; all-failed work is error. A failed scan remains independently retryable on a completed batch. `retry_failed` requeues only failed chapters in one/all batches (requests during active work persist the selected IDs and run after it finishes); legacy retry also supports scan-only recovery. Snapshots and SSE share `listBatches`, which normalizes old JSON into the new fields and caps arrays. Updates derive failure/success from linked chapter outcomes so a partial batch cannot mark a group downloaded.

`chapter_labels` retains bounded source labels from chapter selection (20,000 entries, oldest evicted) under a hashed Suwayomi configuration namespace. Enqueue copies these labels into batch JSON without an upstream wait; arbitrary/legacy IDs resolve labels when the worker fetches chapter metadata. This cache is disposable and cannot establish imported ownership.

Matching count probes request only chapter IDs for score ≥ 0.9 candidates, share the six-call source gate, and cache a count/null for ten minutes under the hashed Suwayomi namespace. Both SSE candidates (maximum three per source) and automatic links (maximum three sources) sort by score then count, preserving preference only for exact ties. No page fetch or Suwayomi download is needed for ranking.

`kavita_cover_status` stores per-entry context, stored hash, series ID, state and safe error with cascade deletion. Writes invalidate the tracked snapshot transactionally. A changed choice/context/hash derives pending immediately; no series or no cover derives none. Cover resolution publishes complete local bytes, then records pending, synchronizes those bytes through the existing serialized upload gate, scans the indexed folder and records synced. Failure records failed for the same current context only. The durable series upload hash suppresses duplicate uploads even after scan failure. Retained bytes remain eligible for retry, and an explicit cover patch wakes/attempts the push promptly.
