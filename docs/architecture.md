# Architecture

KaviSeerr is a long-running Node 22 Next.js App Router service. All route handlers run in the Node runtime, dynamically, with uncached private responses. The root page renders a French React interface with a server layout, locally bundled Geist font, Tailwind CSS and Radix dialogs/tabs. `src/lib/client/api.ts` is the browser adapter over the shared contract; server integrations never enter the client bundle. Authentication gates the views, signed HttpOnly cookies authenticate SSE, and logout/expiry resets interface state.

## Data and execution

- `src/types/shared.ts` is the browser-safe contract. `src/lib/validation.ts` validates untrusted request payloads; UI imports only shared types.
- SQLite WAL and FTS5 are initialized lazily in `db.ts`, with schema version 4. A transactional, idempotent migration adds tracked reading status (default `READING`), numeric read/released values, reading timestamps and a progress-provenance marker. It preserves v1/v2/v3 data and never downgrades a newer user_version. The v3 migration adds `kavita_series` snapshots and durable `download_jobs`; existing files and ledger rows are preserved. The v4 migration adds the singleton `administrator` table (`id=1`, username, versioned password hash, random session epoch); no account is seeded and existing settings/library data stay intact. Alongside `settings`, `tracked_media`, `catalog_fts`, `catalog_keys`, `download_batches` and `worker_lock`, `imported_chapters`, `observed_chapters`, `source_health`, `update_entries`, `update_chapters` and `worker_state` persist the library, source observations and update scheduling. Stable FTS row IDs avoid scanning the entire catalog on every upsert. No sample catalog or media data is seeded.
- AES-256-GCM encrypts API credentials in SQLite using a generated 0600 settings key, separate from the database. Filesystem/volume access controls remain the operator's responsibility. The app's 0600 access token is independent of that key and remains the Bearer automation credential. Browser login uses the single administrator's case-insensitive username and password; first-start setup is atomic through the singleton SQLite primary key. Passwords use Node async `crypto.scrypt`, a random 16-byte salt, a 64-byte derived key, explicit N=32768/r=8/p=1/maxmem=64 MiB parameters and `timingSafeEqual`. The stored `scrypt$v1$32768$8$1$<salt hex>$<key hex>` format is versioned; hashes/passwords never enter logs or responses. Unknown usernames take the same derivation/comparison path using a dummy hash. Login and password-verification attempts share a process-wide 20/minute and per-normalized-username 10/minute budget across route bundles, including successful attempts, without trusting forwarded IPs. Signed browser cookies expire after seven days and contain a random account session epoch: password changes replace the hash and epoch together using a conditional update, reject stale concurrent changes and reissue only the current session. Reset/recreation generates a new epoch, so old cookies cannot revive. Cookie signing still uses `access.token`; rotating that token invalidates cookies too. Raw token browser sign-in is removed.
- `instrumentation.ts` starts the durable worker in the Node server. Its initializer opens the database and handles `KAVISEERR_RESET_ACCOUNT=true` before scheduling background work, even if the worker is disabled. Recovery deletes only the administrator, invalidates all browser sessions, and logs one line without secrets. A process-global volume guard prevents Next module reloads/route bundles from repeatedly resetting a newly created account. Remove the flag after recovery; each fresh server process otherwise resets again. The access token, settings and library data are preserved. Authenticated routes also ensure it starts. A SQLite lease prevents normal Next module instances/processes from duplicating work. Leases renew every 30 seconds and expire after five minutes; restart recovery may wait for that expiry. Deploy one application replica per SQLite volume.
- Batches persist before local transfers. The worker fetches chapter metadata and Suwayomi page proxy URLs, transfers pages itself, builds CBZs atomically, records each imported chapter in SQLite, writes metadata and scans Kavita. No Suwayomi enqueue/status/download-storage or download-setting mutation participates. A completed import is a written CBZ plus ledger entry. Retry/restart reconciles the ledger even if a crash occurred before updating the batch's imported IDs; interrupted unrecorded writes are safe to repeat.
- The local engine serializes chapters and fetches at most three pages concurrently. It persists jobs/progress, cached pages, pause preference and cancellation generation. Pause/clear abort HTTP transfers; a persisted generation and short polling also propagate controls across Next module instances. Clear marks transfer batches CANCELLED and empties jobs, retaining imported files and partial pages for explicit retry. Failed page transfers get up to three attempts with 250/500 ms backoff. Snapshots/SSE read the local queue independently of Suwayomi availability.
- Tracking checks all MANGA entries with selected sources at `updateIntervalMinutes` (5–1440, default 15). It chooses one variant per normalized chapter number in selection priority order. Observations, detection groups and automatic batch creation share a SQLite transaction; manual titles produce pending groups. Repeated checks do not duplicate observations, and unfinished check requests survive restart. The Kavita index refresh runs each cycle, followed by up to three source-title checks concurrently under a shared two-minute bound; reading progress has a separate 15-second bound. Existing batches are processed before checks.
- Update groups are persisted by series/source/detection cycle (groups remain whole; maximum 500 chapters per batch). Each chapter links to an automatic or subsequent manual batch. The feed derives queued/downloading/downloaded/error from durable batches; a completed subset of a manual group does not mark its remaining chapters complete. The latest 200 groups and scheduling state are returned to the UI. `checking` is meaningful only while the SQLite worker lease remains live.
- Library ownership counts the union of distinct imported numeric chapter numbers and matched indexed Kavita chapter numbers. Progress and unread counts use that union plus persisted Kavita reading progress; source release maxima and metadata chapter counts determine released. Unnumbered specials remain downloadable but do not advance numeric counters. Imports preceding tracking are linked when the series is added. Migration does not infer chapter numbers from pre-v2 batch ID lists or scan arbitrary existing media files; ownership is recorded on successful imports from v2 onward.
- Multi-source chapter tables retain all variants for manual fallback. Automatic substitution after a source download failure is not implemented; the user can select the alternate source explicitly. Anime downloads go through Arr, not Suwayomi. Downloader pause/resume/clear controls the local transfer engine and its durable state.

## Protocol choices

Suwayomi is pinned to release `v2.4.2366` (`40bc5da`). Source IDs use its `LongString` scalar and remain strings end to end. Chapter numbers use `chapterNumber`; extension mutations use `UpdateExtensionInput.patch`. APK/JAR upload is not necessary for repository installs: these use `updateExtension`, the supported path requested in the brief. The app never selects or installs third-party extension stores automatically.

Search fans out with `Promise.allSettled`: AniList, MangaDex, MangaUpdates and local FTS. Each public request has a 2500 ms deadline. No-type searches also query AniList anime independently. Exact normalized aliases merge within one media type; conflicting known provider IDs prevent merging sequels/remakes. This heuristic can miss unrelated-language titles without a common alias. It never promises a universal identity graph. Provider failures remain explicit in the response; partial results are usable. A bounded 30-second in-memory cache reduces repeated upstream queries. Search is query-driven, not an invented discovery feed.

Deep search resolves enabled installed sources in preferred languages and queues source calls behind a shared FIFO gate of six. An active call has a 20-second deadline, independent of its queue wait. Search, matching, browse and popular sync share the gate; streams publish each completion immediately. Disconnect cancels queued and active source requests. Actual hits are indexed in FTS. Popular sync iterates a bounded number of pages (1–50) per source and streams progress. These operations progressively index the catalog. Extensions that are unreachable or protected by unsupported challenges can fail independently. Source preferences are stored separately from legacy favorites, which migrate once on first preference access. Empty enabled IDs means all matching sources in Suwayomi order; explicit IDs determine search priority. Every source search/browse persists latency and a safe error code; successful calls above four seconds are slow. GraphQL extension messages classify Cloudflare/challenges/CF 403, HTTP errors, login requirements and other errors separately. `source_error.detail` and persisted health detail contain only a sanitized first line (140 characters maximum), with URLs/query strings, credentials/tokens and emails removed. Messages are never logged raw; Cloudflare mitigation headers are also recognized. Browsing uses the pinned filter union (all eight types), aliased defaults to avoid GraphQL field conflicts, bounded nested groups and the same FTS indexing as search.

Kavita scans need a configured library including the shared path. The persistent index enumerates `Library/libraries`, pages `Series/all-v2` by library, and retrieves `Series/volumes` with at most four series requests concurrently. It stores series/library identity, name/localized/original/sort aliases, folder and distinct numeric chapter numbers in SQLite. Specials and the loose-leaf/volume-only sentinel do not invent chapter numbers; bounded numeric ranges expand into their numbers. A complete refresh replaces the snapshot transactionally; failure keeps the old index and marks it stale/error. The periodic update cycle refreshes it; POST sync is durable and nonblocking, with a 60-second retry backoff on failure. Kavita's scan acceptance itself is asynchronous.

Presence matching first uses a saved tracked series ID, otherwise exact normalized title/alias equality with exactly one indexed series. Every catalog response, related/recommended item and tracked media gets presence from the local snapshot without blocking on Kavita. Cached search results recompute linkage. Chapter lookup can accept a catalog `mediaId` or resolve selected tracked/FTS source identities; ambiguous results expose no owned-number guess. Ownership and update detection union indexed numbers with the import ledger, preventing automatic downloads of existing Kavita chapters.

Reading progress uses the indexed match first, with the legacy bounded `Search/search`, `Series/{seriesId}` folder/title lookup as fallback when no index match exists. Resolved IDs persist. `pagesRead >= pages` marks a numeric chapter complete; partial reads affect the latest reading timestamp. Current `maxNumber` and legacy `number` fields are supported; specials do not advance read progress. Refresh is bounded and failures retain previous values. API-key mode uses `x-api-key`; JWT mode exchanges the stored key at Plugin/authenticate. The image proxy keeps authentication server-side, permits raster image content types only, rejects redirects and caps cover transfer at 15 MiB / 15 seconds. Libraries report mapped folders and real exclusive-create/remove write probes; inaccessible/unmounted folders are not writable.

`libraryTargets` routes MANGA/MANHWA/MANHUA/NOVEL to a Kavita library/folder; ONE_SHOT follows MANGA and both novel formats follow NOVEL. The Kavita-side `kavitaLibraryPath` prefix maps to the application's `/library` mount (environment override for fixtures/local installs). Lexical boundary checks reject external/traversal targets, and each ancestor's realpath is checked before directory creation continues. New series folders use sanitized titles without hash suffixes. A matched series folder inside the target and library is reused exactly. Old files/folders never move. Chapter filenames follow `Series Ch. 0012.5.cbz`, optional `Vol. 03`, and `Series SP - chapter name.cbz`; specials additionally embed ComicInfo Format=Special because the bare SP marker alone does not force a special in Kavita.

Suwayomi v2.4.2366's `fetchChapterPages(input:{chapterId})` returns `pages:List<String>` containing `/api/v1/manga/{id}/chapter/{index}/page/{index}` proxy paths. Only those relative paths are accepted; HTTP Basic auth goes exclusively to configured Suwayomi with redirects refused. Each page has a 20 MiB / 20-second limit and a supported raster content type. A chapter is capped at 2000 pages and 256 MiB page bytes. Its ordered pages and XML are assembled in memory, so allow RAM for page buffers and ZIP creation. Exclusive temporary CBZ creation, fsync and rename happen before ledger insertion. Application-owned page caches survive partial failure and restart, then disappear after import. No Suwayomi download directories or ZIP extraction are used. Metadata/cover writes also use temporary files and rename; optional provider covers retain the restricted HTTPS host allowlist.

Arr results retain rejection information. Sonarr grabs use `/api/v3/release`; Prowlarr grabs use `/api/v1/search`, so results are not incorrectly sent to Sonarr with foreign GUIDs. Grabs use the upstream search cache and can require searching again after expiry. Existing Sonarr series/indexers/download clients must already be configured externally. Light-novel metadata/tracking is supported; no EPUB text scraping or conversion is implemented.

## Verification and limits

`npm run check` covers ESLint, strict TypeScript, backend and SSE framing tests, including v1→v4 migration, singleton/concurrent setup, credential validation, unknown-user scrypt work, rate limits, password/session epoch rotation, startup reset and Bearer/origin checks, source error sanitization/concurrency, local page/CBZ transfers, controls/retry/module restart recovery, Kavita indexing/presence/ownership/track-from-library, source preferences/filters, updates and API-key/JWT progress fixtures, followed by a Next production build when lint/typecheck pass. Tests use local protocol fixtures, deliberate failures and synthetic archives. Docker checks use an isolated stack and real pinned Suwayomi, with unconfigured external services and no extension installation. They validate service startup, native SQLite, authentication, API routing, GraphQL settings/extensions, streams and metadata response shape. Container smoke is historical coverage, not a real-service acceptance result for this new local engine.

Successful local fixture tests do not prove compatibility with every extension, private Sonarr/Prowlarr setup or Kavita instance. Real private-service scans/grabs and a complete real-media download require operator configuration and remain unverified. No hard claim of <200 ms metadata search, <5 ms FTS at arbitrary library size, or guaranteed Cloudflare bypass is made. Public search can legitimately take up to the 2500 ms provider deadline, plus local overhead; the frontend should show a loading state and cache/debounce requests.

## Browser origin check

Next standalone builds `request.url` with its internal bind hostname, so `checkOrigin` compares the browser Origin with the incoming `Host` header (falling back to the request URL for direct calls). Mismatched and `null` origins are rejected; forwarded host headers are never trusted. Reverse proxies must preserve the original Host.
