# Architecture

The active interface language is shared by React and browser request transport. Fetch sends
that choice through `Accept-Language`; SSE adds the supported `uiLanguage` hint because
EventSource cannot set headers. Foreground source searches schedule the interface language
first within the user's allowed source languages. Result lanes keep useful hits before
pending/empty/error lanes, then favor that language with stable source-priority ties. Title
source suggestions rank title relevance, interface language, then chapter count. Interface
changes restart active search/matching streams. Saved language filters, favourite IDs, manual
source links and background matching preferences remain unchanged; an excluded language is
never silently enabled.

Catalog search without a `type` restriction fans out to AniList (including novels), MangaDex,
MangaUpdates, Open Library, configured Metron/Hardcover, tracked works, the local Suwayomi FTS
index and the Kavita index. Provider responses are bounded relevance pages (20–100 entries),
not exhaustive exports of all upstream matches. Google Books, BnF, Rakuten and Royal Road RSS
are publication-feed/detail integrations rather than additional global-search engines. Live
extension search stays separate. Fast and full browser responses belong to their exact query;
a previous full response must never mask the next query's fast answer.

Metron series cards resolve artwork through an authenticated, on-demand issue-cover proxy.
The issue cache remains private and credential-scoped, with provider-wide pacing and at most
two queued cover lookups so browsing does not monopolize the provider queue. Covers can arrive
progressively on a cold cache. Null covers in older cached/tracked series are repaired on output;
retaining a cover for imports resolves the artwork server-side without forwarding auth to the CDN.
The proxy serves raster bytes through the existing private, credential-scoped image cache and
conditional ETags. Browser fetch does not depend on a cross-origin CDN CORS policy.

Bunko is a long-running Node 22 Next.js App Router service. All route handlers run in the Node runtime, dynamically, with private JSON responses marked no-store and a persistent private image cache. The root page renders a French React interface with a server layout, locally bundled Geist font, Tailwind CSS and Radix dialogs/tabs. `src/lib/client/api.ts` is the browser adapter over the shared contract; server integrations never enter the client bundle. Authentication gates the views, signed HttpOnly cookies authenticate SSE, and logout/expiry resets interface state.

Interactive catalog search takes snapshots of each coalesced provider lane instead of awaiting the slowest provider. Search and chapter snapshots poll only while pending (750ms with500ms deduplication). A cold initial cache snapshot is optional; errors retain last-good data or a short failed-attempt marker, preventing perpetual restart loops. Normal blocking consumers retain complete-result behavior.

Chapter snapshots add one source at a time while projecting local ownership on every response. Shared tenant-bound loads outlive individual HTTP snapshots, enforce source namespace/revocation boundaries, and reuse in-flight work. Worker/reader/acquisition callers force complete fresh results into the same per-source cache. Available rows, selection and actions remain usable; notices report remaining work. The first automatic source link does not hide remaining matching progress.

A bounded tenant/source-scoped map of already displayed card metadata opens known sheets immediately while full metadata loads, preserving content on later errors. Novel/book pages with Hardcover enabled independently expose both catalog lanes; existing single-provider and nonfatal-warning semantics are preserved. No UI redesign or schema migration is needed for these incremental responses.

Explicit library association requests take priority over automatic source-less work. Matching takes successive paced two-entry batches while cover/index maintenance is still running,
including when the lane was initially empty. A completed batch must not wait for that maintenance
before starting the next one. Once the other lanes finish, the current batch yields to the tenant
scheduler; unexpected matching/storage failures stop relaunching until the next cycle. The worker
publishes its active title before catalog lookup, bounds that consumer's catalog wait to five seconds
and the whole entry to thirty seconds, and persists confident title hits before count/enrichment or
other extensions finish. Counts still refine relevance ties, with stable source preference ordering;
manual edits, dismissals, language filters, namespaces and lease checks remain authoritative. A timed
out unlinked work retries in five minutes and rotates extension lanes on retry so slow earlier
extensions do not permanently starve later ones. Two-entry tenant fairness remains when yielding the worker, with an immediate wake
for further explicit requests instead of an idle delay. Valid already-committed links survive later
source failures. Profile owns the liked collection; the former favorites URL redirects to its section.
Home shelf fades mask only the actual scrolling viewport edges, including the mobile page gutters;
no absolutely positioned shadow layer covers cards inside that viewport.

## Data and execution

- Same-origin cover and extension-icon transfers are scheduled in the browser, at most two at
  once. An IntersectionObserver starts artwork within 200px of the viewport; leaving a route
  aborts its active transfers and removes its queued work. Each active fetch has a 35-second
  deadline and a 15MiB response limit. Completed images use object URLs revoked when replaced
  or unmounted; normal HTTP caching and credential scoping remain in force. Replacement artwork is decoded before replacing the displayed image; source refreshes never
  clear a usable image first. Remote public artwork uses the browser image cache. This retains connection capacity for navigation/JSON
  on HTTP/1 LAN installations instead of letting slow artwork occupy all six browser sockets.
- Metron cover waits are limited to15 seconds including the outer lookup queue; its image
  response wait is bounded to30 seconds including the public image download. An abandoned
  consumer does not cancel a coalesced provider/cache load used by another consumer. Single-kind
  discovery also returns a progressive snapshot after at most a300ms initial wait instead of
  holding the HTTP request until its provider finishes. Pending/partial/error semantics remain.
- Browser JSON reads have a30-second deadline including the body (120s for explicit mutations), so a lost response ends
  in the existing error state instead of leaving an indefinite skeleton. These bounds do not
  establish NAS throughput or guarantee provider availability.

- `src/types/shared.ts` is the browser-safe contract. `src/lib/validation.ts` validates untrusted request payloads; UI imports only shared types.
- SQLite WAL and FTS5 are initialized lazily in `db.ts`, with schema version17 (tenant-local likes and stable cover identity; v15 adds nullable current-inventory volume declaration). A tenant-local additive v13 migration defaults `kavita_cover_sync` to true and adds stable local-reader chapter identities; existing chapter progress and files are preserved. A transactional, idempotent migration adds tracked reading status (default `READING`), numeric read/released values, reading timestamps and a progress-provenance marker. It preserves v1/v2/v3 data and never downgrades a newer user_version. The v3 migration adds `kavita_series` snapshots and durable `download_jobs`; existing files and ledger rows are preserved. The v7 migration adds a per-entry `backdrop` choice constrained to `auto`/`hidden`, defaulting existing and new entries to `auto`; catalog identity patches reset it to `auto`. The v6 migration adds sticky `off_catalog`, `cover_choice_json`, matching timestamps and per-entry `source_links`/`source_dismissals` tables with cascade deletion. The v5 migration adds sticky `kavita_manual` linkage, durable `kavita_dismissals` and a unique JSON media identity index, preserving earlier rows. The v4 migration adds the singleton `administrator` table (`id=1`, username, versioned password hash, random session epoch); no account is seeded and existing settings/library data stay intact. Alongside `settings`, `tracked_media`, `catalog_fts`, `catalog_keys`, `download_batches` and `worker_lock`, `imported_chapters`, `observed_chapters`, `source_health`, `update_entries`, `update_chapters` and `worker_state` persist the library, source observations and update scheduling. Stable FTS row IDs avoid scanning the entire catalog on every upsert. No sample catalog or media data is seeded.
- SQLite uses WAL, `synchronous=NORMAL`, a 16 MiB page cache (`cache_size=-16384`), `temp_store=MEMORY` and a five-second busy timeout. WAL/NORMAL preserves transaction atomicity and consistency after a crash; a host power loss can lose the latest committed transactions before a WAL sync/checkpoint. Chapter archives publish through fsync and an exclusive hard link; existing destinations are never replaced. Other sidecars use atomic rename. Run one replica per volume.
- Auxiliary `stored_covers`, `kavita_cover_status`, `chapter_labels` and `write_versions` tables are created idempotently alongside the v7 schema. SQL triggers advance durable library, linkage, index, settings and batch versions in the same transaction as each write, including writes from other route connections. Rollback rolls the counters back; uncommitted snapshots are never retained. `listTracked` groups imported/observed numbers by tracked ID in set queries and loads source/cover rows in bulk, then memoizes the result until the library version changes. `getTracked(id)` reuses a fresh snapshot or loads just that entry. Prepared statements, indexed Kavita names/IDs, settings, batch JSON and bounded parsed metadata are reused; catalog presence builds identity/source maps once per list. Reading/matching states remain current without invalidating large payloads on every worker heartbeat.
- AES-256-GCM encrypts API credentials in SQLite using a generated 0600 settings key, separate from the database. Filesystem/volume access controls remain the operator's responsibility. The app's 0600 access token is independent of that key and remains the Bearer automation credential. Browser login uses the signed-in user's case-insensitive username and password; first-start setup is serialized by an immediate SQLite transaction. Passwords use Node async `crypto.scrypt`, a random 16-byte salt, a 64-byte derived key, explicit N=32768/r=8/p=1/maxmem=64 MiB parameters and `timingSafeEqual`. The stored `scrypt$v1$32768$8$1$<salt hex>$<key hex>` format is versioned; hashes/passwords never enter logs or responses. Unknown usernames take the same derivation/comparison path using a dummy hash. Login and password-verification attempts share a volume-wide 20/minute and per-normalized-username 10/minute budget across route bundles, including successful attempts, without trusting forwarded IPs. Signed browser cookies expire after seven days and contain a random account session epoch: password changes replace the hash and epoch together using a conditional update, reject stale concurrent changes and reissue only the current session. Reset/recreation generates a new epoch, so old cookies cannot revive. Cookie signing still uses `access.token`; rotating that token invalidates cookies too. Raw token browser sign-in is removed.
- `instrumentation.ts` starts the durable worker in the Node server. Its initializer opens the accounts store and handles `BUNKO_RESET_ACCOUNT=true` before scheduling background work, even if the worker is disabled. Recovery clears only the first admin’s password and rotates that user’s session epoch, preserves all accounts and tenant data and other users’ sessions, and logs one line without secrets. A process-global volume guard prevents Next module reloads/route bundles from repeatedly resetting a newly created account. Remove the flag after recovery; each fresh server process otherwise resets again. The access token, settings and library data are preserved. Authenticated routes also ensure it starts. A SQLite lease prevents normal Next module instances/processes from duplicating work. Active work renews its lease every ten seconds with a 90-second expiry; restart recovery may wait for that expiry. A process-global scheduler wakes on enqueue/retry/control, tracking/identity edits and update/index requests. It otherwise sleeps 30 seconds (`BUNKO_WORKER_IDLE_MS`, clamped 1–300 seconds), with no idle heartbeat. Cross-process requests remain durable and are observed at the next wake. Deploy one application replica per SQLite volume.
- Batches persist before local transfers. The worker fetches chapter metadata and Suwayomi page proxy URLs, transfers pages itself, builds CBZs atomically, records each imported chapter in SQLite, writes metadata and scans Kavita. No Suwayomi enqueue/status/download-storage or download-setting mutation participates. A completed import is a written CBZ plus ledger entry. Retry/restart reconciles the ledger even if a crash occurred before updating the batch's imported IDs; interrupted unrecorded writes are safe to repeat: an existing CBZ is adopted only when its embedded Bunko import fingerprint matches this work, source connection and chapter. An unknown or different destination returns `IMPORT_CONFLICT` and retains its bytes.
- Schema v14 preserves imports, archive pointers, jobs, observations/dates and source baselines under connection-scoped identities; old batch JSON is bound to its pre-upgrade connection. Archive pointers provide provenance for older imports when available; otherwise the saved connection (or first-instance environment fallback) is used once. The migration is atomic/idempotent and never rebinds history on restart. Connection namespaces are internal and omitted from API batch JSON. Old files remain readable by owned work/number after a server change. A changed Suwayomi URL clears old numeric source associations and local source catalog/health; works, import history and files remain. Old batches fail with `SOURCE_CHANGED` instead of running on the replacement server, and in-flight work checks its connection before publishing. A same-URL upstream database replacement cannot always be identified automatically; a reused imported chapter ID assigned to a different work fails closed before transfer instead of reassigning history. Source ownership is additionally checked against linked work/source selections when available.
- A volume is not complete merely because one imported chapter carries its volume number, including after Kavita scans that chapter file. Only indexed archives whose basename explicitly identifies the volume and contains no chapter number establish complete-volume ownership/read progress. Unknown/partial volume groupings never suppress missing chapters. Existing cached volume counts are invalidated once for a fresh conservative index; no fixed chapter-count heuristic is used.
- The local engine serializes chapters and fetches at most three pages concurrently. It persists jobs/progress, cached pages, pause preference and cancellation generation. Pause/clear abort HTTP transfers; a persisted generation and short polling also propagate controls across Next module instances. Clear marks remaining chapters CANCELLED and empties jobs, retaining imported files and partial pages for explicit retry. Remove cancels only one active batch or deletes a finished history row; per-batch cancellation generations prevent active writers from reviving it. Failed page transfers get up to three attempts with 250/500 ms backoff. Snapshots/SSE read the local queue independently of Suwayomi availability.
- Tracking refreshes all entries with selected sources at `updateIntervalMinutes` (5–1440, default 15). It chooses one variant per normalized chapter number in selection priority order. Observations, detection groups and automatic batch creation share a SQLite transaction; manual titles produce pending groups. Repeated checks do not duplicate observations, and unfinished check requests survive restart. The Kavita index refresh runs each cycle. In parallel, a lease-owned matching queue drains source-less comics continuously, one entry at a time with a 250 ms pause, independently of the update interval and download processing. Never-searched entries precede seven-day retries; identity/title or manual Kavita-link patches clear the last-search timestamp. Source searches run behind a process-wide budget per normalized Suwayomi base URL, shared even across tenants using different credentials. Six total slots include at most four background calls; queued interaction takes priority and background tenant lanes rotate. Queue wait does not consume an upstream deadline or source-health latency. Each tenant yields its matching drain after two entries so later accounts can run. Source searches run concurrently behind that budget, and the best confident hit per source (maximum three, descending relevance then chapter count, with preference order breaking equal scores/counts) is linked transactionally only if identity and manual sources still agree. Each new link immediately refreshes chapters, title and thumbnail. Abort or lease loss discards unfinished results. The worker keeps servicing downloads and scheduled/requested checks while matching drains. Linked entries are checked oldest first, with up to three titles concurrently under a shared two-minute bound and the common six-call upstream gate; reading progress has a separate 15-second bound and cover synchronization a 60-second bound. Existing batches are processed before checks.
- Update groups are persisted by series/source/detection cycle (groups remain whole; maximum 500 chapters per batch). Each chapter links to an automatic or subsequent manual batch. The feed derives queued/downloading/downloaded/error from durable batches; a completed subset of a manual group does not mark its remaining chapters complete. The latest 200 groups and scheduling state are returned to the UI. `checking` is meaningful only while the SQLite worker lease remains live.
- Library ownership counts the union of distinct imported numeric chapter numbers and matched indexed Kavita chapter numbers. Progress and unread counts use that union plus persisted Kavita reading progress; the maximum of source observations, metadata chapter counts and Kavita chapter numbers determines released. Unnumbered specials remain downloadable but do not advance numeric counters. Imports preceding tracking are linked when the series is added. Migration does not infer chapter numbers from pre-v2 batch ID lists or scan arbitrary existing media files; ownership is recorded on successful imports from v2 onward.
- Multi-source chapter tables retain all variants for manual fallback. Automatic substitution after a source download failure is not implemented; the user can select the alternate source explicitly. Anime downloads go through Arr, not Suwayomi. Downloader pause/resume/clear controls the local transfer engine and its durable state.

## Separate user instances and request scope

Every user owns a separate Bunko instance. Admins additionally manage `/api/users` and the shared optional catalog configuration/probes. Members have the same personal settings, sources, extension, catalog usage, library, download, update, Arr and Kavita controls in their own instance. Entering the same Suwayomi URL deliberately connects two instances to the same upstream; Bunko does not isolate mutations within an upstream service that its operators choose to share.

The small `<data>/accounts.db` contains usernames, roles, password hashes, session epochs, login-attempt budgets, token ownership, durable deletion tombstones and shared `catalog_settings`. `access.token` and `settings.key` remain at the volume root. A token is bound to its original user (the first admin by default), including after role changes; deleting that user revokes its API access. Before setup, tenant API calls return `SETUP_REQUIRED`. Password changes and recovery rotate only the affected session epoch. Existing v2 cookies remain valid through migration because signing keys, IDs and epochs are preserved.

Each `<data>/users/<id>/` owns its SQLite database, retained covers, proxy image cache and chapter page cache. Settings, source preferences/flags/health, FTS entries, matches, content filter decisions, indexed Kavita series, reading progress, cover sidecar state, batches/jobs/import ledgers, updates and worker leases are private to that database. Schema v10 retires the v9 membership tables; `tracked_media` is the tenant's library. Numeric work/chapter/series IDs may collide across tenants safely.

`api.route()` resolves the session against the accounts store, enters the identity context and a process-global `AsyncLocalStorage` tenant context, then invokes the handler. Dynamic routes and SSE use the same wrapper; asynchronous continuations retain their initiating tenant. Public handlers explicitly leave tenant scope. `db()`, `dataDir()`, settings and library path resolution throw without a tenant context. There is no implicit default tenant. Accounts operations and startup use the explicitly separate accounts store.

Connections are keyed by tenant path, prepared statements by connection, and module snapshots by tenant ID. Settings, tracked lists, batches, content flags/identity graphs, Kavita index/linkage, release/planning views, parsed metadata and image headers are partitioned. Process-global in-flight metadata/image/release/hero/progress maps include the full tenant directory. The only process-wide queues contain callbacks/budgets (upstream concurrency gates and public-provider pacing), never reusable private results. This implementation conservatively keeps public provider metadata and release ingestion in each tenant too: there is no shared private-data cache or shared cache database.

One scheduler iterates accounts with at most two tenant ticks active, each inside its tenant context and its own SQLite lease. An unconfigured empty tenant skips integration work. Wakes notify that tenant's waiters and the scheduler; idle sleep remains 30 seconds with no heartbeat, while active leases renew every ten seconds. One failed tenant does not stop the remaining ticks. Reading progress, auto-import, scans, matching and cover pushes use that tenant's configured Kavita connection for either role. Key replacement clears old progress; late results from a replaced key/URL are discarded.

Deleting an account requires `{id,confirmDeleteData:true}` and cannot remove the final admin. The account and a permanent deletion tombstone commit together, invalidating sessions before filesystem cleanup. Revocation aborts active page transfers; tombstones prevent old contexts reopening the tenant database or recreating its data directory. Cleanup removes `<data>/users/<id>/` and retries after restart. Account IDs are never reused. Mounted Kavita media outside the data volume is retained.

### Upgrade from a single instance or schema v9

Stop the old process before upgrading; one replica owns a data volume. Startup takes an immediate transaction on `accounts.db`, copies the old administrator or all v9 accounts with unchanged IDs/hashes/epochs, checkpoints and closes the legacy SQLite DB, then renames its complete file and private directories into `<data>/users/1/`. Both `bunko.db` and the older `kaviseerr.db` filename work. Covers, `cache/` and `page-cache/` move without rewriting their bytes; the encryption/signing keys stay at the volume root. No media library files move.

A durable migration marker publishes only after the moves. If the process stops between renames and commit, restart finds the DB either at the root or under `users/1/`, recopies accounts transactionally if needed and resumes the remaining moves. Existing destinations are never overwritten; ambiguous duplicate paths stop startup. Directory fsync follows every rename. The subsequent transactional v10 database migration preserves user 1's current v9 reading status/progress/dates and content filter preference, then drops obsolete membership/account copies. Earlier application migrations still run in order and never lower a newer schema version. V9 members receive empty tenants. A pre-account installation keeps its old library in tenant 1 until initial setup creates user 1.

`SUWAYOMI_URL`, username/password and Kavita/Arr URL/key environment values seed only tenant 1, once, without overwriting saved rows. Later users start unconfigured. `BUNKO_*` settings and legacy `KAVISEERR_*` aliases remain supported, including `DATA_DIR`, `LIBRARY_DIR`, `WORKER` and `RESET_ACCOUNT`.

### Docker volumes and library mounts

Keep one data volume mounted at `/data`; it contains `accounts.db`, root keys and every `users/<id>/` directory. `BUNKO_LIBRARY_DIR` is the common media mount (default `/library`). Each account chooses `Settings.mediaRoot`: the mount itself or one of its direct real subdirectories, with arbitrary names, for example `/library/lucas-special` or `/library/Shared disk`. Null means no folder is chosen. Account names and IDs have no effect on a chosen path, including after a rename. Bunko does not move media.

The accounts store owns `account_media_roots(user_id,mount,path)`, partitioned by the configured common mount. A nullable row distinguishes a cleared/unconfigured account from an account awaiting migration. A `BEGIN IMMEDIATE` transaction validates the existing directory, checks every other account's reservation and writes the choice. Equal paths and ancestor/descendant paths conflict; sibling roots are independent. The account lock remains held while accompanying tenant settings/target validation runs, so an invalid target rolls the reservation back. Independent route bundles/processes cannot both claim overlapping folders. Account deletion cascades its reservations; temporarily missing or unsafe mounts keep their reservation until explicitly cleared.

`GET /api/kavita/status` returns the reachable selected `mediaRoot` (otherwise null) and `mediaRootOptions: {path,usedBy,available}[]`. Options contain only the common mount and its direct real directories, never symlinks, files or descendants. `usedBy` names the exact owner; `available` also accounts for nesting with another owner's root. `Settings.mediaRoot` retains the saved path when its mount is missing, so the operator can distinguish a missing mount from an explicit clear. Settings reads use the accounts store rather than a tenant settings memo. Imports, target validation, library reporting, scans, sidecars and local reader archives share the checked resolver. No choice means unreachable Kavita folders and `TARGET_NOT_CONFIGURED` before enqueue. Symlink ancestors/escapes and ambiguous suffix mappings remain refused. Local page-cache keys include the archive path and filesystem identity; a cached local page never bypasses root validation.

A one-time, transactional migration per common mount snapshots existing accounts before account edits at startup (or after first setup). Existing real username roots take precedence over numeric roots; unambiguous working dedicated roots are retained first. User 1 keeps the legacy common mount when no dedicated root/explicit reservation conflicts. A renamed account whose remembered named root no longer resolves is left null; its old isolation marker alone never deprives user 1 of the common mount. An already explicit subfolder reservation keeps user 1 null. Existing ambiguous/unsafe/missing roots remain unconfigured. The old implementation remembered only that a named root existed, not its former spelling, so it cannot infer an abandoned arbitrary folder after a rename. The account can choose it explicitly. The migration marker and nullable choices prevent future directory appearances, renames or restarts from re-running inference or overriding a clear. No files or Kavita-side paths change.

`tests/tenant-migration.test.ts` upgrades realistic pre-v9/v9 copies with 1,200 works and ledgers, compares preserved rows and file bytes, checks session continuity, interruption recovery, idempotence and environment defaults. `tests/multiuser.test.ts` exercises the entire protected route inventory concurrently, settings and library edits, memo boundaries, asynchronous streams, private image/cover/page files, roles and deletion. `tests/tenant-worker.test.ts` verifies bounded scheduling, private leases and blank-tenant skipping; the idle/performance suites retain their query/timer budgets. Container smoke checks two different Suwayomi URLs and independent libraries in disposable storage.

## Protocol choices

Suwayomi is pinned to release `v2.4.2366` (`40bc5da`). Source IDs use its `LongString` scalar and remain strings end to end. Chapter numbers use `chapterNumber`; extension mutations use `UpdateExtensionInput.patch`. APK/JAR upload is not necessary for repository installs: these use `updateExtension`, the supported path requested in the brief. The app never selects or installs third-party extension stores automatically.

Search fans out with `Promise.allSettled`: AniList, MangaDex, MangaUpdates and local FTS. Each public request has a 2500 ms deadline. Exact normalized aliases merge within one media type; conflicting known provider IDs prevent merging sequels/remakes. This heuristic can miss unrelated-language titles without a common alias. It never promises a universal identity graph. Provider failures remain explicit in the response; partial results are usable. Per-provider successful results persist in the bounded SQLite metadata cache with a 30-second freshness TTL and stale-while-revalidate; local FTS, tracked works, indexed Kavita series and presence are recomputed per response. `fast=1` reads persisted provider values without refresh/network and returns `partial:true`, using the same merge/ranking/enrichment pipeline as the complete call. Search is query-driven, not an invented discovery feed.

Deep search resolves enabled installed sources in preferred languages and queues source calls behind a process-wide per-Suwayomi-URL budget of six, with four background slots and interactive priority. An active call has a 20-second deadline, independent of its queue wait. Search, matching, browse and popular sync share the gate; streams publish each completion immediately. Disconnect cancels queued and active source requests. Actual hits are indexed in FTS. Popular sync iterates a bounded number of pages (1–50) per source and streams progress. These operations progressively index the catalog. Extensions that are unreachable or protected by unsupported challenges can fail independently. Source preferences are stored separately from legacy favorites, which migrate once on first preference access. Empty enabled IDs means all matching sources in Suwayomi order; explicit IDs determine search priority. Every source search/browse persists latency and a safe error code; successful calls above four seconds are slow. GraphQL extension messages classify Cloudflare/challenges/CF 403, HTTP errors, login requirements and other errors separately. `source_error.detail` and persisted health detail contain the complete sanitized extension message without a character cutoff, with URLs/query strings, credentials/tokens and emails removed. Messages are never logged raw; Cloudflare mitigation headers are also recognized. Browsing uses the pinned filter union (all eight types), aliased defaults to avoid GraphQL field conflicts, bounded nested groups and the same FTS indexing as search.

Kavita scans need a configured library including that tenant’s mounted path. The persistent index enumerates `Library/libraries`, pages `Series/all-v2` by library, and retrieves `Series/volumes` with at most two changed/new series concurrently. It also fetches `Series/metadata` and stores series/library identity, name/localized/original/sort aliases, folder, summary, genres, guessed library kind, all-chapters-read state and distinct numeric chapter numbers in SQLite. Specials and the loose-leaf/volume-only sentinel do not invent chapter numbers; bounded numeric ranges expand into their numbers. A lightweight per-library listing compares last-modified/updated, last-chapter-added/scan and reading fields to persisted revisions, fetching metadata/volumes only for changed/new series. Missing timestamps force conservative reloads; daily or connection-identity changes force a full reload. Successful diffs (including deletions) commit transactionally; failure keeps the old index and marks it stale/error. The background worker checks it every fifteen minutes; POST sync is durable and nonblocking, with a 60-second retry backoff on failure. Kavita's scan acceptance itself is asynchronous. `scanKavitaFolder` sends `{apiKey,folderPath}`: Kavita's anonymous scan-folder endpoint reads the body key and requires an admin. A bounded denial-body check maps its fixed non-admin response to `KAVITA_NOT_ADMIN`; all other failures become `KAVITA_SCAN_ERROR`, never upstream text. The batch records `{state,error,at}` separately from chapter completion. Plugin-auth JWT roles establish `ServicesStatus.kavita.admin`; a URL/key-hashed ten-minute boolean cache contains no tokens or keys. Unknown roles remain null; known non-admin keys gate cover uploads, whose 403 also maps to the safe denial code.

Presence matching first honors sticky manual linkage: an explicit ID selects that series and an explicit null forbids automatic presence/progress/source fallback. Otherwise it uses a saved tracked series ID, then exact normalized title/alias equality with exactly one indexed series. Every catalog response, related/recommended item and tracked media gets presence from the local snapshot without blocking on Kavita. Cached search results recompute linkage. Chapter lookup can accept a catalog `mediaId` or resolve selected tracked/FTS source identities; ambiguous results expose no owned-number guess. Ownership and update detection union indexed numbers with the import ledger, preventing automatic downloads of existing Kavita chapters.

Reading progress uses the indexed match first, with the legacy bounded `Search/search`, `Series/{seriesId}` folder/title lookup as fallback when no index match exists. Resolved IDs persist. `pagesRead >= pages` marks a numeric chapter complete; partial reads affect the latest reading timestamp. Current `maxNumber` and legacy `number` fields are supported; specials do not advance read progress. Refresh is bounded and failures retain previous values. API-key mode uses `x-api-key`; JWT mode exchanges the stored key at Plugin/authenticate. All Kavita image fetches share `kavitaCoverEndpoint`, adding the stored `apiKey` query parameter required by stable v0.9.x while retaining API-key/JWT headers for develop compatibility. This upstream URL never enters browser responses. The image proxy keeps authentication server-side, permits raster image content types only, rejects redirects and caps cover transfer at 15 MiB / 15 seconds. Libraries report mapped folders and real exclusive-create/remove write probes; inaccessible/unmounted folders are not writable.

`libraryTargets` routes MANGA/MANHWA/MANHUA/COMIC/LIGHT_NOVEL/WEB_NOVEL/NOVEL/BOOK to a Kavita library/folder; ONE_SHOT follows MANGA; text kinds are distinct. Schema v11 copies legacy NOVEL targets to LIGHT_NOVEL/WEB_NOVEL without overwriting explicit targets. BOOK remains independent. `library-paths.ts` owns the common resolver for reporting, target validation, imports, cover writes and scan namespace conversion. It tries every Kavita folder path suffix under the mount (`/medias/Mangas` → `<mediaRoot>/medias/Mangas`, `<mediaRoot>/Mangas`) and uses indexed relative series folders as evidence. A series library mounted directly at the root needs positive series-folder evidence. One confirmed candidate wins over unconfirmed suffix candidates; multiple confirmed candidates, or multiple existing candidates without evidence, are refused. A nondefault `kavitaLibraryPath` can override only when its prefix and reachable directory match, confirmed by series folders when available. Realpath containment excludes symlink escapes. Existing suffix directories can establish a unique mapping before the first index completes; no arbitrary root fallback is used.

Library definitions and kind suggestions persist in worker state so target selection works across route instances/restarts without upstream calls. Names infer MANHWA (including Manwha)/MANHUA/LIGHT_NOVEL/WEB_NOVEL/NOVEL/BOOK/MANGA; generic Book types default to fiction NOVEL, LightNovel types to LIGHT_NOVEL. Indexed EPUB/PDF series use NOVEL when the generic library kind is Manga; non-fiction genres refine generic NOVEL to BOOK. The name takes precedence over the generic library type. A kind is suggested only by a matching name/type; MANHWA/MANHUA never fall back to Manga. Stored v5 broad suggestions are reclassified on read. An explicit null kind target disables suggestions and fallback and refuses downloads with 409 TARGET_NOT_CONFIGURED. The saved kind target wins; otherwise exactly one reachable writable suggested folder is required. `createBatch` refuses 409 TARGET_NOT_CONFIGURED before persisting any job if there is no effective target. Each ancestor is checked again before creation/writing. New series folders use a sanitized title plus a stable `[bunko-<12 hex>]` suffix. SQLite folder reservations use persistent work UUIDs, independent of reusable tracked row IDs. Existing import/Kavita folders are reused when their ownership agrees; a conflicting reservation is refused with `IMPORT_CONFLICT`. A matched series folder inside the target and library is reused exactly, and scan paths are derived relative to that resolved target, preserving Kavita's namespace. Old files/folders never move. Chapter filenames follow `Series Ch. 0012.5.cbz`, optional `Vol. 03`, and `Series SP - chapter name.cbz`; specials additionally embed ComicInfo Format=Special.

Successful index refreshes run automatic tracking when `autoImportKavita` (validated boolean, default true) is enabled. `kavita-track.ts` shares the explicit track-from-Kavita unique catalog scorer. An unmatched/ambiguous series, or a catalog match blocked by an existing manual/conflicting link, becomes a `kavita:<id>` identity with provider `kavita`, proxy cover, indexed summary/genres and guessed format. Automatic imports apply to either role inside that tenant. New status is COMPLETED when every chapter in that tenant’s Kavita has positive pages and all pages read, otherwise READING. Existing choices are retained. Tracking/dismissal checks repeat transactionally after network matching so edits made during lookup win. DELETE records durable dismissed series; automatic refresh never recreates them. Kavita-only media details use the local snapshot and return empty relations/recommendations; source matching uses the normal title scorer. PATCH can replace catalog metadata and indexed identifiers without losing row identity/history/progress, translates unique conflicts to ALREADY_TRACKED, and stores sticky manual series links/unlinks independently of catalog metadata.

`kavita-cover.ts` fills absent `cover.*`/`folder.*` images only in resolved writable series folders. Catalog downloads require an allowlisted HTTPS host, no credentials/nonstandard port/redirect, raster content type and 15 MiB / 15-second limits. An exclusive temporary file, fsync and exclusive hard-link publication make `cover.jpg` complete without overwriting a user cover. Kavita's scanner does not interpret external series sidecars as custom covers, so Bunko uploads the bounded bytes using `Upload/series` (base64 data URL, lockCover true), then scans the original series folder. Durable pending state retries uploads/scans; a digest detects user replacement and cancels our upload. Kavita-only entries initially use the authenticated cover proxy, then their own retained Bunko cover.

Suwayomi v2.4.2366's `fetchChapterPages(input:{chapterId})` returns `pages:List<String>` containing `/api/v1/manga/{id}/chapter/{index}/page/{index}` proxy paths. Only those relative paths are accepted; HTTP Basic auth goes exclusively to configured Suwayomi with redirects refused. Each page has a 20 MiB / 20-second limit and a supported raster content type. A chapter is capped at 2000 pages and 256 MiB page bytes. Its ordered pages and XML are assembled in memory, so allow RAM for page buffers and ZIP creation. Exclusive temporary CBZ creation, fsync and rename happen before ledger insertion. Reader and download pages share the bounded tenant image cache and survive partial failure/restart until LRU eviction; successful imports remove old legacy per-chapter cache folders. No Suwayomi download directories or ZIP extraction are used. Metadata writes use temporary files and rename; covers use exclusive atomic publication; optional provider covers retain the restricted HTTPS host allowlist.

Arr results retain rejection information. Sonarr grabs use `/api/v3/release`; Prowlarr grabs use `/api/v1/search`, so results are not incorrectly sent to Sonarr with foreign GUIDs. Grabs use the upstream search cache and can require searching again after expiry. Existing Sonarr series/indexers/download clients must already be configured externally. Light-novel metadata/tracking is supported; no EPUB text scraping or conversion is implemented.

## Source identities and tracked cover state

Catalog detachments are explicit tracked-row state. PATCH builds a fresh Kavita/source media identity, clears catalog IDs and retains the row/history; no alternate identity returns NO_IDENTITY. Automatic import returns an already linked row without catalog replacement. Explicit media replacement can restore a catalog identity. Exact catalog IDs or a unique linked source/Kavita identity also connect search/detail cover presence without fuzzy title reassociation.

`tracked-sources.ts` owns continuous source discovery, persistent dismissals and manual/automatic provenance. It processes one eligible source-less MANGA entry at a time, prioritizing never-searched entries, then searches older than seven days. Enabled-source searches run in parallel with the normal title scorer and shared per-server upstream budget; recent background source errors back off one minute. A score of 0.9, best eligible candidate per source and a three-source ceiling constrain automatic links. Transactional rechecks after HTTP preserve concurrent identity/source edits and dismissed pairs. Manual source replacement persists removals and resets retained links to manual.

Every linked entry’s update check persists source title/thumbnail metadata, latest numeric chapter, chapter count, timestamp and safe errors. Source/chapter metadata calls share the six-call gate with searches. Failed checks preserve prior successful values; removed links cannot be resurrected by a completing HTTP call. GET tracked derives released as the maximum of raw catalog chapters, linked statuses, historical observations and Kavita/imported numeric chapters. Oldest-status ordering prevents a slow large library from permanently starving older entries.

`tracked-covers.ts` separates raw catalog metadata from the effective cover. The persisted choice is auto or a validated origin/id with a resolved selected URL. Before validation, auto derives catalog → ordered sources → Kavita locally. A successful bounded fetch persists the selected URL and consecutive-failure count in `resolved_covers`, so GET never requires upstream traffic. Identity, cover choice and ordered source/Kavita links form its resolution context; metadata/thumbnail changes alone do not change it. Two consecutive failed checks permit a replacement; a success clears the count. Choice/identity patches or a changed link context permit immediate re-resolution. Even entries without a Kavita match can retain a validated automatic resolution. Cover options add at most twenty MangaDex volume covers with a durable 24-hour cache. Selected covers propagate to tracked/media/search/discover output without overwriting raw catalog cover metadata. Restart preserves manual choices.

Tracked cover synchronization checks oldest-attempt entries first so its 60-second budget cannot repeatedly starve the rest of a large library. It serializes writes/uploads across route bundles, downloads only allowlisted catalog images or validated authenticated proxy shapes, and caps each image at 15 MiB/15 seconds. It updates a complete sidecar via fsync/atomic rename in a resolved writable series directory; API upload can still work without a mounted folder. Upload/series uses lockCover and a durable SHA-256 byte hash: equal bytes do not upload again across origin/URL changes or restart. Failed requests leave the choice retryable. Kavita’s own cover is copied to a sidecar if available but never uploaded back, preventing a feedback loop. The initial legacy missing-sidecar bootstrap retains its exclusive-write and pending-scan behavior and shares the upload hash.

## Library activity and cover fallbacks

`source-match-state.ts` derives the matching queue from SQLite and ties the persisted current entry to its worker lease owner. `TrackedMedia.sourceMatch` exposes linked/queued/searching/not-found. Foreground discovery for source-less followed works commits confident links through the same guarded transaction as the worker and emits `linked`; custom queries stay suggestions and manual edits/dismissals win. A tenant library write revision and matching/refresh progress drive shared client revalidation without dropping final updates or missing short scans between polls. ## Persistent cache boundaries

Database startup idempotently adds `metadata_cache`, `image_cache` and `resolved_covers` alongside the v7 schema, without changing existing rows or lowering `user_version`. Resolved covers reference tracked rows with cascade deletion. The legacy missing-sidecar bootstrap also records its successfully fetched automatic cover.

`metadata-cache.ts` stores JSON, UTF-8 size, last successful refresh and last attempt. At most 1,000 values / 64 MiB survive pruning by oldest successful refresh, with an 8 MiB per-value cap. A process-global, volume-scoped promise map coalesces cache misses and stale refreshes across independently loaded route bundles. Stale values return without waiting; failed refreshes retain the saved payload and back off for 30 seconds (or the TTL when shorter). Provider requests have their own deadlines and outlive browser request cancellation. Discovery retains its ten-minute TTL; detail data uses 30 minutes; genres and MangaDex volumes use 24 hours. Existing durable MangaDex volume options are adopted from worker state on first use, preserving offline upgrades. Public metadata integrations are AniList, MangaDex and MangaUpdates; there is no Kitsu client. Suwayomi detail cache keys also include a hashed configuration/authentication namespace.

Followed detail requests seed missing detail extras from `tracked_media` and immediately return that durable media. A successful background load conditionally updates its saved JSON/title using the pre-fetch identity snapshot, preserving concurrent edits, sources, reading state and resolved cover. Stored detail extras enrich the response locally. Unfollowed detail requests use the same persistent cache and only need network on a miss.

Private image and retained-cover responses vary on `Cookie` and `Authorization`, including 304 responses. A browser changing accounts cannot reuse one tenant’s cached private image for another tenant at the same proxy URL.

`image-cache.ts` stores a self-contained MIME/timestamp header and bounded image bytes in one 0600 file under `<data>/users/<id>/cache/images/<sha256(key)>`. Temporary creation, fsync and atomic rename publish a complete value. SQLite triggers incrementally maintain cache byte/count totals in `cache_usage`, including updates/deletions/replacements. Publication uses async filesystem writes/fsync/rename and never walks or sorts directories. Exceeding 500 MiB schedules asynchronous LRU pruning to 450 MiB in batches of 32, yielding between batches; indexed access-time queries choose victims. Once-daily asynchronous reconciliation removes orphan files and old crash partials. Metadata eviction likewise skips its bounded SQL prune while counters remain below the limits. Configuration/credential hashes isolate upstream identities without storing secrets in cache keys. Both image routes use this cache, including Suwayomi extension icons. At most one stale refresh attempt per day is claimed in SQLite, with a shared in-process promise for concurrent misses. Failed upstream refreshes keep the previous complete image. Authentication and proxy input validation still run on cache hits and 304s.

Image responses persist a strong SHA-256 ETag when bytes are published and reuse it on disk-streaming hits. Legacy cache headers compute it once per process until refreshed. Responses support `If-None-Match` lists, weak comparison and `*`. They use `private, max-age=86400, stale-while-revalidate=604800`. A successful `Upload/series` invalidates that series' Kavita cache file and detaches/invalidates any prior in-flight response so it cannot repopulate the cache. The chosen automatic bytes are passed directly to the existing cover synchronizer, keeping validation and upload consistent; its persisted byte hash suppresses redundant uploads.

`progress-refresh.ts` claims on-demand refresh attempts at most every 120 seconds per tenant using its private SQLite timestamp. Independently loaded route modules share one process-global run per tenant directory and user ID. Concurrent callers await that run; calls later in the window return saved progress immediately. Each run retains the existing four-entry concurrency and 15-second total deadline, and failure keeps the stored progress and throttle timestamp.

`tests/persistent-cache.test.ts` uses isolated temporary storage and deterministic upstream fixtures to verify disk hits/misses, module reloads, ETags/304s, stale failure/recovery, LRU eviction, upload invalidation/in-flight races, persistent metadata/SWR/pruning, immediate followed details, automatic cover stickiness/reset rules and progress throttling/coalescing.

## Chapter outcomes and source completeness

Each durable batch embeds at most 500 `DownloadChapter` values and a nullable scan result. Chapter metadata uses the upstream name, normalized number and source name; progress writes carry the pages-done ratio, followed by importing/done or a safe per-chapter error. One failure does not stop subsequent chapters. Ledger reconciliation precedes transfer and cancellation, preserving imports after interruptions. A batch with any successful imports finishes as completed; all-failed work is error. A failed scan remains independently retryable on a completed batch. `retry_failed` requeues only failed chapters in one/all batches (requests during active work persist the selected IDs and run after it finishes); legacy retry also supports scan-only recovery. Snapshots and SSE share `listBatches`, which normalizes old JSON into the new fields and caps arrays. Updates derive failure/success from linked chapter outcomes so a partial batch cannot mark a group downloaded.

`chapter_labels` retains bounded source labels from chapter selection (20,000 entries, oldest evicted) under a hashed Suwayomi configuration namespace. Enqueue copies these labels into batch JSON without an upstream wait; arbitrary/legacy IDs resolve labels when the worker fetches chapter metadata. This cache is disposable and cannot establish imported ownership.

Matching count probes request only chapter IDs for score ≥ 0.9 candidates, share the six-call source gate, and cache a count/null for ten minutes under the hashed Suwayomi namespace. Both SSE candidates (maximum three per source) and automatic links (maximum three sources) sort by score then count, preserving preference only for exact ties. No page fetch or Suwayomi download is needed for ranking.

`kavita_cover_status` stores per-entry context, stored hash, series ID, state and safe error with cascade deletion. Writes invalidate the tracked snapshot transactionally. A changed choice/context/hash derives pending immediately; no series or no cover derives none. Cover resolution publishes complete local bytes, then records pending, synchronizes those bytes through the existing serialized upload gate, scans the indexed folder and records synced. Failure records failed for the same current context only. The durable series upload hash suppresses duplicate uploads even after scan failure. Retained bytes remain eligible for retry, and an explicit cover patch wakes/attempts the push promptly.

### Response-cache schema and discovery degradation

Every persisted metadata/response entry written through `metadata-cache.ts` has a `{schema:1,value}` envelope. Increase that schema constant when a stored contract changes; incompatible/unversioned entries become cold misses. Legacy home feeds and last-good top arrays are the exception: they are normalized on read to retain usable shelves. `home-shape.ts` enumerates every non-all DiscoverKind with a typechecked Record, normalizes every latest row to an array and normalizes hero/top arrays. Home composition also applies that normalization before returning HTTP data. An older whole feed retained under a top key supplies only its safe top array. Invalid JSON is a cache miss.

Open Library discovery fails softly: HTTP errors, timeouts and malformed JSON/search shapes return an empty HTTP 200 page with `warnings:[{provider:"openlibrary",code:"METADATA_UNAVAILABLE"}]`. Failures are never cached as successful empty responses. A stale good provider page returns immediately and survives failed revalidation; subsequent reads expose the warning until a successful refresh clears it. Warning state and all payloads remain tenant-local. Search/detail keep their existing provider-error handling. `tests/cache-schema-discovery.test.ts` covers old persisted home shapes through cache reads and the authenticated home route, cache schema compatibility, provider failures, stale recovery and isolation. Media-root coverage includes API claims/nesting/rollback, named/numeric/legacy migration and the renamed-folder regression, plus independent-worker SQLite contention in `tests/media-root-concurrency.test.ts`.

## Optional catalog credentials and adapters

`settings.ts` includes Google Books, Metron API token/password, Rakuten application ID/access key and Hardcover token in the encrypted-secret allowlist. Fresh installations defer the marker until an administrator exists. The source must be a regular non-symlink tenant DB. Shared-row triggers advance a durable revision on insert/update/delete. ## Immediate ownership and local reading

After a successful batch scan, Bunko polls the affected Kavita series for at most ten seconds (six attempts, 250 ms–3 s delays). Known series use their ID; newly created series are found through a bounded search and an exact scanned-folder match. Only that series' volumes/files are read and upserted, independently of the periodic snapshot revision. Newly discovered series link to the tracked work unless a manual link/unlink supersedes the download. Expected imported chapter and volume numbers determine completion. Late/unavailable indexing requests a durable index refresh without turning a successful scan or imported CBZ into a failed download. Connection changes and tenant revocation discard late results.

Chapter lists project the union of the import ledger and the linked Kavita index, including numbers missing from all source responses. These rows have `localOnly:true`, no variants and their indexed/imported volume when known. Local chapter reading resolves an owned number against the followed/indexed/imported work, its archive pointer or Kavita file path (with an unambiguous chapter-filename fallback). Directory and realpath checks run before cache access and stay under the chosen tenant media root. Indexed volume files support arbitrary CBZ names. Local identities use negative chapter IDs backed by `local_reader_chapters`, avoiding collisions with positive source IDs; local progress uses the existing page validation, coalescing, resume and monotonic read marking. Numeric neighbours include all owned numbers. No Suwayomi request is required.

`kavitaCoverSync` controls all Bunko cover pushes and cover sidecar writes for a linked work, including bootstrap and direct series synchronization. Disabled entries report `kavitaCover.state:none` while their Bunko cover remains available. The upload path rechecks the choice after asynchronous work. Re-enabling clears the prior Kavita upload hash and immediately resolves/pushes the current cover, restoring it even if Kavita was edited during the disabled period.

## Coherent reading and loading (October 2026)

Owned chapter rows and the main Read action prefer a local archive. A historical positive
source URL can resolve a pre-Bunko Kavita file through the current namespace-qualified
`reader_chapters` record, without a source request. Its previous source position is used
until a local position exists. The reader merges current-lane source neighbours with the
work's owned numbers, including imports from other source connections. Pure local reading
uses accessible owned archives; missing files do not produce dead next/previous links.
Chapter and volume sequences remain separate, including manually retyped imports.
This does not automatically select an unowned chapter from another source or infer edition
identity from matching numbers. Existing source and local IDs remain valid.

`MediaLink` seeds the destination browser detail cache from the selected card before
navigation. The sheet revalidates on entry, shows that preview during loading and preserves
it on failure with the partial-data notice. It does not submit a preview as server metadata.
A route loading boundary and a pending link indicator cover navigation/chunk delays.
Quick search, posters, releases, planning, library, related titles and download/update links

The existing tenant `write_versions` table now also tracks `content` and `progress`.
Triggers advance these domains transactionally; page-position writes do not advance content,
and release ingestion advances its existing release domain. Activity returns all three
revisions and active-download count. Mounted views revalidate by domain: content affects
library, sheets, chapters, reader and catalog projections; progress affects library/sheets/home;
releases affect home/planning/releases. Activity polls at five seconds while busy, thirty
seconds while idle, and on focus; the reader independently refreshes every five visible seconds.

Unchanged chapter labels, reader inventories and released maxima no longer perform SQL

## Download cancellation and maintenance recovery

The lease-owning worker continues to pump durable download batches while source matching,
cover backfill or Kavita/update maintenance runs. A wake on enqueue, retry, pause or removal
interrupts its wait; task completion also wakes the pump. Slow maintenance does not hold new
lots in `enqueuing`. The worker retains one maintenance run at a time and the existing source,
chapter-transfer and tenant concurrency limits. It sleeps when idle instead of polling rapidly.

Before processing a queue snapshot, `processBatch` reloads the durable batch and ignores
removed/terminal entries; a cancelled snapshot cannot overwrite `CANCELLED`. Worker ownership
and tenant revocation are included in the transfer signal. Kavita index requests issued by the
worker/update check inherit its lifetime, so lease loss cancels ongoing index network work.
Existing imports, files, retry generations and pause preference remain intact. On restart,
nonterminal lots already in SQLite are retried through the same pump after lease recovery;
no purge or queue reset is required for this correction.

Library's source-less view lives in the sort dropdown, intersecting the active format, status and
ownership shelf. It includes pending, searching and unmatched manga works; novel/book integrations
do not participate in Suwayomi source association. Only that view exposes the bulk action, and its
submitted IDs match its visible works. Matching progress remains informative in other views.
Sheet summaries and library card stock labels show actual chapters and tomes separately from the
chosen progress unit. A complete owned tome may cover source chapters with known tome metadata;
that coverage does not turn it into individually owned chapter files or change reading progress.
